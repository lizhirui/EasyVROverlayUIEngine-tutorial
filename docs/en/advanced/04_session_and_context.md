# Engine Sessions and Context Management

Open two applications, each with two windows. When you click on the text box of Application A, then enter the confirmation window through its button. At this point, several questions need to be answered separately. Which session should the server send the keyboard to? Which window can be selected by the laser? Which control within Application A holds the editing focus? When will the callback from the outer button that initiated the confirmation continue? These questions involve connections, windows, controls, and call stacks. Understanding the lifespan of each layer allows us to explain why multi-layer modals can block callers while allowing other windows to continue processing messages.

## 1. From Connection to Registered session

The engine listens for TCP connections via IPv4 or IPv6 and assigns service-side session numbers to these connections. At this stage, only session numbers are assigned; protocol operations must wait until TLS and application authentication are completed. `ipc_connection::implementation::run()` first initiates the handshake, calls `authenticate()`, sends `welcome`, then enters the `verified` state, starts heartbeat operations, and handles regular requests. When a client reconnects, it receives a new connection and new session identity; the old window number mapping from the disconnected state cannot be directly reused. For handshake data and frame formats, see [Chapter 03](./03_ipc_tls_protocol.md).

The local loopback connection provides an opportunity to use the system TCP table to find the parent process. After finding the process and establishing `process_watch`, the engine checks if the declared PID is consistent and retains the verified PID and process creation time. PID is a short-term number that can be reused by the operating system, and the creation time helps distinguish new processes with the same number. If the connection comes from a remote location, the same number PID on the service machine cannot represent the initiator. `welcome` can return the declared remote PID, but the local process identity passed to the management operation during runtime is empty. The loopback search itself may also fail; to determine if local process-level operations can be performed, we should look at the verification result. Any `welcome.owner_process_id` cannot be considered a trusted local process handle.

The Engine host connects the connection layer with the business layer. The host requests a callback to subscribe to tracking status in the protected runtime context, reports the session, connection process, and name to the application and Desktop tracker, and then hands the request to `service_runtime::execute()`. The transmission of `verified` and when the application registry observes the first request are two different observation points. A connection with a valid session does not mean it has already submitted a window. A window may also remain hidden for a long time; when querying, we should read the session, visible windows, and application objects separately according to their purpose.

## 2. session Roles and Auxiliary Surfaces

Ordinary applications create their own windows using `present` and can open the input area on the appropriate current window. Layout or IME sessions are registered through `input_provider_register`. The registration conditions check that the session has no active input area and that existing windows meet auxiliary surface requirements, then the input component management logic records its role. Roles are used throughout the connection lifecycle, and message processing is determined by the registered identity. An invalid registration request will fail, and the existing focus state of an ordinary window cannot be quietly changed to the input component state.

Auxiliary surfaces are windows with specific conditions. For example, IME candidate windows and virtual keyboards are drawn with their own controls but need to be placed near the application input area. The Engine determines their spatial position and eligibility based on the input area and current component state. Clicking on an auxiliary surface can move the pointer to the application it belongs to, while keeping the current ordinary application window as the keyboard input target. This is the basis for words entering the original text box when using the laser to point the keyboard. The display position of auxiliary surfaces and the public tracking mode of ordinary applications belong to different control layers.

Role mutual exclusion addresses timing and ownership issues. If the same connection serves as both an input user opening the input area and a component generating text within that area, the service must determine which windows in the same session should close along with the old area, which should remain focused, and which thread operations should wait for which components. With mutual exclusion roles in place, a regular close command affects the original application window, while the eligibility to send and clear auxiliary components is managed separately along the input path. The SDK can also decide whether to use the regular window or auxiliary surface for submission based on the role. For the complete timing sequence, see [Chapter 06](./06_input_routing_and_drain.md).

## 3. Window Lifecycle, Local and Global Numbers

Let both applications A and B use `window=7` as the local numbering. The server first finds `session_map[session]` using the current verification session, converts window 7 to a global surface ID, and then accesses `surface_map`. If session A closes its window 7, the surfaces mapped to A will be released. Cross-session selections for input, rendering, and tracking require a global identifier, which is restored when the application is sent back. Window names, display titles, and these two numbers should be considered separately. The first two can be used for interface presentation, while the mapping key indicates ownership.

The engine verifies and maintains the surface for the session with `present`, including metadata, commands, and initial layout. If there is no existing record for this window, a global object is allocated and a mapping is established. Subsequent batches can only change the locatable windows or nodes. Hidden windows may still save surface data, allowing reuse when displayed again. When a submitted window is closed, the SDK sends `surface_close`, and the service cleans up the surface by session. When closing repeatedly, the closed records associated with the session are used to distinguish between expected and unknown objects.

When a session disconnects, `service_runtime::disconnect()` organizes its input state, collects global surface IDs under that session, and then closes the surfaces one by one. Subsequently, the session's mapping, tracking cache, and closing records are removed, and the component connection state is updated. Copying the list of IDs to be deleted before closing can prevent destroying the original mapping while deleting objects. The host's disconnection callback also notifies the application of registration and Desktop tracking. Resource recycling occurs by session, so the management interface can know whether all surfaces of a program disappear or a single window closes.

Two log fields can be used for practice. Record the session ID and local window number for `window=7` operations generated by the client, and the global surface ID for Engine's hit records. If an event is mistakenly sent to another application, first check the input values of the two mappings. If an unknown window is reported after the same client reconnects, confirm that the operation uses the window handle of the same generation as the current connection. Comparing window titles only indicates the same name and cannot replace these two checks.

## 4.Z-order, spatial distance, capture, and current window

### The same position may appear overlapping, with various reasons.

Suppose two surfaces are adjacent. If they adopt the same pose, position, and physical scale, they appear completely overlapping from a specific perspective. Overlay synthesis must follow a sequence, and the same distance can be calculated for the rays between the two surfaces. If the order is available but the graphic depth is the same, the operator cannot determine which surface is currently hit from the image. The initial placement of windows takes into account the source window and existing surfaces, with results processed by the engine. When verifying placement, consider spatial position and rotation to avoid overlapping from the root, and then check if the display order is appropriate.

Let A be 0.85 meters from the controller, and B be 0.70 meters from the controller. When both windows are visible and the rays intersect with the surfaces, the intersection point of B is closer, and the laser stops at B. If B is disabled or blocked in mode, it remains a geometric occluding surface, and the engine draws the laser landing point there. Only after hiding B or having the rays bypass B can the rays reach A. If the controller already captures A, the engine first processes A that still meets the capture rules.

Visual Z-order and the current window can also be understood through the title bar and auxiliary windows. When a button on the virtual keyboard in front is hit, the surface providing input can be located visually in front, but the server keyboard target continues to point to the regular application. This applies to candidate windows as well. The focus of input within the application does not change with the hover of another process. Debugging requires looking at data from three stages simultaneously. First, look at the global surface selected by the engine, second, at the local window ID sent to the target session, and third, at the controls selected by the SDK in that window. The same local window number does not mean the cross-process target is the same.

The experience of the two windows before and after also depends on whether capture has started. When holding and moving the control out of the surface, the original event target still receives the position. If capture is released and a new surface is hit, it does not necessarily result in the click that was originally intended. The engine also tracks the condition that the press must be released first before accepting new interactions. Testing "moving from one place to another" and "pressing again in another place" separately can verify boundary behavior.

In traditional two-dimensional desktops, overlapping windows are often treated as a stack of papers, and it's only necessary to determine whether a screen point falls on the topmost one. In VR, each surface has a real spatial pose, and rays may first pass through a segment expected in the "foreground" or may pass outside the edge of a closer window surface. Two sets of relationships need to be observed. The display order of overlays serves for synthesis. Currently, `overlay_manager` uses fixed sorting values for windows and lasers, while the intersection between ordinary windows is calculated separately. The pointer determines occlusion based on the actual intersection distance of visible and locatable window surfaces. For the nearest window surface, it determines whether to deliver an event based on available status and `is_eligible()`. When `service_runtime.cpp` fails to capture, it traverses the windows in reverse order, replacing intersections only when the distance is strictly closer. Equal distances are naturally handled according to the traversal encountered, while in general, geometric distances determine the outcome.

For window surfaces with handles and tracking anchors, it's also necessary to consider whether the handle can be reasonably used to interact with them, with auxiliary surfaces being constrained by their working status. The nearby display area can leave an extended edge for the laser beam, but the actual operable target still needs to hit within the window boundary. If it is found that the beam is still lit outside the window edge, this observation alone cannot assert that the button can be clicked. It's necessary to distinguish between visible laser beams, actual hits, and interactive captures for three sets of outputs. For detailed calculations, see Chapter 07 of [and](./07_spatial_math.md).

Once a legitimate pointer capture is obtained, the update process prioritizes checking whether the window is still valid and calculating its intersections. When necessary, broader projection scenarios are considered, even using the previously captured position as a backup when the window is locatable. When capturing allows dragging the scroll bar or adjusting the window, the pointer's movement out of the area still has a clear destination. When the target is hidden, becomes non-interactive, releases the capture, or the session disconnects, both the service and SDK must close in accordance with the corresponding status.

The current ordinary window of the Engine does not change every time the hover hits. Target selection is related to the interaction phase. When the trigger is pressed or the side grip hits a suitable ordinary window, the window can be selected and the old input path can be closed. The selection of an ordinary window is independent of the focus of the control. After the title bar of a window is clicked, it can become the current window, and whether the text falls into the text box is still determined by the session SDK. Cross-window debugging should record the ray target, capture target, current window, and internal focus of the application separately. If one of these items is missing, another should be used for speculation, often leading to the mistaken belief that a normal focus transfer is an event loss.

## 5. Application discovery, working directory, and management list

`.easyvrui` is the application startup list, with `name` providing localized names, and `launch` determining the native program or Python script and parameters. The Desktop configuration records the managed list path, and the File Manager can also obtain the list from the current path or file associations. The SDK parses and starts the program on the machine where the process is located. The relative execution path in the list and the working directory of sub-processes are based on the list directory. This startup directory has different uses from the configuration directory next to the Engine executable file and the design file directory of `.easyvruifrm`.

The following list assumes that `main.py` is next to the list. If the engine on the calling machine is remote, the application must obtain connection materials before submitting the window to the same service. By deploying scripts along with the list, a portable directory layout can be described using relative paths. The caller can add parameters through the public startup interface, and a single instance is coordinated by the application itself.

```json
{
    "name":
    {
        "zh": "计数器",
        "en": "Counter",
        "ja": "カウンター"
    },
    "launch":
    {
        "runtime": "python",
        "script": "main.py"
    }
}
```

The applications installed in the list also differ from the currently running sessions. The startup list can exist without a running process, and a process may also be started from the command line and connected to the Engine. The running information of the Task Manager is generated based on active sessions, connection identities, and window records. Only targets that have been verified and meet relevant permissions can be used for local process management. Remote sessions can provide window and communication status, but the server cannot directly operate on local processes with the same number that are coincidentally connected, based on the remote declared PID.

## 6. How ordinary applications drive a message pump

### How the keyboard moves to the appropriate window during the modal period

The modal blocking of the SDK updates the interactable status of the window, and the Engine processes it according to the current window rules after receiving the update. For example, if the main window currently has the keyboard, after opening a confirmation box, the main window is still visible but temporarily disabled. The service suspends the main window's eligibility for selection and reorganizes the old input path. If there is only one interactable ordinary window in the same session, the keyboard can be taken over by that window. This is the common condition where "you can enter information in the confirmation box immediately after opening the main window." If there is a third interactable ordinary window in the session, it cannot be guessed based on just one of the newly appearing ones; the laser selection can still be explicitly used.

When the original window is re-enabled, it can return to the original target according to the restoration order, provided that it is still visible, belongs to the original session, and reference is available. If the user has explicitly chosen another application window, subsequent closure of the modal should not reclaim the selection. If the window has been truly closed or hidden, subsequent redisplaying should follow general selection rules. The interactive surface of the auxiliary input bar and the regular candidate windows should also be considered separately; the input bar can receive pointers while maintaining the keyboard location of the original regular window. To troubleshoot modal and input issues, the client's direct owner, Engine, should record three status items: window availability, and the current keyboard window.

The SDK's `ui_runtime::get_current()` obtains the current thread's runtime. The regular program first creates a window, then pumps messages through `easyvrui::run()` or Python `easyvrui.run()`. When there are other event hosts, `pump()` can be explicitly called, with waiting arranged according to the host's conventions. For each round, `pump()` handles the network queue and local callbacks, executes `tick()` to update the clock-dependent state, and then attempts `flush_window_list()`. Waiting is coordinated by `wait_for_activity()` based on connection status, key or controller scrolling, cursor, and idle deadline.

This is a model where work is consumed by one owner thread. The background reader can receive service data, and interface event handlers are still executed in the owner thread. Background application tasks are also delivered to this thread. The regular `run()` checks whether there are windows that still need to be driven and whether there are runtime stop markers. At the end, `finish_run()` is called to complete the corresponding asynchronous cleanup, and the connection is closed if necessary. A window being hidden does not mean it is closed; the termination of the message loop should be determined based on the actual statistics during runtime.

`process_message()` first distributes directly, then attempts to submit changes when an active connection exists. Taking window input events as an example, it selects the correct window for distribution, then searches along its control tree for a receiver. The SDK maintains `dispatch_window` for semantics of the source window and the new window during distribution. This context allows windows created in button events to reference the correct source window. Having the source context and delaying all inbound events due to distribution are different approaches. In the former, each distribution is set according to its own semantics, and the source window is restored; the normal nested message loop still uses a shared queue.

## 7. Understanding synchronous return from Win32 modal habits

Consider the usual Win32 pattern. The caller disables the owner with `EnableWindow(owner, FALSE)` while the confirmation dialog continues to receive input. The caller then enters a nested loop using `GetMessage` and `DispatchMessage`. When the dialog has a result, the caller exits that inner loop and restores the owner's ability to receive input. MFC and similar desktop frameworks expose the same pattern as a modal window API. A Windows framework may also provide dialog keyboard navigation and application shutdown handling.

Breaking "blocking" into two layers makes the code clearer. The outer button function now stops at the modal call line, with local variables still on the stack, so the statement does not continue before the dialog box returns. The inner loop still runs on the same thread, capable of dispatching messages and executing the dialog box's button callbacks. The thread's program counter is still in the inner loop and is not permanently frozen. Other windows with interaction capabilities can still be processed. As long as there is no lock that must be held to obtain other callbacks across modal calls, the business can organize code in this order.

EasyVRUI corresponds to SDK window surfaces and event permissions. `begin_dialog()` treats the display window as not closed, invisible, and not in a modal state, verifying that the owner belongs to the same runtime and is interactive. It resets `dialog_result` to `none`, sets the owner's status with `dialog`, and displays the window. The SDK uses `get_blocking_dialog()` to determine whether the direct owner has a visible and active modal subwindow, cancels related interactions, and updates the submission status. It applies to its own window and Engine window surfaces, conceptually equivalent to temporarily losing interaction rights. unrelated session windows are not blocked by the direct owner rule.

## 8. How the same thread enters two layers of EasyVRUI modal

### Blocking is a relationship on the call stack

Suppose each function places its local variables in the stack frame when it enters. The main loop calls the button callback, which in turn calls `show_dialog()`. A normal C++ call does not destroy the caller's local variables; at this point, the button callback's stack frame simply waits for the called function to return. The inner `show_dialog()` execution, after one pump, can call another button callback, resulting in a new ordinary function call. The local states of the two callbacks are saved by different stack frames. When the interpreter executes the Python callback, it also creates an independent call frame. The network continues to be received by the background, so there is no need to copy the entire UI runtime for internal use.

To understand this with a verifiable difference, when the modal passes the owner, it prohibits the interaction of this window. If the application sets the business attribute `enabled` of the owner to true or false, there are additional reasons and lifespans for that. The current implementation accumulates the window's own qualifications and modal blocking through `is_interactable()`, and queries the active dialog box to obtain results. Therefore, even after the modal ends, a window that originally did not have interactive qualifications will not become interactive out of thin air. The metaphor of windows helps understand temporary blocking of the owner; when writing business code, window attributes should not be overwritten additionally.

The two layers also maintain a reasonable owner over time. Running A blocks the main window, and at this moment, B should use A as the owner. If the already blocked main window is used as B's owner again, the interactive requirements of `begin_dialog()` will block this call. This ensures that the blocking chain of inner windows is consistent with the top layer that users can still use. Setting `none` does not trigger automatic closure; if business logic wants to explicitly cancel, it can write the cancellation result or directly request normal closure. After receiving the cancellation result, distinguish between "user cancellation" and "a closure that was vetoed by the processor but later confirmed," depending on the process the business wants to record.

`ui_runtime::show_dialog()` enters after `begin_dialog()`, with `item.dialog && !stopped` as the condition for the loop. After each pump event, it checks if it has ended. If it is still valid, it executes `tick(0.0)`, attempts to refresh, and waits through `wait_for_activity()` when more work is needed. Below is a normal example path: the outer application loop, the confirmation window loop, and the second confirmation loop are actually driven by the same thread.

```text
run()
  Main window button on_click
    show_dialog(main_window)   Dialog A becomes modal
      Details button in A: on_click
        show_dialog(A)          Dialog B becomes modal
          B's OK button sets dialog_result = ok
        B returns ok
      A's callback reads B's controls and returns
      A's confirmation button sets dialog_result = yes
    A returns yes
  The main window resumes the original button callback
```

At the deepest level, the main window has a direct modal subwindow A, and A has a direct modal subwindow B. Therefore, the first two are blocked by their direct subwindows. Closing B unblocks A, and the main window is still blocked by A. Closing A restores the main window's qualification. This state can be seen as a direct owner relationship at each layer, derived from the active window state. Business code does not need to manually maintain an additional blocking count.

Setting a non-`none` value for `dialog_result` will attempt `close()`. If the event is cancelled upon closing, the setter restores the previous result and the modal loop continues. If the result remains `none` upon normal closing, `finish_dialog()` adopts `cancel`, removes the `dialog` flag and owner relationship, and related metadata enters the update phase. When closing or hiding an owner, its child dialogs will close according to the respective cause. The dialog object can still be held by the caller and read for business controls after return. This lifecycle is directly related to the reference rules introduced in Chapter [02](./02_sdk_and_engine_interface.md).

## 9. Why can a dual queue and pure nested loops work together

### Check the shared queue at four moments

Suppose the network has received events A, B, and C, and the processor of A intends to open a confirmation box. The outer pump first gets the upper limit of the current round's sequence number, then only takes A from the front of the queue. A prepares the dialog box in application code, while B and C are still connected. When A calls `show_dialog()`, the inner pump gets its own upper limit and can take B and C in order. Whether C happens to trigger another layer's callback by making B start or not, unprocessed messages are still managed by the same connection. Eventually, the inner loop exits, and the outer loop recovers from the current unprocessed items in the shared queue, rather than re-executing B and C that were already processed by the inner loop.

Now insert a normal synchronous request into A, and assume that the reading thread receives event D before its response. D enters the event queue in the normal sequence, and the corresponding synchronization response is placed in a dedicated slot. A continues with its normal statements after waiting ends, and D is only executed when explicitly entering modal or returning to the outer application pump. The synchronous request does not bring intermediate states into A, but the modal loop can execute D as intended. By determining the respective entrances of these two paths, we can understand why the depth guards used to prevent ordinary recursive distribution are not lost, and why this limitation is maintained.

The shared runtime state still needs to adhere to the object lifetime and scope. When an outer processor obtains a control before calling the modal, events in other inner windows may modify the layout of the same application or close the window of that control. After returning to the outer layer, it is necessary to re-verify whether the objects in use are still alive and in the correct stage according to business requirements. A direct owner relationship can limit the interaction of the specified parent window, while the same thread pump still allows running general tasks and timing-related work. Saving business data that must be maintained across modals as values is clearer than assuming the state of a complex control remains unchanged forever.

### Why is it more important to keep the UI thread running than to sleep alone?

A counterexample is first displaying a dialog box, then waiting on a condition variable in the UI thread, only waking it up with the dialog box button callback. The button callback precisely requires this UI thread to execute; waiting without sending messages to the thread pump creates a mutual waiting situation. Another counterexample is entering modal with the component lock in the same call, then trying to obtain the same lock in any inner callback. Although the loop is still pumping, the callback will get stuck on the lock. In normal use, complete the preparatory work and release these locks before entering modal. The inner layer relies on the thread to correctly assign both tasks, while the outer layer continues business with the return value. Only by coordinating both types of waiting can they work together.

Rendering protection is also a problem of similar work stages. Before the command record of the current page is completed, the SDK does not allow synchronizing the display and operation of another page, because waiting requires running a new submission round. At this time, the dialog box should be opened by the appropriate business event, or the action should be scheduled for the subsequent owner thread dispatch. The diagnostic `dialog_wait_during_render` indicates the specific call location more accurately than "the entire program cannot pop up a window." How to combine ordinary buttons, multi-layer nesting, or background delivery still depends on whether they actually enter the event stage or the rendering stage.

The key is to distinguish between "a calculation result must be synchronized" and "the application explicitly wants to enter a new interactive loop." Synchronous `connection::request()` registers its own ID and waits only for its own response slot, while the background reader adds them to the queue when receiving events. Waiting for a result does not require executing application code, so there is no reason to suddenly assign a new click halfway through any property operation. In contrast, `show_dialog()` explicitly requires continuing to run the event pump in the current call stack; it enters the same connection queue in a verifiable window state.

The outer `on_click` does three things locally. First, synchronize to the service to obtain the value, then open the confirmation window, and finally submit the modification based on the returned result. If the reader receives confirmation-related events in the first step, the event remains in the queue. After obtaining the value, the outer layer enters `show_dialog()`, and then it can be processed by the inner layer. The core condition is that no ordinary synchronous waits borrows the event pump. This allows `process_message()` to dispatch directly, and a pure modal loop does not need to save the distribution depth, clear the delayed event list, or restore a pending input marker. The source window context used to place the new window is still managed according to the actual life cycle of each actual assignment.

`pump_message_list()` first records the end number value, selects the next item from the response and event queue, releases the connection lock after dequeuing it, and then executes user code. If the outer layer opens modal in the callback, the next item remains in the shared queue and can be taken by the inner layer. After the outer layer returns, it continues from the current queue head without executing the same item twice. When consuming from the reached queue, network responses and events are still merged according to their respective received numbers. Event callbacks may advance more work in the inner loop than the original deadline of the outer layer; here, the correctness is observed in the queue consumption, window lifetime, and business stack each completing their tasks.

`!state->flushing` protection must still be maintained. During rendering submission, the runtime may be traversing nodes, recording commands, updating difference baselines, or temporarily relying on a certain window and cache state. If the rendering callback opens modal, the inner loop can handle the closing of the current window and control changes, while the inner layer needs to draw its dialog box. `flush_window_list()` itself also avoids ongoing submission rounds. Forced re-entry may cause the outer layer to use objects that have already changed, and may also leave the inner window without a submitable image. Arranging modal calls in events driven by buttons or menus can clearly create and respond to stages. Rendering callbacks still focus on generating this round of commands.

## 10. Turning the boundary into a reproducible experiment

First open the main window, independent window, and confirmation window under the same session. During the confirmation window on the main window, try clicking on the independent window; the independent window should still be updated. Then, open the next layer from the confirmation window and close both layers in sequence, recording each callback entry and exit. This experiment verifies the direct owner relationship, nested calls of the UI thread, and the ability of window objects to continue being read. If the inner `on_closing` is deliberately canceled once, it can further verify the result restoration and continued interaction branches.

It is also possible to observe the session and window boundaries separately. Start two processes, giving each a window with the same name. Close one of the processes and check whether the other window still exists. Then, use the auxiliary keyboard to input and determine which one the current regular window and the actual laser hit surface belong to. Finally, let a regular event handler perform a short synchronous read and receive new events in the background, recording when the request returns and when the next pump cycle actually executes the event. This allows for separate verification of session recycling, input attribution, and synchronization waiting isolation.

The problem only occurs when two modal layers overlap. First, collect the owner, sub-window visibility, and `dialog_result`, then check if anyone cancels the close or calls during rendering. If multiple applications show the same lag, then look at the Engine and connection layers for common failures. If the visual has been updated but the focus is still on the old control, observe the input area being empty, current window notifications, and local focus. Do not infer the state based solely on the last frame. This boundary-by-boundary verification method also applies to [Chapter 05](./05_rendering_pipeline.md) submission and rendering debugging.
