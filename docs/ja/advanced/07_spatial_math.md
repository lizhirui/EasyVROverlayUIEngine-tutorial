# 空間変換とSteamVRの座標系

VRウィンドウを目盛りの付いた紙と捉えてください。アプリは紙上のボタン位置を知っており、SteamVRは紙が部屋内のどこにあるかを知っています。コントローラーは起点と方向を持つ光線を1本出力します。空間UIとは、まずこの3つの要素が同じ幾何学的言語で話せるようにすることです。紙を回転させたり、コントローラーに追従させたり、弧面に変形させたりしても、ボタンの位置は依然として紙上の目盛りによって定義されます。

本章は連続的な問題に沿って展開します。まずピクセルを空間に送り、次に逆算してレーザーがどのピクセルに落ちるか求め、最後に同じ座標変換を用いてウィンドウの移動、回転、拡大縮小、曲率調整を説明します。読み進める際は、紙、ペン、机の縁を座標軸とみなしてください。本文中では`X/Y/Z`で空間の3軸、`left/top`でウィンドウ上の論理ピクセル、`R`で回転または円柱面セクションにおける半径、`T`で回転と並行移動を含む姿勢を表します。

## 1.まず座標系を確立する

### 原点は測定開始点を、座標軸は測定方法を規定します

紙の左上隅を机面上の1点に固定し、右方向への目盛り増加を正、下方向への目盛り増加も正と規定します。紙上の`(120,80)`は2回の有向変位です。別の紙を使用する場合、紙上の`(120,80)`は同じレイアウトを記述できますが、机面上では別の位置に落ちます。紙の左上隅の位置を変更でき、紙の向きも回転できます。これは3次元変換における並行移動と回転です。

3次元座標系は紙より1軸多いです。2本の垂直な単位軸を取った後、第3軸には2つの逆方向の指向があります。右手系は`eX × eY = eZ`を規定します。右手の人差し指が`+X`、中指が`+Y`、親指が`+Z`の方向を示します。左手系は同じ最初の2軸を保つ場合、第3軸は逆方向になります。手性は3本の軸の相対的な約束です。物体が空間内で回転しても、その3本の軸は一緒に回転し、もともと右手系だった軸組は回転後も右手系のままです。1本の軸だけ反転させると手性が変わります。鏡を見ると左右が入れ替わるように見えるのは、鏡像を通常の回転としてクォータニオンに直接埋め込めない理由です。

SteamVRのトラッキングは右手系で表現されます。ヘッドセットの姿勢が単位回転の場合、`+X`は右向き、`+Y`は上向きです。右手の法則により、`+Z`は装着者側を向き、視線の前方は`−Z`で表されます。これは、ゼロ回転時にデバイスのローカル軸とトラッキング空間との整合約束です。頭を回した後、前方はヘッドセットの回転が`(0,0,−1)`に作用した結果です。例えば、右手の法則に従って`+Y`周りに`90°`回転させると、もともと`−Z`に沿った視線が`−X`に移動します。この単純な方向セットで実験を行うことは、「ヨー角が正のときどちらを向くか」を覚えるよりも確実です。ユーザーが左右への頭部の回転を異なる言語で呼ぶ可能性もあるためです。

もう1つよく混同される量は位置と方向です。位置`(0,1.6,−1)`は点が原点からどれだけ離れているかを説明します。方向`(0,0,−1)`はどの方向へ進むかを説明します。座標系全体を1メートル並行移動すると、点の位置座標は並行移動の影響を受けますが、方向の3成分は座標軸が回転した場合にのみ再計算が必要です。レーザーの起点は前者に属し、方向は後者に属します。交差を求めるコードは、これら2つの項目をそれぞれ変換します。

### 論理ピクセルとメートルの変換

ウィンドウの論理幅と高さを`w、h`、ピクセルスケーリング倍率を`s = physical_scale`とします。以下の3つの量を定義し、後のすべての数式でこれらを繰り返し使用します。

```text
m = s / LOGICAL_PIXELS_PER_METER = s / 1000
W = w · m
H = h · m
```

`m`の単位はメートル/論理ピクセル、`W`と`H`は物理的な幅と高さです。SDKは`render_style.h`で`LOGICAL_PIXELS_PER_METER`を定義し、`window::get_physical_width()`と`window::get_physical_height()`はこの数式に基づいて計算されます。Engineの`service_runtime::get_physical_width()`も同様に`1000`を基準とします。入力補助サーフェスには例外があり、Engineは現在所有ウィンドウがある場合、その所有ウィンドウの`physical_scale`を使用します。

`s = 1`の場合、1論理ピクセルは1ミリメートルに対応します。`640×360`ウィンドウの物理サイズは`0.64×0.36`メートルです。同じウィンドウ上で`s`を`1`から`1.5`に調整すると、物理サイズは`0.96×0.54`メートルになります。この操作はVR内のウィンドウ面のサイズを変更しますが、コントロールの矩形は依然として元の論理ピクセルを使用します。解像度を`640×360`から`960×540`に変更しても`s = 1`を維持する場合、物理サイズも`0.96×0.54`メートルになりますが、描画ターゲットとコントロールレイアウト座標は変わります。2つの結果の空間サイズは同じであっても、インタラクションとリソースコストは異なります。論理解像度を変更しつつ物理幅を維持したい場合は、新旧の論理幅の比率に基づいて`s`を逆方向に調整する必要があります。

左上隅を原点とする場合、平面上の1点のローカル空間座標は`(m·left, −m·top, 0)`です。負号は、紙上の`top`が下向きに増加するのに対し、VRの`+Y`は上向きであるという違いから来ています。ウィンドウ面の中心を原点とする場合、まずピクセル座標を中心基準にし、次にメートルに変換します。

```text
左上角原点 A 中的点  pA = (m·left, −m·top, 0)
从左上角到中心       cA = (W/2, −H/2, 0)
中心原点 C 中的点    pC = (m·(left − w/2), m·(h/2 − top), 0)
两种写法的关系       pA = cA + pC
```

ここで`w/2`は2つの境界の中間点を表し、幅が`640`の場合、`320`です。ウィンドウ面のヒット判定は連続座標を使用し、`left`は`120.25`であっても構いません。ピクセル位置はレイアウトとヒット判定に使用され、描画サンプリングがどの離散テクスチャピクセルに落ちるかはレンダリングが処理します。最初から落点を丸めると、一部の線やヒットエッジが閾値に近い場合にジッターが発生します。

`window.position`およびプロトコル内の`metadata.position`は、参照系における左上隅の姿勢の並行移動部分を記述します。Engineの`resolve_pose()`とSDKの`get_anchor()`はこの左上隅の姿勢を復元します。Engineの`get_center_pose()`とSDKの`get_world_pose()`はさらに中心オフセットを組み合わせます。公開されている`window::get_world_transform()`は`get_world_pose()`を呼び出し、世界空間の中心姿勢を取得します。`position`と`get_world_transform()`の並行移動部分を直接比較する際は、まず両者の参照系と原点が一致していることを確認してください。

例えば、単位参照系、ゼロ回転の下で、左上隅は`A = (0,1.6,−1)`、幅と高さは前例と同じです。中心は`C = (0.32,1.42,−1)`、`(left,top) = (120,80)`は中心基準で`(−0.20,0.10,0)`、加算して世界座標`(0.12,1.52,−1)`が得られます。`A`を誤って`C`としてしまうと、結果は半幅と半高だけ全体がオフセットされます。`top`の負号だけを忘れると、垂直方向がミラーリングされます。同じモデルでこれら2つのエラーをそれぞれ診断できます。

## 2.ベクトルを用いた射影、向きの判定、座標軸の構築

### 内積は1つの方向の成分を取り出します

ベクトルは方向を持つ矢印として読み取れます。`a = (3,4,0)`は、起点から右へ3歩、上へ4歩進むことを表せます。長さは`sqrt(3² + 4²) = 5`です。`vec3_t::get_length()`は3引数の`hypot(x,y,z)`で計算します。座標の差は2点間の移動ベクトルを与え、座標の和は「起点に移動ベクトルを加える」操作に使用できます。方向ベクトルに負数を掛けると向きが反転し、正数を掛けると長さのみが変化します。

内積`a·b = ax·bx + ay·by + az·bz`は、`|a|·|b|·cos(φ)`にも等しく、ここで`φ`は2つのゼロでないベクトルの間の角度です。`b`を単位ベクトル`b̂`に正規化した後、`a·b̂`は`a`がこの軸に沿った符号付き長さになります。`a = (3,4,0)`、`b̂ = (1,0,0)`の場合、射影長は`3`で、対応する射影ベクトルは`(3,0,0)`です。基準軸を`(−1,0,0)`に変更すると、長さは`−3`になりますが、射影ベクトルは依然として`(3,0,0)`です。符号は、指定された正方向に対する向きを表すために使用されます。

直交座標系では、既知の点と3本の直交する単位軸を用いて、同じ移動ベクトルを各軸それぞれと内積することで、3つの局所成分が得られます。平面の法線`n`とレイの方向`d`に対して、`d·n = 0`はレイが接平面に平行であることを意味し、ゼロに近づくほど非常に斜めに入射することを意味します。`d·n < 0`は、レイが正面法線の反対方向を向いており、法線が指す側から表面に向かって入射していることを示します。`d·n > 0`は背面からの入射です。SDKはこれらの量を`vec3_t::calculate_dot_product()`で計算します。後述する曲面の議論では、法線は横方向の位置に応じて変化するため、正面か背面かはヒット点における法線で判断します。

2つの単位ベクトルから実際の角度を計算するには、`acos(clamp(a·b,−1,1))`を使用できます。区間を制限するのは、丸め誤差により理論上の`1`が`1`よりわずかに大きい数値にならないようにするためです。「どちらがより前方を向いているか」の比較のみが必要な場合、内積を直接比較することで計算量を節約し、1回の比較を角度の逆三角関数計算に置き換えることを避けることができます。符号付きの回転角を表すには、軸の方向の規約が必要であり、後述する位相公式内の`atan2`を用いて軸周りの正負の方向を区別します。

### 外積は垂直な軸を与え、順序が正負を決定します

外積の出力はベクトルです。式は以下の通りです。

```text
a × b = (ay·bz − az·by, az·bx − ax·bz, ax·by − ay·bx)
|a × b| = |a|·|b|·sin(φ)
```

`a = (1,0,0)`と`b = (0,1,0)`を代入すると、`(0,0,1)`が得られます。両者を交換すると`(0,0,−1)`が得られます。SDKの`vec3_t::calculate_cross_product()`は同じ成分式を使用します。外積は同時に平行四辺形の面積と垂直方向を与えます。2つの入力ベクトルがほぼ平行な場合、面積はゼロに近づき、垂直方向の結果は非常に短くなります。このとき単位ベクトルに拡大すると、測定ノイズも同時に増幅されます。

一般的な構成として、必要な前方の単位ベクトル`f`と概ねの「上」`u`が既知であり、右手系の右、上、後方の軸を生成することを求めます。局所的な`−Z`が前方を向いているため、まず`z = −f`を取り、次に`x = normalize(u × z)`とし、最後に`y = z × x`とします。使用時には、まず`u`と`z`がほぼ平行でないことを確認します。安定した構築が必要な場合、退化に遭遇したら他の基準軸から方向差の大きい軸を選択するか、一時的に前フレームの方向を保持します。3本の有効な直交する単位軸が与えられた後、SDKの`quat_t::create_from_axis_basis(a,b,c)`はそれらを回転行列の3列として四元数に変換します。ソースコードはまず行列のトレース`a.x + b.y + c.z`を計算し、トレースが正の場合はスカラー成分から他の成分を求め、それ以外の場合は最大の対角成分を安定した入口点として選び、最後に正規化します。行列の行と列を逆にしてしまうと、局所から世界への回転を、その逆回転として誤って記述することになります。

厳密には、局所的な`X`軸のベクトルを世界座標で記述することは、行列の第1列であることに相当します。行列に`(1,0,0)`を掛けることでこの列が選択されます。`(2,3,0)`を掛けることは、第1列に沿って2倍、第2列に沿って3倍進むことに相当します。これは「回転行列の列が軸を表す」ことを検証する最も便利な方法です。

### 正規化はまず数値範囲を安定させます

通常、ベクトルをその長さで割ることを正規化と呼びます。`(1e300,1e300,0)`の長さを計算する際、直接二乗すると先にオーバーフローする可能性があります。非常に小さい値は、二乗時にアンダーフローしてゼロになる可能性があります。SDKの`vec3_t::get_normalized()`はまず有限値を確認し、次に最大成分の絶対値`M`を見つけます。`M`でスケーリングした後、各成分の絶対値は`[0,1]`以内になり、少なくとも1つの成分の絶対値は`1`になります。その後、スケーリング後の範囲内で`get_length()`を用いて長さを求め、最後に正規化します。この過程は計算経路を変更しますが、2回のスケーリングが正であるため、数学的な結果は保持されます。

例えば、`(30,40,0)`をまず`40`で割って`(0.75,1,0)`とし、長さ`1.25`を求めてからさらに割って`(0.6,0.8,0)`とします。ゼロベクトルや非有限成分に対して、SDKは`zero_direction`を報告します。四元数の正規化もまず最大成分でスケーリングしますが、エラーキーは`invalid_rotation`です。「方向が定義できない」場合、呼び出し側は測定または入力条件を解決する必要があり、適当な小数を加えると方向の跳躍を導入することになります。

`numeric_limits<double>::epsilon()`は、`1.0`に近づいたときの倍精度の解像度を記述します。ソースコードを見ると、判定の用途はそれぞれ異なります。`vec3_t::is_equal()`は成分の比較に`epsilon·max(1,|a|,|b|)`を使用します。SDKの平面交差計算は、方向の局所的な`z`をチェックするために`epsilon`を使用し、両手回転における最小の有効射影長には実際の物理的閾値である`0.02`メートルを使用します。これら3種類の閾値を1つの定数に混同すると、単位と実際の意味が失われます。数値精度の閾値は浮動小数点の境界を解決し、物理的閾値はデバイスノイズとジェスチャーの安定性を解決します。

## 3.姿勢は2つの座標系を接続します

### 点はまず回転し、その後平行移動します

`T_WA`は、座標系`A`内の数値をトラッキング空間`W`内の数値に変換することを表します。これには回転`R_WA`と移動`t_WA`が含まれます。点に対しては、まず局所基準軸を世界基準軸に置き換え、その後結果を局所原点の世界座標位置に平行移動します。

```text
P_W = R_WA · P_A + t_WA
D_W = R_WA · D_A
```

`pose_t::transform_point()`は実質的に`position + rotation.rotate(v)`を実行します。方向の変換には`rotation.rotate()`のみを使用します。例えば、`(1,0,0)`だけ平行移動した後、局所原点`(0,0,0)`は`(1,0,0)`に移動します。同じ軌跡の接線は依然として元の方向を向いています。方向に対して点の変換関数を呼び出すと、得られるレイはウィンドウがグローバル原点からの距離に応じて方向が変わり、ウィンドウを別の場所へ移動した後、ヒットが突然歪むように見えます。

本文の記号では、`T_WA · T_AB`はまず`B`から`A`へ、次に`A`から`W`への変換を表します。2つの式を展開すると、合成移動と合成回転が得られます。

```text
P_A = R_AB · P_B + t_AB
P_W = R_WA · (R_AB · P_B + t_AB) + t_WA
R_WB = R_WA · R_AB
t_WB = t_WA + R_WA · t_AB
```

これはまさに`pose_t::operator*()`の2項の実装です。小座標系の移動は、大座標系の局所方向に属するため、先に回転する必要があります。左手で紙を持っており、紙がハンドルの局所的な右側10センチメートルにあると想像してください。手を回転した後、この10センチメートルは依然としてハンドル自身の右側ですが、部屋の座標系では方向が変わります。2つの`position`を直接成分ごとに足し合わせると、この10センチメートルは部屋の正右側に固定されてしまいます。

### 世界から局所へ戻すには、完全な逆姿勢を使用する必要があります

`P_W = R·P_A+t`から`P_A = R⁻¹·(P_W−t)`を導出します。したがって、逆姿勢の回転は`R⁻¹`、並進は`−R⁻¹·t`です。SDKの`pose_t::get_inverse()`はまず四元数の逆を求め、次に`q.rotate(position * −1.0)`を計算します。ここでは、並進と回転はペアで逆転させる必要があります。座標軸に沿って一直線に配置された図形の場合、位置のみを減算すると偶然正しくなることがありますが、手や頭を回転させた後に問題が顕在化します。

完全なチェーンを手計算できます。参照系`A`の位置を`(1.00,1.50,−0.80)`とし、ワールドの`+Z`周りに`90°`回転させます。ウィンドウの左上隅は参照系内の`(0.20,0.10,−0.50)`にあり、参照系に対する回転はゼロです。ウィンドウの幅は`600`、高さは`400`で、`s = 1`です。

1. ワールド内の参照系`+X`が`+Y`に、参照系`+Y`が`−X`に変化します。したがって、ウィンドウのローカル並進を`Z`周りに回転させた後に`(−0.10,0.20,−0.50)`を加え、さらに参照系の原点を加算します。ワールド内のウィンドウの左上隅は`A_W = (0.90,1.70,−1.30)`になります。
2. ウィンドウ面の中心は、左上隅に対するローカル座標で`(0.30,−0.20,0)`です。ワールド増分に変換すると`(0.20,0.30,0)`となるため、中心は`C_W = (1.10,2.00,−1.30)`です。
3. ボタンの中心の論理座標`(150,100)`は、左上隅に対するローカル座標で`(0.15,−0.10,0)`、ウィンドウ面の中心に対する座標では`(−0.15,0.10,0)`です。最初の表記法を使用する場合、ワールド増分は`(0.10,0.15,0)`となり、ボタンのワールド点は`(1.00,1.85,−1.30)`です。2番目の表記法を使用する場合、ワールド増分は`(−0.10,−0.15,0)`となり、中心に加算すると同じ点になります。
4. 逆算する場合、ボタンのワールド点から`C_W`を引いて`(−0.10,−0.15,0)`を得ます。`90°`を逆転させると、ウィンドウ面中心系での`(−0.15,0.10,0)`が得られます。ピクセルに変換すると、`left = 300 − 150 = 150`、`top = 200 − 100 = 100`です。逆回転を忘れると、ワールドの`(−0.10,−0.15)`をそのままウィンドウの`x/y`として扱い、逆算して`(200,350)`になってしまいます。ヒットの誤差は回転に伴って変化するため、この性質を利用してこの種の実装エラーを特定できます。

フレームワークを使用して各ウィンドウのフォワードチェーンを表し、ウィンドウの左上隅の姿勢は`T_WA = T_WR · T_RA`です。`R`はここでは特定のウィンドウ参照系を表します。中心系から平面点を求めた場合、左上隅から中心への固定オフセット`T_AC`を乗算します。逆向きは`P_C = T_AC⁻¹ · T_RA⁻¹ · T_WR⁻¹ · P_W`です。ワールド点はこの式に従って順次変換できますが、ソースコードでは重複計算を避けるため、中心姿勢を直接合成して一度だけ逆を求めます。最後に、中心ローカル座標からピクセルへ変換します。トラッキング空間には5つの選択可能な参照系があり、各ウィンドウはこのチェーンの中間座標系としてそのうち1つを選択します。

### 参照系の切り替え、トラッキングの欠落とリセット

`world`はEngineの`world_origin`を使用し、その役割はアプリケーションが配置しやすいローカル座標でウィンドウを表すことです。有限なヘッドセット姿勢を初めて取得したとき、`initialize_world_origin()`は原点をヘッドセット位置に立位軸`(0,0,−1.2)`を加えた位置に置き、初期方向は単位回転です。ここではオフセットがトラッキング空間の`−Z`に沿っており、先にヘッドセットの回転を乗算していません。`head`はリアルタイムのヘッドセット姿勢を使用し、ローカル`−Z`はヘッドセットと一緒に回転します。`left`と`right`は対応するコントローラーのトラッキング姿勢を使用し、ヒット時にEngineの`is_eligible()`は反対側の手のレーザーに制限されます。デバイスがトラッキングを失った場合、参照はnullになり得ます。前回の変換を保持してクリックを続けると、宙に浮いたヒットが発生しやすいため、この経路ではまず利用不能な姿勢を処理する必要があります。

`body`はリアルタイムのヘッドセット位置と固定された参照方向に基づいています。`BODY_HEAD_TO_NECK_OFFSET = (0,−0.075,0.08)`はヘッドセットの原点を名目上の頸部ヒンジに向けます。このベクトルを現在のヘッドセット姿勢で回転させ、ヘッドセット位置に加算することで、推定される頸部位置を得ます。その後、固定された方向を使用して「頸部からヘッドセット」への逆オフセットを加算し、ウィンドウ配置用の参照点を得ます。式で表すと`p_body = p_head + R_head·d − R_body·d`であり、参照系の方向は`R_body`によって与えられます。頭を回転させたとき、2つの位置補償がヘッドセットの頸部周りの運動による並進を軽減します。補償には固定された人体近似を使用するため、デバッグ時には実際の歩行による位置変化と区別する必要があります。`reset_body_center()`はリセット時の完全なヘッドセット回転を記録します。

`Ctrl+Alt+Pause`の処理では`world_origin`もリセットできます。初期キャリブレーションで保存された`B = T_world_initial⁻¹ · T_head_initial`、リセット前に測定した現在のヘッドセット姿勢`H`とします。新しい参照系下で測定されるヘッドセットの関係が依然として`B`となるように、`T_world_new · B = H`を解くことで`T_world_new = H · B⁻¹`が得られます。`reset_world_origin()`に基づいて参照系を更新します。ここではOverlayの参照系が移動しており、アプリケーションウィンドウは自身のローカル姿勢関係を保持します。SteamVRの立位空間とゲームキャラクターのマップ座標は異なるシステムによって管理されており、ゲームのジョイスティックでキャラクターを移動しても、この物理トラッキング姿勢は自動的に変更されません。

`reparent(reference, keep_world=true)`は別の類似した方程式を解いています。まず、古いチェーンで計算されたウィンドウのワールド左上隅姿勢`T_old`を保存します。新しい参照系`T_new_ref`を選択した後、同じ位置と方向を維持するために、`T_new_local = T_new_ref⁻¹ · T_old`を設定すれば十分です。SDKは`ui_runtime::reparent()`内で`get_anchor()`、`get_reference()`および`change_transform()`を通じてこれを実装しています。`keep_world`が真であり、どちらかの端の参照系がトラッキングを失った場合、古い参照状態は保持され、インターフェースは`reference_not_tracked`を報告します。`keep_world`が偽の場合、ウィンドウはローカルパラメータを保持したまま参照系を切り替えます。これは、明示的に紙を新しいオブジェクトに貼り付けたいことを意味します。

デフォルトの中央配置は最初の配置に該当します。有効なソースウィンドウがない場合、視線の前方の初期距離は`max(1.2,W,H)`メートルとし、まず中心を求め、次に回転後の中心オフセットを減算して左上隅を書き戻します。有効なソースウィンドウがある場合、初期の中心と方向はソースウィンドウに基づき、目の位置に応じて新しいウィンドウを前方に移動させます。すでにほぼ平行で範囲が重複しているウィンドウも深度間隔チェックに参加します。`STARTUP_DEPTH_OFFSET`は`0.02`メートルであり、目に近づくとオフセット量も制限されます。静的な数学の例から実際の`center`位置を推定する際には、特に複数のウィンドウが連続して開かれる場合、このステップを忘れないでください。

## 4.オイラー角の順序とジャイロスコープロック

### 3つの角度には明確な順序を付ける必要があります

ペンを持ってまず水平に右向きに置きます。机の垂直軸周りに一度回転した後、ペンの先端の方向が変わります。次に机の縁周りに回転するとき、結果は最初のステップでペンをどこまで回転させたかによって決まります。2つの回転は一般には可交換ではありません。`eZ = (0,0,1)`を取り、まず`X`周りに`90°`回転させて`−eY`を得、次に`Y`周りに`90°`回転させても依然として`−eY`です。順序を逆にすると、最初のステップで`eX`が得られ、2番目のステップでも依然として`eX`です。この例を使用して実装内の「どの乗算が先か」を確認することで、言語における「順次乗算」による曖昧さを回避できます。

SDKの`quat_t::create_from_euler(v)`は度を入力として受け取り、`v.x/v.y/v.z`をそれぞれ`X/Y/Z`周りの角として使用します。`qZ·qY·qX`を構築して返します。ベクトルが式の右側から入る場合、まず固定の`X`周り、次に固定の`Y`周り、最後に固定の`Z`周りに回転します。これは、組まれた局所中間軸を用いて同じ回転行列を説明する場合と等価ですが、2つの表現の読み順は異なります。航空用語を誤って公式として解釈しないよう、以下では`α/β/γ`で`X/Y/Z`の角を直接表します。どの軸をピッチ、ヨー、ロールと呼ぶとしても、順序と軸方向が一致している場合のみ、数値に意味があります。プロトコルの`metadata.rotation`はこの3軸の度数値で伝送され、`tracking`と`pointer.rotation`は`[x,y,z,w]`の四元数成分を伝送します。

列ベクトル規約で`R = Rz(γ)·Ry(β)·Rx(α)`を書き出します。最も単純な`Y`周りの行列と比較できます。その第1列は`(cos β,0,−sin β)`、第3列は`(sin β,0,cos β)`です。これは、回転後に局所`X`軸と`Z`軸がそれぞれどこを指すかを示しています。続けて`Rz`を掛け合わせ、第1列を確認すると、`(cos γ·cos β, sin γ·cos β, −sin β)`が得られます。中間角が`90°`の場合、第1列は`(0,0,−1)`に退化し、`γ`の変化に全く依存しなくなります。第3列と第2列は依然として`α`と`γ`に依存しますが、両者の差にのみ依存します。

### 2つの制御軸が特異姿勢下で同じ方向を表す

紙の上に3つの回転可能な鉄の輪を描き、最初の輪を2番目の輪の中に通し、さらに3番目の輪に通します。外側の輪を動かすと、内側の2つの輪も一緒に引きずられます。直立状態では、各回の操作で異なる方向を変えることができます。中間の輪が直角回転した後、最も内側の軸の一つが最も外側の輪の軸と一致します。この2つのノブを動かすと、実際には同じ空間軸上で角度を重ねたり相殺したりしています。

以下の式は行列を用いて正確な状況を示します。まず`Ry(90°)·Rx(α)`を掛け合わせ、次に`Rz(γ)`を掛けます。`δ = α−γ`とすると、結果は

```text
R(α, 90°, γ) =
[  0      sin δ    cos δ ]
[  0      cos δ   −sin δ ]
[ −1        0        0   ]
```

差`δ`が不変である限り、2つの角に同時に同じ値を加えても同じ姿勢が得られます。`(0,90,0)`と`(90,90,90)`はその一例です。また、瞬間回転軸を見ることもできます。最終姿勢から見て、最も右側の`α`を変更すると`Rz·Ry·eX`周りの増分が生じ、最も左側の`γ`を変更すると常に固定の`eZ`周りの増分が生じます。`β = 90°`の場合、前者は`−eZ`、後者は`+eZ`です。パラメータの変化方向は逆ですが、空間上の直線は同じです。3つの制御ノブの瞬間的な作用は2つの独立した方向にのみ残ります。これが自由度の退化です。`β = −90°`の場合、別の結合に対応し、姿勢は`α+γ`にのみ依存します。

![欧ラ角の軸の一致と単位四元数の軸角表示](/images/ja/advanced_gimbal_lock_quaternion.png)

この事実は、混同されやすい2つの問題を説明しています。第一に、`(0,89,0)`と`(0,90,0)`は当然、同じ`Y`軸周りの`1°`だけ異なります。第二に、`(90,89,90)`と`(0,89,0)`は特異点付近で効果が近似しますが、`89°`では依然として差異があります。第1列に代入すれば、前者の水平成分が`Y`、後者の水平成分が`X`であることがわかります。これは、`90°`に近い場合、両者の水平成分が共に小さくなるためです。共通して`cos β`を掛けているためです。これは数値的に不安定になりやすい領域でもあります。非常に小さな測定誤差が、オイラー角の2つのパラメータに大きな変化を要求し、それらの変化が互いに相殺しても、物体の方向自体は依然として安定しています。

ジャイロロック（万向節ロック）は、この組の角がその点付近での独立した制御と読み取りに影響します。剛体は依然として任意の軸周りに回転できます。「1つの自由度を失う」ということにも実際の影響があります。例えば、アニメーションシステムが成分ごとの加算でカメラを制御する場合、特異姿勢下では、本来`α`と`γ`にそれぞれ割り当てられた2つの入力が同じ軸での操作になります。角度を逆算して軸ごとの補間を続ける場合、不要な大きな弧を描く可能性があります。3軸操作インターフェースは多くのソフトウェアで世界軸に沿って直接増分回転できるため、ユーザーがドラッグしてもこのパラメータの特異性を必ずしも感じません。内部表現を判断するには、変化をどのように組み合わせ、姿勢から角度をどのように逆算するかを観察します。

## 5.四元数は1つの軸と1つの角から始まる

### 軸角表示で半角を使用する理由

単位ベクトル`û`を回転軸とし、`θ`を右手系の回転角とします。数学の教科書では、四元数を`(w, v)`のように、スカラーが先、ベクトルが後になるように書くことが多いです。本記事では以下でこの数学的記号を用いて導出します。SDKの実際の構造体のフィールド順序は`quat_t{x,y,z,w}`で、ベクトル成分が先です。`û`周りに`θ`回転する単位四元数を構築する際、SDKは`{ux·sin(θ/2), uy·sin(θ/2), uz·sin(θ/2), cos(θ/2)}`を保存する必要があります。単位回転は`{0,0,0,1}`です。スカラーが先の教科書の公式を使用する場合、コードの初期化部分で実際のフィールド順序に戻すことを忘れないでください。

四元数の乗算は内積と外積に分解できます。`a=(s,u)`、`b=(t,v)`とすると、

```text
a · b = (s·t − u·v, s·v + t·u + u×v)
```

左側の点は四元数の乗算を表し、第1成分の`u·v`はベクトルの内積です。`quat_t::operator*()`の第1項と最終項を用いてフィールド順序を検証できます。`u×v`にゼロでない成分がある限り、2つの操作数を交換すると結果が変わります。これは実際の回転が可換でないという事実と一致します。通常のベクトル`p`を純粋な四元数`(0,p)`に代入した後、初めて四元数の乗算がベクトルの回転と結びつきます。片側からのみ掛け合わせるとスカラー成分が生じ、問題の意味も変わります。`q·(0,p)·q⁻¹`を用いて両側から作用させると、結果のスカラーは再びゼロになります。

`q = (c, û·s)`とします。ここで`c = cos a`、`s = sin a`です。軸が単位ベクトルであるため、`c²+s²=1`となり、逆四元数は`(c,−û·s)`です。上記の積の式を用いて2回の乗算を展開すると、ベクトル部分は

```text
(c²−s²)·p + 2cs·(û×p) + 2s²·û·(û·p)
```

次に`p`を軸に平行な`p∥ = û·(û·p)`と軸に垂直な`p⊥ = p−p∥`に分解します。軸方向の項の係数は`c²−s²+2s² = 1`になります。垂直方向の2つの項は`(c²−s²)·p⊥ + 2cs·(û×p⊥)`です。後者の2つのベクトルは等しく垂直であり、三角関数の公式`c²−s² = cos(2a)`、`2cs = sin(2a)`により、まさに`p⊥`を平面上で`2a`回転させます。ベクトルを`θ`回転させたい場合、四元数には`a=θ/2`を使用する必要があります。これが半角の由来です。これは両側からの乗算が方向に作用する結果から来ています。

`û = eZ`、`θ = 90°`、`p = eX`を代入します。半角は`45°`で、`c = s = √2/2`、軸方向の射影はゼロです。式の第1項は消去され、第2項の係数は`1`で、残りは`eZ×eX = eY`です。したがって、コード`quat_t::get_axis({0,0,1},90).rotate({1,0,0})`は`(0,1,0)`に近い結果を返すはずです。`get_axis()`はまず角度が有限であり、軸が正規化可能であることを確認し、次に`720°`で入力を剰余計算し`π/360`を掛けます。このステップで同時に度からラジアンへの換算と半角化が行われます。同じ軸周りに`360°`回転すると、`−q`に対応する同じ空間回転が得られます。表現値は`720°`回転して初めて元の四元数の符号に戻ります。

### なぜ組み合わせ可能か、なぜ共役で逆数を求めるか

任意の四元数に対して共役を求めると、ベクトル部分の符号が反転します。`q·q* = |q|²`は純粋なスカラーです。厳密な代数逆は`q*/|q|²`です。SDKは回転に使用される場合、まず正規化してから共役を求め、実際に返されるのが単位回転の逆であることを保証します。`quat_t::rotate()`もまず入力回転を正規化し、次に`{v.x,v.y,v.z,0}`を構築して、`(q·p)·q⁻¹`を実行し、結果の`x/y/z`を取得します。四元数のフィールドは浮動小数点計算により単位長からわずかに逸脱する可能性があるため、これらの正規化ステップには意味があります。

まず`a`でベクトルに変換し、次に`b`で変換して、`b·(a·p·a⁻¹)·b⁻¹`に展開します。結合則に従って並べ替えると`(b·a)·p·(b·a)⁻¹`が得られます。したがって、四元数の積は確かに連続的な回転を表しており、右側の項が先に作用します。四元数の回転合成は単位ノルムを保持しますが、実際にはソースコードと同様に定期的に正規化して誤差の蓄積を制御します。回転の4成分は単位長の制約を受け、実際には自由度は3つだけです。完全な4つの値が姿勢を決定しますが、`q`と`−q`は同じ姿勢を表します。単一の成分だけを見ると、軸方向と半角の両方の影響を受けるため、その軸のオイラー角として直接読み取れません。

### SLERPとSDKの現在の補間実装

理論上の球面線形補間は、まず2つの単位四元数を4次元単位球上の2点とみなします。内積が負の場合、終点を反転させることで、同じ空間姿勢を表す終点をより短い弧側に来るようにします。その後、`Ω = acos(a·b)`を設定します。`0<t<1`かつ`sin Ω`が安定して評価できる場合、厳密なSLERPは以下の式を使用します。

```text
q(t) = sin((1−t)·Ω)/sin Ω · a + sin(t·Ω)/sin Ω · b
```

分母は平面内の2つの端点ベクトルの射影関係から来ています。終点を`b = cos Ω·a + sin Ω·n`と書くことができ、ここで`n`は`a`に直交する単位ベクトルです。弧に沿って比率`t`の点まで進むと`cos(t·Ω)·a + sin(t·Ω)·n`になります。`n`を消去すると上記の式が得られます。2つの角が非常に近い場合、`sin Ω`は非常に小さくなり、計算重みが誤差を増幅させるため、多くの実装はこの範囲で線形近似を使用してから正規化します。

本プロジェクトの`quat_t::blend()`は、まず内積の判定と符号反転を行い、次に成分ごとに`a+(b−a)·t`を計算し、最後に正規化します。Pythonのパブリックメソッド`quat.slerp()`はこの動作にバインドされています。これは正規化線形補間であり、NLERPと表記されることが多いです。単位端点と区間`[0,1]`に対して、方向は同じ短い弧に沿って変化しますが、時間比率と球面弧長比率には差異があります。固定軸で`0°`から`120°`へ回転する例では、厳密なSLERPは`t=0.25`で`30°`を与えます。このときNLERPの未正規化スカラー成分と軸方向成分はそれぞれ`0.875`と約`0.2165`であり、両者の比は保たれ、逆算した回転角は約`27.8°`です。両端の姿勢は同じですが、中間の速度は異なります。アプリケーションが一定の角速度を要求する場合、厳密なSLERP式を使用し、近接点の分岐を保持します。SDKの両手コントローラーの回転は、位相変化に基づいて直接軸角四元数を構築するため、このインタラクションチェーンは補間速度に依存しません。

## 6.ソースコードからオイラー角と四元数の相互変換を導出する

正向関数`create_from_euler()`には単一の乗法式しかなく、演算順序はすでに規定されています。逆関数を読み解くために、`a = α/2`、`b = β/2`、`c = γ/2`を設定し、`sx/cx`で`sin a/cos a`を表し、`sy/cy`と`sz/cz`も同様にします。まず軸が1本だけの3つの四元数を書き、`qZ·qY·qX`に従って展開すると、

```text
x = sx·cy·cz − cx·sy·sz
y = cx·sy·cz + sx·cy·sz
z = cx·cy·sz − sx·sy·cz
w = cx·cy·cz + sx·sy·sz
```

逆解の鍵は成分の組み合わせです。展開済みの式を`cy+sy`と`cy−sy`で共通因数を抽出し、次に2角和差公式を適用します。

```text
(w+y, x−z) = (cy+sy) · (cos(a−c), sin(a−c))
(w−y, x+z) = (cy−sy) · (cos(a+c), sin(a+c))
```

`quat_t::get_euler_angle_vector()`の最初のステップは`get_normalized()`です。次に上記の2組の長さ`difference = hypot(w+y,x−z)`と`sum = hypot(w−y,x+z)`を計算します。規範分岐`β∈[−90°,90°]`では、`b`は`[−45°,45°]`にあります。したがって、`cy+sy`と`cy−sy`はどちらも非負であり、長さはこれら2つの係数です。さらに和角式を用いて、

```text
difference = √2 · sin(b+π/4)
sum        = √2 · cos(b+π/4)
b+π/4      = atan2(difference,sum)
β          = 2·atan2(difference,sum) − π/2
```

これがソースコード`ry`の計算式です。残りの2つの角については、ソースコードは`first = atan2(x−z,w+y)`と`second = atan2(x+z,w−y)`を計算します。前者は`a−c`を復元し、後者は`a+c`を復元するため、`rx = first+second`、`rz = second−first`です。コードは`remainder(角度,2π)`を用いて主値付近に正規化し、ラジアンを度に変換します。入力`β`が規範分岐の外にある場合、同じ姿勢は別の3要素組で表現できます。逆解はその分岐上の表現を与えます。アプリケーションが往復比較を行う場合、回転後の軸または姿勢自体を比較すべきです。

また、2つの特異点分岐を説明する必要があります。`β=90°`の場合、`cy−sy=0`となり、2組目の長さ`sum`はゼロになり、`first`のみが定義されます。コードは`second=first`と設定し、したがって`rz=0`となり、元の`α−γ`を`rx`に統合します。`β=−90°`の場合、1組目の長さ`difference`はゼロになり、コードは`first=second`と設定し、したがって依然として`rz=0`を選択し、`α+γ`を`rx`に統合します。実装は`epsilon`を用いてゼロに近い長さを判定します。これは特異姿勢下で再現可能な代表値を選択することです。連続的な軌跡に対して、この代表値は境界を通過した後、別の角度組にジャンプする可能性があるため、レンダリング、トラッキング、連続インタラクションでは、まず回転表現上で計算し、角度は設定と表示に適しています。

公式の検証には3組の手計算を行うことができます。単軸`(0,30°,0)`は`q = {0,sin 15°,0,cos 15°}`に対応します。2組の正弦成分はどちらもゼロであるため、`rx=rz=0`となり、`30°`のみが逆算されます。2組目`(20°,90°,10°)`は`rx≈10°、ry≈90°、rz=0°`を与えます。3組目は`(20°,−90°,10°)`を取り、代表値は`(30°,−90°,0°)`です。2つの姿勢で同じ3つの単位基底軸を回転させることで、それらが等価であることを検証できます。特異点に近い場合、表示された単一の角度を比較するよりも、局所的な前方と上方のベクトルが同じ方向かどうかを確認する方が適切です。

## 7.円柱面はフラットなウィンドウからどのように曲げられるか

### 弧長スケールと同一の中心接平面を保持する

フラットなウィンドウの中心を`(0,0,0)`に置き、曲げられていない状態では表面は`z=0`にあります。物理的な幅方向の弧長`u`と垂直メートル座標`v`でスケールを付けます。正の曲率`κ`の単位は毎メートルとし、半径は`R=1/κ`です。水平断面の中心は`(0,R)`にあります。弧角を`φ = κ·u`と定義すると、中心局所点は

```text
u = (left / w − 1/2)·W
v = (h/2 − top)·(W/w)
x = R·sin φ
y = v
z = R·(1 − cos φ)
```

`u=0`時`x=z=0`では、中心点およびその接平面はフラットウィンドウと同一です。左右両端の`|u|`が大きくなるにつれて、`z`が増加し、ウィンドウの縁が中心正面側へ湾曲します。曲線方程式を検証すると、`x²+(z−R)²=R²`となります。弧長は円周の角度から換算され、`u = R·φ`です。ウィンドウ全体が占める角範囲は`Θ=κW`で、左右の辺はそれぞれ`−Θ/2`と`+Θ/2`にあります。`Θ`が1回転分に達すると、両辺が重なり、同一の空間位置が異なる横方向論理スケールに対応することになります。`window::set_curvature()`、物理サイズ設定、およびEngineの`present()`は、`κ≥0`かつ`κW<2π`であることを要求します。コントロールハンドルは、`160°`未満の総角範囲のみを許可し、この制限はSDKの`get_maximum_handle_curvature()`に由来します。この関数は`nextafter`を用いてゼロ方向へ丸めます。プログラムプロパティの合法領域とインタラクティブコントロールハンドルの上限には、それぞれ異なる用途があります。

`service_runtime::get_surface_local_point()`が`κ=0`の場合、直接`(u,v,0)`を返します。湾曲時には`z`を`2·sin²(φ/2)/κ`として記述します。恒等式`1−cos φ = 2·sin²(φ/2)`を用いると、両者が等価であることがわかります。角度が非常に小さい場合、`cos φ`は`1`に非常に近くなり、直接減算を行うと多くの有効桁が失われます。半角公式はこの打ち消しを軽減します。エンジニアリング上では、微分によって曲面のスケールが歪んでいないか確認することもできます。`v`を固定し、`u`に沿って微分すると`(cos φ,0,sin φ)`が得られ、長さは常に`1`です。したがって、横方向のピクセル間も依然として弧長に基づいて均等に分布しています。正面法線は`n=(-sin φ,0,cos φ)`と記述でき、中心では`+Z`に戻ります。幾何学的には、これは水平接線および垂直方向の両方に垂直な単位軸です。

## 8. レーザーのワールド座標点をウィンドウピクセルに逆算する

### まず射線に変換し、次に平面を解く

射線は始点`o`と方向`d`で定義され、線上の点は`p(t)=o+t·d`です。`d`が正規化されている場合、`t`はメートル単位です。`t≥0`は、始点からレーザー発射方向へ向かう側のみを考慮します。中心姿勢の逆変換を始点に適用し、逆姿勢の回転のみを方向に適用します。これにより、ウィンドウ面中心座標系における射線は`o′+t·d′`と記述できます。フラットウィンドウ上の`z=0`から`o′z+t·d′z=0`が得られ、したがって`t=−o′z/d′z`です。`d′z`がゼロの場合、射線は平面に平行です。両項が同時にゼロの場合、無限個の共面点が存在します。プログラムでは通常、利用可能な一意のヒットがないとして処理し、キャプチャされたターゲットを保持するかどうかは後続のポインタ状態によって決定されます。

SDKの`ui_runtime::intersect_plane()`は、押下後のコントロール追跡に使用され、`abs(ray.z) ≤ epsilon`を用いて近似平行を判定し、`t<0`を拒否します。返される3値は`{t,local_x,local_y}`の順に並べられます。この戻り値は`vec3_t`によって運ばれますが、`x`フィールドの意味は距離パラメータであり、`y/z`フィールドがそれぞれ平面の横縦座標です。Engineの`service_runtime::intersect()`はウィンドウ選択に使用され、平面ブランチでは`local_direction.z == 0`で平行を拒否し、候補選別段階では`t≤0`および非有限値も拒否します。両方の関数は同じ基礎直線方程式を使用していますが、それぞれの許容域と出力契約は呼び出し目的によって決定されます。

例えば、中心座標系における射線の始点`(0.12,0.06,0.50)`、方向`(0,0,−1)`。`t=0.50`メートルを求め、`(0.12,0.06,0)`にヒットします。幅と高さが`640×360`かつ`s=1`の場合、逆算すると`left=320+120=440`、`top=180−60=120`となります。`top`を確認すると、ヒット点の`y`が正であることは中心より上にあることを示し、ピクセル行番号は`180`より小さくなければなりません。この直感的な検証は、座標代数をもう一度やり直すよりも容易です。

### 円柱面方程式の展開と安定した根の求解

円柱面は`x²+(z−R)²=R²`から`κ(x²+z²)−2z=0`に展開でき、ここでは両辺に共通する`R²`を約分し、等式に`κ`を乗算しています。射線の`x=ox+t·dx`、`z=oz+t·dz`を代入し、`at²+bt+c=0`にまとめます。

```text
a = κ·(dx²+dz²)
b = 2·[κ·(ox·dx+oz·dz)−dz]
c = κ·(ox²+oz²)−2oz
Δ = b²−4ac
```

ここではプライム記号を省略し、すべての量はすでにウィンドウ面中心座標系内にあります。方向が円柱軸`Y`に沿う場合のみ、一意の横断面交点が存在せず、`a=0`は拒否されます。`Δ<0`は、射線の横断面が円と交わらないことを示します。`Δ=0`は接線を意味し、円と接する場合、1つの重根しかありません。`Δ>0`では2つの候補が得られ、前後の根については弧長と高さでさらに選別する必要があります。

一般的な直接根求解式`(−b±sqrt Δ)/(2a)`には、2つの大きな値が近接する際に減算される項があり、小さい方の根は精度を急速に失う可能性があります。Engineはまず`q=−0.5·(b+copysign(sqrt Δ,b))`を計算し、同符号の項を加算することで打ち消しを回避します。次に、2つの根を`q/a`と`c/q`とします。2つの根の積`c/a`から第2項を検証できます。`q=0`の場合、`−b/(2a)`を用いて重根を得ます。コードでは、無次元角範囲`κW`と`epsilon`を比較し、湾曲が非常に小さい場合は平面候補として計算し、実際の曲率成分に基づいて横座標の逆算式を決定します。このアプローチにより、極小の曲率下で非常に遠い第2の円柱交点を強制的に求解することを回避できます。

各候補点について、`κx=sin φ`および`1−κz=cos φ`を用いて弧角を逆算します。`atan2`は2つの成分を同時に考慮し、左右の半円と同一の正弦値を持つもう一方の枝を区別できます。`u = atan2(κx,1−κz)/κ`とすると、消費される論理ピクセル数は

```text
left = (u/W + 1/2)·w
top  = h/2 − (y/W)·w
```

通常、`0≤left≤w`かつ`0≤top≤h`が要求されます。これは、円柱をウィンドウが占める角区間と垂直高さに制限することと等価です。ソースコードでは、正かつ有限の距離および有限のピクセルのみを保持し、距離が最小の有効な根を選択します。二次方程式を解いた後、最小の根のみを確認しないでください。小さい方の根はウィンドウの弧区間外に位置する可能性があり、もう一方がユーザーが見る有限の曲面である場合があります。

### 段階的に検証できる円弧面の例

幅`W=1`メートル、`κ=1`/メートル、`w=1000`とし、`h=400`とします。ウィンドウの左右境界の弧角は`−0.5`および`+0.5`ラジアンです。ターゲットピクセル`left=750`、`top=200`は`u=0.25`メートル、`v=0`に対応し、弧角は`0.25`ラジアンです。これを正向モデルに代入すると、`x=sin(0.25)≈0.2474`、`z=1−cos(0.25)≈0.03109`が得られます。レーザーを`(sin 0.25,0,0.5)`に配置し、方向を`(0,0,−1)`とします。この固定`x`における2つの交点を求めると、`z`はそれぞれ約`0.03109`および`1.96891`です。後者は射線の始点よりも大きく、負の`t`に属します。前者は`t≈0.46891`メートルが得られます。`atan2`を用いて逆算すると、元の`0.25`ラジアンが得られ、さらに`750`および`200`が得られます。粗く`x=0.2474`メートルで換算すると、`747.4`程度と誤算され、ウィンドウの湾曲が大きいほど、弦の位置を弧長に置き換えることによる誤差は大きくなります。

同じ点の正面法線は`(−sin 0.25,0,cos 0.25)`であり、ここで`(0,0,−1)`との内積が負になることから、正面入射であることがわかります。Engineの交差計算では、正面と背面の両方にヒット可能性があります。同じ曲面点に対して、ピクセル変換式は完全に同一です。背面から見える逆転した画像は、背面Overlayの幾何学とテクスチャ方向に由来します。SDKは空間キャプチャ開始時に、ヒット点で法線とレイの内積を計算し、`capture.backside`を保存します。曲率調整時に、これを用いてドラッグの横方向作用方向を反転させることができます。正面・背面の選択と、最近の有効ルートの選択は異なる2つの事柄です。

ウィンドウがキャプチャ中の場合、Engineはまず通常の有限面のヒットを計算し、次に`outside`モードで面外の連続座標を取得することを許可します。現時点で新しい交点がないが、ターゲットに有効な姿勢がある場合は、キャプチャ状態を継続できます。キャプチャがない場合、Engineは可視かつインタラクティブな表面間で最も近いヒットを探し、別途`BEAM_MARGIN_LOGICAL_PIXEL`で定義されたエッジ範囲をレーザー表示候補として許可します。これにより、エッジ付近でもビームが見えるようになり、インタラクションヒットは依然としてウィンドウ境界をチェックします。コントロールのヒットはSDK内で発生し、受信した`left/top`とコントロールの幾何学を用いて選択を行います。カーソルのずれをデバッグする際は、順に空間レイがウィンドウ面に到達しているか、計算されたウィンドウ面のピクセルが正しいか、UIがどのコントロールにヒットしたかをチェックしてください。

## 9. ウィンドウインタラクションにおけるこれらの幾何量の利用方法

### 片手移動で保存されるのは相対姿勢です

グリップキーを押してウィンドウを掴むと、SDKはコントローラーの原点と回転から手の姿勢`H₀`を構成し、ウィンドウのワールド座標系における左上角の姿勢`A₀`を読み取ります。`rebase_window_grab()`は相対関係`G=H₀⁻¹·A₀`を保存します。その後、手が`H₁`に移動すると、`update_window_grab()`によりウィンドウの新しいワールド姿勢`A₁=H₁·G`が求められます。更新対象のウィンドウプロパティは現在の参照系`R`で記述されており、最終的に`R⁻¹·A₁`に書き込まれます。これらの3つの乗算はそれぞれ、「掴んだときに紙が手のどこにあるか」「現在その紙が部屋のどこにあるか」「結果をウィンドウ自身の座標系に戻す」という問いに答えています。

相対姿勢全体を保存することで、並進と回転を同時に駆動できます。2本の指で紙の1点を挟み、手首を回転させた場合を想像してください。紙の他の位置は円弧に沿って移動します。距離が遠いほど、同じ角度変化がより大きな横方向の位移に対応します。これは、元のコントローラーとターゲット間の相対関係を保つことによる幾何学的結果です。相対関係はキャプチャ開始時に確立され、以降は常に同じ`G`を使用されるため、前回の丸め誤差が次の変換に累積することはありません。

### 8つのコントロールポイントによる両手回転軸の制限

ウィンドウの周囲には8つのコントロールポイントがあり、上、右上、右、右下、下、左下、左、左上の順に番号付けされ、その方向配列は`ROTATION_HANDLE_DIRECTION_LIST`です。異なるコントロールポイントは、必ず両手で同時に同じウィンドウを掴む必要があります。対向する点を掴む場合、`window::get_rotation_axis()`はまず「最初の点から2番目の点へ向かう」ウィンドウ平面方向を正規化し、次に`+Z×その方向`を用いてウィンドウ面内の回転軸を取得します。したがって、上と下を掴むと軸は`X`方向に、左と右を掴むと軸は`Y`方向に、対角線を掴むと軸はその対角線に垂直な面内の斜め軸になります。どちらの手が先にどの点を占めるかを交換すると、軸の符号が変わります。掴んだ2つの点が対向しない場合、ソースコードは`+Z`を返し、ウィンドウ法線周りの回転に使用されます。ポイントペアを選択することで、ユーザーは限られた軸上で精密な調整を行うことができます。

各手は、掴み開始時にヒット距離を保存します。`update_window_rotation()`は`コントローラーの原点+現在の方向×キャプチャ距離`を用いて2つの仮想グリップポイントを計算し、その差`span=P_right−P_left`を取得します。この差は、まず掴み開始時のウィンドウ面局所軸系に変換されます。`Z`軸の回転に対しては、`span.x、span.y`に対して`atan2`を行います。面内軸`a=(ax,ay,0)`に対しては、横方向が`span·(ay,−ax,0)`、縦方向が`−span.z`です。これら2項は、回転軸に垂直な2つの直交方向におけるベクトルの成分です。`calculate_window_rotation_phase()`により平面内の位相が求められます。射影長が`ROTATION_HANDLE_MINIMUM_SEPARATION=0.02`メートル未満の場合、位相の読み取りは信頼できないため、一旦停止します。有効な位相を再取得した時点で新しい基準を確立し、無効期間中の跳躍を一度にウィンドウに加えません。

位相は`π`で符号が反転します。例えば、前フレームが`179°`で、次のフレームが`−179°`と記録された場合、実際の増分は`2°`であるべきです。ソースコードはまず2フレームの位相差に対して`remainder(差,2π)`を取り、その後累積します。次に、累積角と固定局所軸から増分クォータニオンを構築し、初期ウィンドウ回転に右乗算します。回転中心は開始時に保存され、更新時に左上角`A=center−R_new·(W/2,−H/2,0)`が再計算されます。したがって、ウィンドウ面は中心周りに回転し、左上角は角度に応じて適切に移動します。常に左上角周りに回転すると、プレイヤーは大きなウィンドウが手中で振り回されているように感じます。位相法には有効な2点間の接続が必要ですが、毎フレーム両手が曲面のどの側面に切り替わったかを推測する必要はありません。

### サイズと曲率のコントロールハンドルは同じキャプチャアプローチを使用します

右下隅のスケーリングハンドルと左下隅の曲率ハンドルはトリガーキャプチャを使用します。SDKは最初のヒットの距離と位置を保持し、現在のレーザーを同じ距離上の点と初期点から減算して、ウィンドウ局所`(Δx,Δy,Δz)`を取得します。これにより、ハンドルのドラッグ時に安定した相対位移を追跡し、毎フレーム変化する曲面交点による跳躍を回避します。Engineは`lock_position`付きの`pointer_capture`リクエストを受信すると、ビームの視覚的端点をキャプチャ点に従わせることができます。ドラッグ終了、ターゲットのインタラクション資格喪失、またはキャプチャキャンセル時、SDKは対応するジェスチャを終了します。

スケーリングはアスペクト比`r=h/w`を維持する必要があります。幅が`dW`変更された場合、右下隅の理想位移は`(dW,−r·dW)`です。実際の局所位移を`(1,−r)`に射影し、`(Δx−dW)²+(Δy+r·dW)²`を最小化し、`dW`に対して1回微分すると得られるのは

```text
dW = (Δx − r·Δy) / (1 + r²)
```

これが`update_pointer()`中の`width_delta`です。例えば`r=0.5`で、`(0.10,−0.05)`メートルドラッグした場合、分子は`0.125`、分母は`1.25`であり、したがって幅は`0.10`メートル増加します。水平方向にのみ`0.10`メートルドラッグした場合も、同じ式により`0.08`メートルが得られます。これは、システムが固定比率方向に沿ってジェスチャを吸収するためです。`set_window_physical_width()`は次に`s=1000·W/w`を用いて物理的スケーリングを書き戻し、インタラクション最小幅により少なくとも`0.1`メートルに制限し、拡大時に必要に応じて曲率を調整して、弧角がコントロールハンドルの範囲内に留まることを保証します。

曲率ハンドルで横方向の局所変位を使用し、`κ_next=clamp(κ_initial ± 4·Δx,0,κ_max)`を計算します。正背面では符号が逆になります。`CURVATURE_DRAG_SENSITIVITY`は`4.0`です。コントロールハンドルはジョイスティックも受け入れます。曲率はジョイスティックの`X`を読み取り、総弧角に変化を与えます。最大速度では1秒あたり最大`2`ラジアンになるため、曲率の増分は現在の物理幅で割る必要があります。サイズはジョイスティックの`Y`を読み取り、`W_next=W_current·2.25^a`を使用します。ここで`a`は正規化されたジョイスティック速度と時間の積です。対数幅の累積は逐次的な比例乗算に相当し、最大速度で1秒間上方向に維持した場合、境界に達していない状態で`2.25`倍になります。下方向でも同じ時間続ければ逆数を掛けます。1秒あたり固定の零点数メートルを加える場合と比べて、小さなウィンドウと大きなウィンドウの相対的な変化速度がより近づきます。ジョイスティックは`128`を中性点とし、コードではまずデッドゾーンを差し引いた後、両側それぞれの有効範囲に対して正規化を行います。

ダブルクリックによる展平の判定は、同じ手の直前の曲率ハンドル解放に基づきます。ウィンドウIDが同一であり、次の押下と前回の有効な解放の間隔が`CURVATURE_DOUBLE_CLICK_INTERVAL{500}`ミリ秒を超えていない場合、SDKは`curvature=0`を設定し、今回のキーを先に離してから次のジェスチャーを開始することを要求します。これは通常の属性更新パスを使用して平面をコミットし、その後のEngineのOverlay更新時にのみ表示状態が反映されます。したがって、SDKの曲率変化と最終的なOverlayの表示をそれぞれ記録することで、「すでに展平されているのに目の前ではまだ古い曲面が表示されている」というタイミング問題を調査できます。

## 10.レイヤー別デバッグと練習

「ウィンドウが表示されない」場合、まず参照座標系に現在有効なトラッキングがあるか、次に初期位置決定が完了したかを確認します。コントロールがずれている場合は、まず単位回転と`s=1`で再現し、その後1項目のみ変更します。サイズに伴う偏差は通常半幅または比例単位に関連し、ヘッドセットの回転に伴う偏差は通常変換方向に関連します。曲面でのみ現れる偏差は、左右対称点のテストで使用できます。対称点は逆の`x`と同一の`z`を取得すべきであり、ヒットすれば対称な`left`に戻る必要があります。背面からのキャプチャが不安定な場合は、キャプチャ時の法線の符号とその後固定されるキャプチャ距離を記録し、翼端ヒットの変化と実際の回転軸の変化を区別します。

以下の練習を使用して、直感が確立されているか確認できます。

1. `w=800`、`h=400`、`s=0.5`の場合、ウィンドウ面中心座標系における`(left,top)=(200,300)`はいくつですか？1ピクセルあたり半ミリメートルで、水平方向は中心から`−200`ピクセル、垂直下方向は`100`ピクセルです。答えは`(−0.10,−0.05,0)`です。幅の変化に対して物理的な拡大を行う場合、この問題の`w`と`s`を同時に変更しないでください。
2. `W=0.8`メートルで総曲げ角が`90°`になる場合、曲率はいくつですか？まず角を`π/2`に変換し、次に`0.8`で割ると、`κ≈1.9635`毎メートルになります。このときOpenVRが使用する周数比は`Θ/(2π)=0.25`であり、物理曲率である`1.9635`とは単位が異なります。
3. ある方向が`(1,0,0)`の平面レイは、なぜその起点だけではヒットを判定できないのでしょうか？`z`方程式に代入すると`d_z=0`となり、レイに沿ったすべての点が同じ`z`を持つためです。起点が平面内にある場合はすべての点が共面になり、起点が平面外にある場合は交点がありません。交差関数が必要なのは、相互作用に使用できる一意の距離です。
4. ボタンクリック処理で`left/top`を取得した後、なぜ通常四元数を知らなくてもよいのでしょうか？Engineが物理レイをウィンドウ面ローカルに変換し、論理ピクセルを復元しているためです。SDKは当時のコントロールジオメトリ、クリッピング、フォーカス、イベントチェーンのみを担当します。ジオメトリ層とUI層がそれぞれ自分の契約を確認すれば、個別に検証できます。

ソースコードを逆方向に照合する場合は、SDKの`geometry/vec3.cpp`、`geometry/quat.cpp`、`geometry/pose.cpp`から始め、次に`core/ui_runtime.cpp`内の参照変換を確認し、最後にEngineの`core/service_runtime.cpp`とSDKの`core/ui_runtime_input.cpp`、`core/ui_runtime_grab.cpp`、`core/ui_runtime_scroll.cpp`に接続します。各成分がピクセル、メートル、度、ラジアンのいずれかを明確にマークすれば、ほぼすべての数式の符号と比例を独立して照合できます。
