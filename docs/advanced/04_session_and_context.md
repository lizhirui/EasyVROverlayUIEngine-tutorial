# Engine会话、窗口焦点与嵌套模态循环

打开两个应用，每个应用各有两个窗口。你点击应用A的文本框，然后从它的按钮进入确认窗。此时需要分别回答几个问题。服务端应把键盘送往哪个会话？哪个窗面可以被激光选中？应用A内部哪个控件保存编辑焦点？发起确认的外层按钮回调何时继续？这些问题分别涉及连接、窗面、控件和调用栈。理解每层上下文的寿命，就能从源码解释为什么多层模态可以阻塞调用者，同时让其他窗口继续处理消息。

## 1.从接入连接到登记会话

Engine从IPv4或IPv6监听接入TCP连接，为连接分配服务侧会话编号。此时只是为接入对象编号，协议操作要等TLS和应用鉴权完成。`ipc_connection::implementation::run()`先握手，调用`authenticate()`，发送`welcome`后进入`verified`状态，启动心跳并处理普通请求。一个客户端重连得到的是另一条连接及新的会话身份，不能直接沿用已经断开的旧窗面编号映射。握手数据和帧格式见[第03章](./03_ipc_tls_protocol.md)。

本机环回连接提供机会用系统TCP表查找属主进程。找到进程并建立`process_watch`后，引擎会检查申报PID是否一致，并保留经核验的PID与进程创建时间。PID是操作系统可复用的短期编号，创建时间能帮助分辨同号的新进程。若连接来自远程，服务机器上的同号PID不能代表发起方。`welcome`可返回申报的远程PID，但运行时向管理操作传递的本机进程身份是空的。环回查找本身也有可能失败，判断是否能执行本机进程级操作应看核验结果。不可将任意`welcome.owner_process_id`视为可信本机进程句柄。

Engine宿主把连接层与业务层接起来。宿主请求回调在受保护的运行时上下文中订阅跟踪状态，将会话与连接进程及名称报告给应用和Desktop跟踪器，再将请求交给`service_runtime::execute()`。传输的`verified`与应用注册表何时观察到第一条请求，是两个不同的观察点。一个连接有合法会话还不意味着它已经提交窗面。一个窗面也可能在隐藏状态存活很长时间，查询时应按目的分别读取会话、可见窗面及应用对象。

## 2.会话角色与辅助表面

普通应用用`present`创建自己的窗面，并可以在合适的当前窗口上打开输入区。layout或IME会话通过`input_provider_register`注册类型。注册条件会检查该会话没有活动输入区、现存窗面都符合辅助表面要求，再由输入组件管理逻辑记录它的角色。角色在连接生命周期内使用，消息处理按已注册身份判断资格。一个不合法的注册请求会失败，不能把普通窗面现有的焦点状态悄悄变成输入组件状态。

辅助表面是一种有具体条件的窗面。例如IME候选窗和虚拟键盘都用自己的控件绘制，却需要排在应用输入区附近。Engine按输入区和当前组件状态确定其空间位置及命中资格。点击辅助表面可以把指针送给该表面所属应用，同时让当前普通应用窗口保留键盘输入目标。这就是用激光点键盘时字仍进入原文本框的基础。辅助表面的显示位置和普通应用的公开跟踪模式属于不同的控制层。

角色互斥解决的是时序与归属。若同一连接既作为输入用户打开输入区，又作为该输入区组件产生正文，服务必须判断同一会话里哪些窗面要跟随旧区关闭、哪些应保有焦点，以及哪个线程操作应该等待哪个组件。用互斥角色约束后，一条普通关闭命令影响原应用窗口，辅助组件发送和排空的资格沿输入路径单独管理。SDK也能据所在角色决定用普通窗口还是辅助表面进行提交。完整时序见[第06章](./06_input_routing_and_drain.md)。

## 3.窗面生命周期、局部与全局编号

设应用A与B都选`window=7`作为本地编号。服务端先用当前验证会话找到`session_map[session]`，把窗口7转换为全局表面ID，再访问`surface_map`。如果会话A关闭自己的窗口7，能释放的是映射中归A所有的表面。输入、渲染和跟踪的跨会话选择需要全局标识，发回应用时则还原它熟悉的局部窗口号。窗口名、显示标题和这两个编号也应分别看待。前两者可用于界面呈现，映射键表达的是归属。

Engine接到`present`对该会话的元数据、命令和初始布局作验证并维护窗面。若没有这块窗口的已有记录，则分配全局对象并建立映射。后续批次可以只改变能定位的窗口或节点。隐藏窗口仍可能保存窗面数据，达到再次显示时复用所需状态。关闭已提交窗口时SDK发`surface_close`，服务按会话清理表面。重复关闭时使用与会话绑定的已关闭记录区分期望回收和未知对象。

会话断开时，`service_runtime::disconnect()`整理它的输入状态，收集该会话名下的全局表面ID，再逐一关闭表面。随后移除该会话的映射、跟踪缓存和关闭记录，并更新组件连接状态。先复制待删ID列表再关闭，可以避免删除对象的同时破坏正在遍历的原映射。宿主的断线回调还通知应用登记和Desktop跟踪。资源回收按会话发生，因此管理界面中可知道是一个程序的所有窗面消失，还是某一单独窗口关闭。

可用两个日志字段做练习。对客户端产生的`window=7`操作记录会话ID和本地窗口号，再对Engine的命中记录全局表面ID。若事件误送到另一个应用，先排查两次映射的输入值。若同一客户端重连后事件报告未知窗口，再确认操作使用的是当前连接同一代的窗口句柄。比较窗口标题只能说明同名，不能代替这两项核对。

## 4.Z序、空间距离、捕获与当前窗口

### 同一位置看起来重叠，原因可能各不相同

设想两块窗面正好相邻。若两者采用相同姿态、同一位置和物理尺度，它们从特定视角看上去完全重叠。Overlay合成必须有顺序，而射线对两块面也可能求出同样的距离。若次序可用但图形深度相同，操作者未必能从图像判断当前命中了哪一扇。窗口初始放置会尽量考虑来源窗与已有窗面，结果由Engine处理。验证放置时应看空间位置与旋转，从根源上避免互相覆盖，再单看显示排序是否合适。

设A距控制器0.85米、B距控制器0.70米。两窗可见且射线均与窗面相交时，B的交点更近，激光止于B。禁用或被模态阻塞的B仍是几何遮挡面，Engine在该处绘制激光落点。隐藏B或让射线绕开B后，射线才可能到达A。若控制器已捕获A，Engine先按捕获规则处理仍符合条件的A。

视觉的Z序与当前窗口还可以用标题栏和辅助窗理解。在前方虚拟键盘上命中按钮时，提供输入的表面可以位于视觉前方，但服务端键盘目标继续指向普通应用。这对于候选窗也相同。应用内输入焦点更不会随另一个进程的Hover改变。调试需要同时看三个阶段的数据。第一看引擎选择的全局表面，第二看发送给目标会话的局部窗口ID，第三看SDK在该窗口选中的控件。局部窗口号相同并不能说明跨进程目标相同。

前后两个窗口的体验还取决于是否开始了捕获。按住可调整控件再移出窗面时，原事件目标仍会接收位置。若捕获被释放，新命中另一个窗面，不一定产生本来在它身上按下的那次点击。Engine还跟踪按下后需先释放再接受新交互的条件。把“从一处按下后移动到另一处”和“在另一处重新按下”分开测试，能验证边界行为。

传统二维桌面常把重叠窗口当成一叠纸，只需算屏幕点是否落进最上面那张。VR里每块表面有实际空间位姿，射线可能先穿过一个预期在“前景”的片段，也可能从较近窗面的边缘外经过。有两套关系要观察。Overlay的显示排序服务于合成。当前`overlay_manager`为窗口与激光分别使用固定的排序值，普通窗口之间的拾取另走空间求交。指针以可见、可定位窗面的实际交点距离裁决遮挡。对最近窗面再根据可用状态和`is_eligible()`判断是否投递事件。`service_runtime.cpp`在无捕获时逆序遍历窗口，只在距离严格更近时替换交点。相等距离按遍历遇到的候选自然处理，而一般情况由几何距离裁决。

带手柄跟踪锚点的窗面还要考虑该手能否合理与之交互，辅助表面另受其工作状态约束。附近的显示区域可以给激光束留下边缘延伸，实际可操作目标仍需真正在窗面边界内命中。如果发现窗口边缘外光束还亮，仅凭这项观察不能断言按钮可以被点击。要区分可见激光束、真实命中和交互捕获三组输出，计算细节见[第07章](./07_spatial_math.md)。

一旦获得合法指针捕获，更新过程优先检查该窗面仍有效并计算它的交点。必要时考虑更宽的投影情况，甚至在窗面可定位时使用先前捕获位置作为回退。捕获让拖动滚动条或调整窗口时，指针移出区域也继续有明确去向。目标隐藏、变为无法交互、释放捕获或会话断开时，服务和SDK都要收尾相应状态。

Engine的当前普通窗口并不是每次hover命中都改变。目标选择跟交互阶段有关。按下扳机或侧握命中适合的普通窗面时，可以选中该窗口并衔接旧输入路径关闭；与此同时，Engine还会将左右手按键边沿作为`global_pointer_down/up`广播给全部已鉴权会话（独立于当前窗口与激光落点，由SDK派发给未关闭、未释放的全部窗口）。普通窗面选择与控件的焦点又独立。一个窗口的标题栏被点击后，它可以成为当前窗口，文字是否落进文本框仍由该会话SDK决定。横跨多个窗面的调试，应分别记录射线目标、捕获目标、当前窗口、应用内部焦点。没有某一项就用另一项推测，常会把一次正常的焦点交接误作事件丢失。

## 5.应用发现、工作目录与管理列表

`.easyvrui`是应用启动清单，其`name`提供本地化名称，`launch`决定原生程序或Python脚本、参数以及可选的`run_as_administrator`管理员权限要求（与`launch_application()`调用参数取逻辑或，普通权限启动器请求管理员目标时返回`administrator_privilege_required`）。Desktop的配置记录所管理的清单路径，File Manager也可以从当前路径或文件关联取得清单。SDK在调用进程所在机器解析和启动程序。清单中的相对执行路径与子进程工作目录以清单目录为基准。这个启动目录与Engine可执行文件旁的配置目录、与`.easyvruifrm`的设计文件目录均有不同用途。

以下清单假设`main.py`就在清单旁。若调用机上引擎在远程，应用必须拿到连接材料才会把窗口提交到相同服务。把脚本与清单一起部署，就可以用相对路径描述可移植的目录布局。调用者可在公开启动接口附加参数，单实例由应用自身协调。

```json
{
    "name":
    {
        "zh": "计数器",
        "en": "Counter",
        "ja": "カウンター"
    },
    "launch":
    {
        "runtime": "python",
        "script": "main.py"
    }
}
```

已安装于列表的应用与当前运行中的会话也有区别。启动清单可以存在而进程未运行，进程也可能由命令行启动并连接Engine。Task Manager的运行信息根据活跃会话、连接身份和窗口记录产生。只有经过核验且满足相关权限的目标才能用于本机进程管理。远端会话可以提供窗口与通信状态，不能让服务机拿远端声明的PID直接操作碰巧同号的本机进程。

## 6.普通应用如何驱动一次消息泵

### 模态期间键盘如何转到合适的窗口

SDK的模态阻塞会更新窗面的可交互状态，Engine会在收到更新后按当前窗口规则处理。举例来说，主窗当前拥有键盘，打开确认框后主窗仍可见但暂时被禁用。服务暂停主窗的选择资格，整理旧输入路径。若同一会话只剩一个可交互的普通窗口，键盘可由该窗接替。这就是常见的“主窗打开确认框后立即可以在确认框输入”的条件。若会话里还存在第三个可交互普通窗口，不能只根据其中某一个新出现就猜键盘应该给谁，仍可显式用激光选择。

原窗重新启用时可以按恢复顺序回到原来的目标，需满足仍可见、属于原会话且参考可用。若用户已经明确选择其他应用窗口，后续关闭模态不应将选择抢回。若窗口已真正关闭或隐藏，之后再次显示要遵循一般选择规则。辅助输入条的可交互表面和普通候选窗口也要分开看，输入条可以接到指针而保留原普通窗口的键盘去向。排查模态和输入问题，应同时记录客户端直接owner、Engine收到的窗面可用性和当前键盘窗口三项状态。

SDK的`ui_runtime::get_current()`取得当前线程运行时。普通程序先建立窗体，再通过`easyvrui::run()`或Python`easyvrui.run()`泵消息。有其他事件宿主时可显式调用`pump()`，按宿主约定安排等待。对每一轮，`pump()`处理网络队列和本地回调，执行`tick()`更新依赖时钟的状态，再尝试`flush_window_list()`。等待由`wait_for_activity()`根据连接状态、按键或手柄滚动、光标及空闲截止点协调。

这是一种有工作由一条拥有者线程消费的模型。后台reader可以接收服务数据，界面事件处理器仍在拥有者线程执行，后台应用任务也经投递进入该线程。普通`run()`关注有没有仍需驱动的窗口及运行时停止标记。结束阶段会调用`finish_run()`完成对应异步收尾，必要时关连接。窗口隐藏不必等于已经关闭，判断消息循环终止应看运行时实际统计的状态。

`process_message()`先直接分发，再在活跃连接存在时尝试提交变化。以窗口输入事件为例，分发选择正确窗体，然后沿自己的控件树寻找接收者。SDK在派发期间维护用于源窗口和新窗位置等语义的`dispatch_window`。这项上下文让在按钮事件里创建的窗口能参考正确源窗。拥有来源上下文和因为已在分派而推迟所有入站事件，是不同做法。在前者里，每次分派按自己的语义设置并复原源窗口，正常的嵌套消息循环仍使用共享队列。

## 7.从Win32的模态习惯理解同步返回

可以用一个典型Win32模式来理解。打开确认窗时对owner调用`EnableWindow(owner, FALSE)`，对话框可以继续接收输入。发起函数进入嵌套的`GetMessage`与`DispatchMessage`循环。直到对话框取得结果，函数退出该内层循环，然后恢复owner的交互机会。MFC等桌面框架将相同思想封装在模态窗口接口中。这里讲的是同步API的运行模型，实际Windows框架还能处理对话框键盘导航、应用退出等专门细节。

将“阻塞”拆成两层，代码变清楚。外层按钮函数现在停在模态调用那行，局部变量还在栈上，所以语句在对话框返回之前不继续。内层循环仍运行于同一线程，能够分派消息和执行对话框的按钮回调。线程的程序计数器此时在内层循环中，并未被永久冻结。其他具备交互资格的窗口仍可被处理。只要没有拿着其他回调也必须取得的锁跨越模态调用，业务可以按这个顺序组织代码。

EasyVRUI对应的是SDK窗面与事件权限。`begin_dialog()`核对待显示窗体尚未关闭、不可见且未在模态中，验证owner属于同一运行时且可交互。它重置`dialog_result`为`none`，设置owner与`dialog`状态，显示窗体。SDK用`get_blocking_dialog()`判断直接owner是否有可见且活跃的模态子窗口，取消相关交互并更新提交状态。它适用的是自己的窗口与Engine窗面，概念上等价于暂时丧失交互资格。无关的同会话窗口不被直接owner规则阻塞。

## 8.同一线程如何进入两层EasyVRUI模态

### 阻塞是调用栈上的关系

假设每个函数进入时把自己的局部变量放在栈帧中。主循环调用按钮回调，按钮回调再调用`show_dialog()`。正常的C++调用不会销毁调用者的局部变量，此时按钮回调的栈帧只是等待被调函数返回。内层`show_dialog()`执行的一次泵，可以再调用一个按钮回调，发生新的普通函数调用。两份回调的局部状态由不同栈帧保存。解释器执行Python回调时也会建立独立的调用帧。网络由后台继续接收，所以没有必要复制一份整个UI运行时供内层使用。

用一个可验证的差异来理解，模态传入owner后禁止的是这个窗面的交互。应用把owner的业务属性`enabled`设为真或假则有另外的理由和寿命。当前实现由`is_interactable()`积累窗口自身资格及模态阻塞，查询活动对话框来得出结果。由此，即使模态结束，原本就不具备交互资格的窗体也不会凭空恢复成可交互。Windows的比喻只是帮助理解临时阻塞owner，真正写业务代码时不应额外覆盖窗口属性。

两层还要按时间维持合理的owner。正在运行的A已阻塞主窗，此刻B应该以A为owner。若再次拿已阻塞的主窗当B的owner，`begin_dialog()`的交互要求会拦住这项调用。这样内层窗口的阻塞链和用户可继续使用的最上层一致。设置`none`也不触发自动关闭，如果业务逻辑希望明确取消，可以写取消结果或直接请求正常关闭。收到取消结果后区分“用户取消”和“某次关闭曾被处理器否决但后来又确定”，取决于业务要记录何种过程。

`ui_runtime::show_dialog()`在`begin_dialog()`之后进入以`item.dialog && !stopped`为条件的循环。每轮泵事件，再检查是否已结束。仍有效时执行`tick(0.0)`、尝试刷新，并在还需要工作时通过`wait_for_activity()`等待。下面是一条正常例路径，外层应用循环、确认窗循环、二次确认循环都实际由同一线程推动。

```text
run()
  主窗按钮 on_click
    show_dialog(主窗)       确认窗A开始拥有模态交互
      A的详情按钮 on_click
        show_dialog(A)      确认窗B开始拥有模态交互
          B的确定按钮设置 dialog_result = ok
        从B返回 ok
      A的回调读取B的控件，随后退出
      A的确认按钮设置 dialog_result = yes
    从A返回 yes
  主窗继续原按钮回调
```

在最深处，主窗有直接模态子窗A，A有直接模态子窗B，所以前两者都各自因直接子窗口而阻塞。关闭B后解除A的阻塞，主窗仍由A阻塞。关闭A后主窗恢复资格。这个状态可视为每层一个直接owner关系，由活动窗体状态推导，业务代码不用手动维持一个额外的阻塞计数。

给`dialog_result`写非`none`值会尝试`close()`。如果关闭事件取消，setter恢复之前的结果，模态循环继续。若正常关闭时结果仍为`none`，`finish_dialog()`采用`cancel`，解除`dialog`标记和owner关系，相关元数据进入更新。关闭owner或隐藏owner时，其子对话框会按相应原因关闭。对话框对象仍可由调用者持有，在返回后可以读取业务控件。这个生命周期与第[02章](./02_sdk_and_engine_interface.md)介绍的引用规则直接相关。

## 9.双队列与纯嵌套循环为何能够配合

### 按四个时刻检查共享队列

假设网络已收到事件A、B、C，A的处理器打算打开确认框。进入外层泵先得到本轮的序号上限，然后只从队首取A。A在应用代码准备对话框，B与C仍在连接里。A调用`show_dialog()`时，内层泵获得它自己的上限，可以按序取B及C。无论C是否恰好让B所处的回调去启动另一层，未被处理的消息仍由同一个连接管理。最终内层退出，外层从共享队列当前的未处理项恢复，而不是又执行早先已被内层处理的B与C。

现在把一个普通同步请求插到A里，并假设读线程在它的响应前收到事件D。D按正常序号入事件队列，对应的同步响应放专属槽位。A等待结束后先继续自己的普通语句，只有显式进入模态或返回外层应用泵时才会执行D。同步请求没有把事件带入A的中间状态，模态循环则可以按意图执行D。确定这两个路径各自的入口，就能理解为什么省去用于阻止普通递归分发的深度守卫也不会丢失这层限制。

共享的运行时状态仍然需要遵守对象寿命和作用域。一个外层处理器在调用模态前拿到某个控件，内层其他窗口的事件可能修改同一应用的布局或关闭该控件的窗口。回到外层之后，要按业务需要重新确认所用对象是否还活着并处在正确阶段。直接owner关系能限制指定父窗的交互，同线程泵仍允许运行一般任务与定时相关工作。把必须跨模态保持的业务数据另存为值，常比假定一个复杂控件状态永远不变更清晰。

### 为什么保持UI线程可继续走比单独睡眠重要

一个反例是先显示对话框，然后在UI线程等一个条件变量，只让对话框按钮回调来唤醒它。按钮回调正需要这条UI线程执行，等待又不给该线程泵消息，两者形成相互等待。另一种反例是在同一调用中拿着组件锁进入模态，再在任何内层回调试图取得同一锁。虽然循环仍在泵，回调会卡在锁上。正常使用中先完成准备工作并释放这些锁，再进入模态。内层依靠线程正确分派双方工作，外层依靠返回值继续业务，两种等待才能协调。

渲染保护也是类似的工作阶段问题。当前窗面的命令记录还未结束时，SDK不会允许同步等另一个窗面的显示及操作，因为等待需要运行新的提交轮次。此时应由合适的业务事件开启对话框，或将动作安排到后续拥有者线程调度。诊断中的`dialog_wait_during_render`指出具体调用位置比“整个程序不能弹窗”更准确。普通按钮、多层嵌套或后台投递如何组合，仍取决于它们实际进入的是事件阶段还是渲染阶段。

关键是分清“一个计算结果必须同步拿到”和“应用明确要进入新的交互循环”。同步`connection::request()`登记自己的ID并只等待自己的响应槽，后台reader接收事件时将它们入队。要等一个结果不需要执行应用代码，也就没有理由在任意属性操作进行到一半时忽然分派新点击。相比之下，`show_dialog()`就是明示需要在当前调用栈里继续运行事件泵，它在可验证的窗口状态下进入同一连接的队列。

设外层`on_click`在本地做三件事。先向服务同步取得数值，接着打开确认窗，最后根据返回结果提交修改。如果reader在第一步收到确认相关事件，事件留在队列。取得数值后外层进入`show_dialog()`，才可由内层泵进行处理。核心条件是没有任何普通同步等待会借用事件泵。这让`process_message()`可以直接分派，纯模态循环也无需保存分发深度、再清空延迟事件列表或恢复一个待完成输入标记。用于放置新窗口的源窗口上下文仍按每次实际派发生命期管理。

`pump_message_list()`先记录序号截止值，从响应与事件队列选出下一项，出队后释放连接锁再执行用户代码。外层如果在回调里打开模态，下一项仍留在共享队列，可以由内层泵取走。外层返回后再按当前队首继续，没有把取出的同一项执行两遍。从已到达队列开始消费时，网络响应与事件仍按各自接收序号合并。事件回调可能在内层循环中推进比外层原定截止值更多的工作，这里观察的正确性是队列消费、窗口寿命和业务栈各自完结。

仍须保留`!state->flushing`保护。渲染提交期间运行时可能正遍历节点、记录命令、更新差量基准，或临时依赖某块窗面和缓存状态。若渲染回调打开模态，内层循环可以处理针对当前窗面的关闭和控件改动，同时内层需要绘制其对话框。`flush_window_list()`本身也避开正在进行的提交轮次。强行重入既可能使外层工作使用已经变化的对象，又可能让内层窗体没有可提交的画面。将模态调用安排在由按钮或菜单驱动的事件中，可以明确创建与响应的阶段。渲染回调仍专注于生成这一轮命令。

## 10.把边界变成可以复现的实验

先开同会话下的主窗、独立窗和确认窗。在主窗打开确认窗期间尝试在独立窗点击，确认独立窗仍能更新。再由确认窗打开下一层，按顺序关闭两层，记录每个回调进入和返回。此实验验证的是直接owner关系、UI线程的嵌套调用和窗口对象可继续读取。若故意让内层的`on_closing`取消一次，可进一步验证结果恢复和继续交互的分支。

也可以把会话与窗口两个边界分开观察。启动两个进程，给其中各一扇同名窗口。关闭其中一个进程，核对另一个窗口继续存在。再从辅助键盘输入，检查当前普通窗与实际激光命中的辅助表面分别归谁。最后让一个普通事件处理器做短的同步读取并在后台收到新事件，记录请求何时返回以及下一轮泵何时真正执行事件。这样可以分别验证会话回收、输入归属和同步等待隔离。

问题只有在两层模态套叠时发生，先收集owner、子窗可见性与`dialog_result`，再查是否有人取消关闭或在渲染期间调用。若多个应用表现同样卡顿，再回到Engine和连接层看共同故障。若视觉已更新而焦点仍指向旧控件，观察输入区排空、当前窗口通知和本地焦点，不要仅凭最后一帧画面推断状态。这种逐边界验证的方法也适用于[第05章](./05_rendering_pipeline.md)的提交与渲染调试。
