# Input Routing and Serial Draining

Suppose you type in pinyin in the input field of window A, while the mouse pointer is on window B. However, it takes a while for the candidate words to be processed. Which window should this candidate word ultimately be sent to? If the system only reads “current window” at the time of sending, the word might end up in B. If the old input method is stopped immediately, the user's result, which has already been confirmed, might be lost. To handle this correctly, a time period must be reserved for the old route to complete its work, and a clear boundary must be established for the switch.

This chapter first separates window selection, control focus, keyboard mode, and input. Then, it traces back to `input_router` in Engine from two input chains. Finally, it gradually derives the necessary conditions for serial draining, including key release, delayed results, component timeouts, and how SDK returns to the old editor to complete the input in a single thread.

## 1. Distinguish between windows, controls, input areas, and input components

### “What is currently selected” has two answers

Engine maintains the current target at the window level. After the mouse laser selects a window that meets the conditions in Engine, regular keys have a reachable session. `input_router::get_current_window_id()` also checks that the surface exists, is visible, interactable, has a valid spatial pose, and is a regular window that can become the current target. If this window temporarily loses tracking, even if its previous ID is remembered, there is no reliable new input destination. This layer only requires windows and sessions, allowing it to serve different applications and components.

After receiving events sent to the window, the SDK maintains the focus within the window. The focus can be on a particular `textbox`, a button, a list, or a grid. A window can have multiple editors, but at the same time, keyboard events are sent to the currently selected control. If the focus moves from the first input field in Window A to the second input field using `Tab`, the Engine will still see Window A as the current window. When switching to another input field, the SDK must also ensure which control receives the old text and when the new focus is applied. Equating window selection with control focus will miss situations where the focus changes without actually changing the window.

When a window has no available editor, the user can still operate buttons or lists to receive `key_down/key_up`. Only when entering text editing does SDK request the opening of the input area under appropriate conditions. The input area is a rectangle associated with a regular window, described along the window surface logic pixels. It tells Engine where the auxiliary window should be displayed and indicates which IME the current input chain should pass through. Text buffering, selection, and cursor are maintained by SDK controls and applications. The candidate words and combined content seen by the user are generated by the IME. The same input area rectangle does not mean that two text boxes refer to the same business object, so switching requires clear timing rather than coordinate comparison.

### Keyboard mode determines where to input

There are two types of keyboard modes: physical and virtual. In physical mode, the system can receive keys from the physical keyboard and send them to Engine. In virtual mode, `layout` is an independent application that displays key positions and generates keyboard events. `ime` is an independent application that consumes, processes, or forwards keys and submits text. The responsibilities of the two components can be understood by changing the keyboard layout. Changing the American keyboard to another layout changes the key positions, characters, and modifiers. Changing pinyin to Japanese IME changes how continuous input is interpreted into final text. Both choices can be changed separately.

The components being selected and currently processing input are two different states. Registration completion means that a certain session has a confirmed component role. Being selected as the default or current component means it may be used in the next segment of input. Only when there is a valid target currently, the input area is open, and the path requires the component does it actually become `active`. The selected virtual keyboard remains in physical keyboard mode but does not participate in input along this path. The IME selection for regular applications can also be maintained by session; which IME is chosen is found through the current application's session. `input_router::refresh_route()` retrieves `get_selected_ime_session()` from the current window's session, and when it is a virtual keyboard and the IME is valid, it retrieves the active `layout` session.

The complete state can be represented as a quad `(目标窗,输入矩形,键盘模式,活动组件)`. When a quantity changes, two things need to be checked. What outputs might the old route produce? Under what conditions can the new route start? `hide_input_ui` changes the input rectangle, cutting the window changes the target, `Pause` changes the keyboard mode, and choosing different IMEs changes the active component. These actions have different interface effects, but they all may require the old route to finish first.

## 2. Where does the complete route start and end?

### Directly deliver regular keys when the input area closes.

Assume the focus is on `button` in a window, the input area closes, and the user has turned on physical mode. The Engine normalizes physical keys into events, `input_router::handle_key()` puts them into the queue for execution, `route_key()` verifies the active window and physical mode, and then sends them to the session belonging to this window through `send_window_event()`. When sending, `window` writes the local window ID of that session. The server object table uses a global mapping internally, and applications only need to understand their own local IDs. Even if both applications create windows numbered `100`, they will reach different targets through different sessions.

For the same physical key, `key_down` and `key_up` represent two state changes. The event `key` is the standardized key name, and `shift/ctrl/alt/meta` describes the modifier state at that time. Pressing may also be accompanied by `text` generated by keyboard decoding, for example, pressing the letter `A` without a modifier key, and the decoding result might be `a`. But the key name is used for key binding, and the text is used to pass to the editor; the two must be distinguished. `Shift` usually does not generate text, and `Backspace` corresponds to the editing action. The "Hello" submitted by IME may be produced by many keys. Writing `text` as the key identifier will lose these differences.

If the input area closes and it is currently in virtual mode, the Engine's regular physical key path is not enabled. The virtual keyboard, as an auxiliary component of the input area, also needs to meet active conditions before it can send keys to the old route or the current route. In this state, the handle can still directly activate window controls. The input method routing focuses on keyboard and text events, and laser clicks do not need to go through IME first to decide whether to press the button.

### Menu mnemonics and input method combination keys

When the SDK receives the `Alt` press event, it will make the `menubar` of the current window display the mnemonic underline; it will also display the underline after entering the menu keyboard navigation. The Engine only attaches `alt_tap=true` to the release event of the independent press and release of `Alt`. The input component automatically forwards this field when it releases. The SDK also checks the current window and the pending activation state, and switches the menu keyboard navigation only when the conditions are met.

`Alt+Shift` is processed by the Engine for input language switching. The release of combination keys and the release generated by draining the input path use regular key events. After switching, the original `textbox` continues to hold the editing focus. During troubleshooting, record the key press/release, `alt_tap`, IME selection, and control focus separately.

### The input area is processed through IME when it opens.

After the input area opens, the starting point of the physical path is still the physical keyboard, but `route_key()` sends standardized events to the current IME. The IME is allowed to implement various behaviors. It can consume keys used for word grouping, draw candidate interfaces as needed, submit text when the user confirms, or transfer unconsumed keys as key events to the application. For example, if there is an unsubmitted pinyin in the input box, pressing the space can be consumed by the IME to select words. When there is no combined content, the IME can decide whether to use a regular space input or forward based on its behavior. The application distinguishes keys and completed text by event type.

Virtual mode has an additional starting point. `layout` converts the key hit by the laser into `key_down/key_up`, which is sent to the Engine through `input_provider_send`. The Engine only forwards it to the IME when it still has the right to send this path. After that, it shares the second half of the chain with physical mode. The built-in EasyVRUI English direct keys are identified in English. The built-in pinyin and Japanese IME each draw candidate windows, and the candidate window buttons are always in Chinese or Japanese. The input bars of regular applications are displayed according to the SDK interface language. Third-party IMEs can also implement their own candidate interfaces using independent auxiliary windows.

|Current input area|Source conditions|Path before routing to the application|
|---|---|---|
|Close|Entity mode has a valid window|Physical keyboard → Engine → SDK belonging to the regular window|
|Open|Entity mode|Physical keyboard → Engine → IME → Engine → SDK belonging to the regular window|
|Open|Virtual mode|`layout` → Engine → IME → Engine → SDK belonging to the regular window|

All three routes leave the final control selection in the SDK. Upon receiving `ime_submit`, the SDK treats `text` as completed text input and processes it according to the edit focus of the window to which the current event belongs. During the input region activation, the SDK distinguishes between key operations and IME-submitted text when processing `key_down` to prevent a character already sent to the IME from being written again verbatim. When verifying actual behavior, a combined process can be recorded as an event sequence, with each item queried as either a "key interaction" or "completed text." If an input method forwards plain text for regular letters while also submitting the same string, it will cause duplication in the consumption rules; the routing layer will not automatically understand the meaning of the candidate words.

## 3. What protocol actions do the application and components use separately

### The opening of the input area is requested by the current regular window

The SDK calculates the window logical rectangle from the focus editor. The input controls in a scrolling container may only be partially visible, so the range of the `get_input_area_rectangle()` combination ancestor is taken, taking into account the area of the positioning assist border. If the editor is non-interactive, read-only, or has no actual area, the SDK should disable the input area through input state management instead of providing a zero-width and height window frame for the component to guess. The application only needs to provide the window and geometric range, and the height and content of the candidate window are arranged by the IME itself.

Here is an example of requesting the opening of the input area in virtual mode, with the coordinates of the fields still using the top-left corner as the origin. In actual sessions, fill in the corresponding credential fields and request number.

```json
{
    "message_type": "request",
    "id": 21,
    "session_id": 1,
    "session_token": "<应用会话令牌>",
    "op": "show_input_ui",
    "window": 100,
    "rectangle":
    {
        "left": 24.0,
        "top": 124.0,
        "width": 590.0,
        "height": 42.0
    }
}
```

Engine's `input_router::handle_operation()` checks that this is a regular application session, searching for the corresponding surface by session and window ID, requiring it to be the current window, and reading limited values and positive width and height. The opening path also requires an available IME, and in virtual mode, an available `layout`. This application change checks again that the session is still alive and the window is still the current target, to avoid the application being opened in the assist area after closing during queuing. When there is already an input rectangle, position adjustment can directly update the rectangle. Opening and closing boundaries and moving the assist window position do not need to use the exact same reset method. The request to close the input area is `hide_input_ui`. Engine can directly return success for already closed areas, while emptying the currently used path.

### `input_ui_state` presents different perspectives according to the recipient description

When Engine releases `input_ui_state`, ordinary applications receive `window/physical/rectangle`. `rectangle` indicates that the application window currently has no input region; `null` represents this state. When the component receives `active/physical/rectangle`, if the component is required in the current path and the input region is valid, `active` is true and provides the actual rectangle; otherwise, an empty rectangle is received. Some updates include `provider_list`, used to update the input bar or component selector. The selection state in this list differs from the meaning of `active` in the state event of this message. A typical scenario is when the entity keyboard is active, but the virtual keyboard component is still in a known configuration and receives `active=false`.

Here are the states that IME may receive when in the current input chain. This example shows the component perspective. The regular application gets the same geometry, using `window` to indicate the associated local window.

```json
{
    "message_type": "event",
    "event_type": "input_ui_state",
    "session_id": 3,
    "session_token": "<IME会话令牌>",
    "active": true,
    "physical": false,
    "rectangle":
    {
        "left": 24.0,
        "top": 124.0,
        "width": 590.0,
        "height": 42.0
    }
}
```

Distinguishing between these two perspectives has practical benefits. IME only needs to determine whether its input help interface needs to be enabled, while the regular application needs to know which input area to close or which parent window to attach the assist bar to. The protocol expresses window layer routing, and the SDK can continue to maintain multiple controls' own local focus and selection. If the component's `active` is treated as the application focus, switching to entity mode may incorrectly understand that the virtual keyboard is closed, causing the text box to lose focus.

### Both text and key output return from the component path to Engine

`input_provider::send_event()` encodes the event into the nested `event` object of `input_provider_send`. The component identity comes from the connected session. The engine cleans up the session and target window fields in the nested events, determining the destination based on the current or queued routes. `layout` can only submit key events. `ime` can simultaneously submit unconsumed keys and `ime_submit`. Both branches check the field type; keys or text must be readable from the current protocol encoding. IME can express the submission text through `commit_text()`.

```json
{
    "message_type": "request",
    "id": 47,
    "session_id": 3,
    "session_token": "<IME会话令牌>",
    "op": "input_provider_send",
    "event":
    {
        "event_type": "ime_submit",
        "text": "你好"
    }
}
```

The engine sends to the application the local `window` written to `message_type="event"` and the associated window. This makes the application receive a routed window event. The input method's guess history, incomplete combination strings, and candidate interfaces can remain within IME. Before submitting the text, the content drawn on the IME window may change many times, with each change going through normal window drawing, while the final text event is only generated when submission is selected. Do not mix the frequency of candidate drawing with text events, as the latter directly modifies the editing results in the application.

## 4. Role Mutual Exclusion and the Lifecycle of Auxiliary Surfaces

Once a SDK session is registered as `layout` or `ime`, the connection operates according to the role of the input components, creating only auxiliary surfaces. The regular application is responsible for opening the input area within its valid window. This boundary prevents candidate windows from being selected as the final input target as soon as they appear. When the user selects an option, the event is sent to the component belonging to the auxiliary surface, which reports the result to the Engine. The actual current application window remains the parent routing target. Regular application sessions can also provide auxiliary windows such as input bars for the current input area of this session.

The Engine uses `input_router::is_input_ui_surface_active()` to verify the ownership of auxiliary surfaces and whether they are in the current input chain. When a component becomes inactive, the current window becomes invalid, or the input area is closed, the corresponding surface loses this association. When calculating the position, `get_reference_pose()` reads the current regular window reference pose, subtracts the half width of the auxiliary window from the horizontal center of the input area to determine the left side of the auxiliary window. In the vertical direction, starting from the bottom edge of the input area, the application input bar is placed first, followed by the IME candidate interface, and then the virtual keyboard, using the previously displayed and valid heights of the auxiliary windows. In entity mode, there is no active `layout`, so the virtual keyboard area is automatically omitted. The width is re-aligned according to the center when it changes. The scaling of the auxiliary window inherits from the owning window, with slight front and back offsets to avoid the surface being stuck in the same position from the viewing side.

Assuming the input area is at window coordinates `left=200` with width `240`, and its horizontal center is `320`. Assuming the auxiliary window itself has no additional displacement, `physical_scale=1`, and the current IME width is `400` logical pixels, converting by the same ratio, the left edge of IME relative to the top-left corner of the window is approximately `0.320−0.200=0.120` meters. If IME changes the logical width to `280` based on the number of candidates, the left edge becomes `0.320−0.140=0.180` meters, and the center remains `0.320` meters. If the bottom of the input area is at the `300` pixel row, the first auxiliary window starts at the local `Y≈−0.300` meters of the window. This formula shows that the same IME can reuse any parent input area, and the Engine does not need to know how many characters are displayed or what dictionary is used.

A modal window changes the actual interactive target, and cannot allow the blocked or hidden parent window to continue receiving new key presses. The Engine invalidates the target in time in `invalidate_window()`; if an old window that is being emptied also becomes invalid, then `old_window_valid` is cleared. The old IME can still perform its cleanup action, and when actually delivered to the old application, it must still be checked to see if it has disappeared, been hidden, disabled, or lost its valid pose. This detail is important. The purpose of saving the old window is to retain the identity pointing to the old path and only give the still valid old target. Text after the window disappears cannot survive through a new window and automatically be delivered to a new window.

## 5. Deriving Why serial draining Is Necessary from Two Contradictions

### Why do old candidates appear in the new input box?

Starting with a deliberately simplified incorrect implementation. The Engine only maintains the variable `current_window`, and unconditionally reads this variable when receiving IME output. The time sequence may be:

|Moment|Action|State in the simplified implementation|
|---|---|---|
|`t₀`|Input box A receives key presses that form pinyin|`current_window=A`|
|`t₁`|The user confirms the candidate, and IME starts searching for results|The result is still within the old IME.|
|`t₂`|Handle selection window B|`current_window=B`|
|`t₃`|The old IME calculates and submits "hello".|Send "hello" to B using the new variable.|

The problem is that the work between `t₁` and `t₃` belongs to the old path, while the global variables read at `t₃` describe the new path. The solution must prevent these two things from being used together. The simplest fix is to discard all subsequent outputs of the old IME, which would suddenly cause A to lose the text that the user has confirmed. Fixing it to wait for `50` milliseconds only delays `t₂` by estimation, and there is no reliable completion condition when the load changes. TCP has a single connection order, but user clicks, layout, and IME can come from different connections, and the algorithm tasks of one process do not belong to the read/write order of another connection. A clear "old work completed" signal is needed.

serial draining first freezes several necessary identities of the old route. The old target is `old_window`, and the components are `old_layout` and `old_ime`. When the new route has not taken effect, results that meet the qualifications of the old phase can still be delivered to the still valid old application by `forward_provider_event()`. Only when the relevant components confirm that there is no old output will the Engine change the current window. It can be seen that this protocol uses causal boundaries instead of guessing delays. Even if `t₃` comes slightly later, as long as it is within the legal draining phase, `t₃` can only affect A.

There is another more detailed SDK-side timeline. Assume that there are text boxes one and two in A. The old IME submits the last character in the first input. The user presses `Tab`, and the SDK requests to collapse the old input area, while still maintaining focus on text box one. After the Engine completes the old channel, it sends a successful close response. Events and close responses are ordered in the connection, and the SDK applies the text that has arrived to text box one in the next round of pumping, then applies the successful callback to the target to be switched, and only then can it open the input area of text box two. This timeline verifies why the switch involves both the old session identity of the Engine and the old editing focus of the SDK.

### Why wait for layout first, then let IME confirm?

The virtual keyboard is upstream, and IME is downstream. The last output upstream may become the new work downstream. Suppose the old layout is processing a key sequence with modifier keys. At the start of the switch, it still has the last `key_up` waiting to be sent. If the Engine empties both at the same time, IME may first find that "it currently has no task" and then confirm. A few milliseconds later, the last key of the layout reaches the Engine, and there is no old IME to receive this last key. This will either discard the last key or let the new IME see a release event it has not processed.

Therefore, the confirmation order must follow dependencies. Let the layout complete its sending first, and the Engine transfers these keys to the old IME at the corresponding stage. After confirmation, close this upstream entry, and then send `input_drain` to IME. Only then can the set of old channel inputs received by IME be sealed, and it can meaningfully wait for "I have processed all work belonging to the old path." This is similar to stopping a production pipeline. First, let the upstream stop putting things onto the conveyor belt, wait for the last item to enter the downstream, and then close the downstream. If the downstream is closed in reverse, the remaining items will never complete the entire chain.

The physical keyboard path has no active virtual layout, and the old IME can directly enter IME draining. When the old input area originally has no components or the old components are disconnected, the program can skip the non-existent stage. Skipping is a decision based on the actual route and active connections. The two emptying actions still have the same logical order of dependencies.

## 6. Four-stage state transition and actual implementation

### Stage one: intercept the new route and save the old route

Enter from `input_router::begin_transition()`. The code sets `draining` to true, saves `completion` to be executed later, freezes the old window, old components, and old target validity. At the same time, clear the related caches of pointer movement and reset IME shortcut storage. For physical button presses that have already been routed through the Engine, a matching `key_up` is generated according to the old route. For example, holding down `Shift` to switch windows, the old IME or the old window when closing the input area receives the release event for finishing. At this time, the normal input continuously sent by the new route will be queued to avoid reaching both targets at the same time.

Why is synthetic release necessary? Suppose after A receives `Ctrl down`, the user releases the button before switching to B. If only the changes in focus are recorded, A may continue to think that `Ctrl` is still pressed, while B receives a `down` that it has never seen before, along with `up`. `pressed_key_map` was the pressed event originally routed by the Engine. During synthetic release, the code changes the original event to `key_up`, removes the text `text`, and places the key in `suppressed_key_set`. Only when the actual physical release occurs is it removed from the suppression list. This ensures that the same physical key that was pressed during the switch does not immediately take effect on the new target. Testing involves verifying that the old target is released, that the actual release does not become an isolated event on the new target, and that the new press can be recognized again. Only the ability to continue inputting letters after the switch is tested; residual modifier keys cannot be detected.

### Stage two: Wait for the old layout to close.

The Engine sets `draining_layout` as true. If the old layout can still send, it records the session as `waiting_session`, sets a deadline for this stage, and then sends `input_drain` along its connection. The old layout still in this stage can send old keys, and the Engine forwards these keys to the old IME. Outputs that have already been deposited in the old IME can continue to be delivered according to the validity of the old application. The shortcut handling during emptying will not initiate new IME selection for the old layout.

`input_provider_drained` is not a button that can be completed by anyone. In `input_router::handle_operation()`, it requires that `draining` is true and the session initiation equals the current `waiting_session`. This means that the old IME cannot send a valid confirmation before the old layout, and the old layout cannot confirm again during the IME stage to proceed to the next route. Component connections have been verified through the session; the sender cannot replace the component waiting by changing `role` in the event field.

### Stage three: Wait for the old IME to complete conversion and sending.

After receiving the layout confirmation, `advance_drain()` clears the waiters in the stage, changes `draining_layout`, and decides the next step based on whether the old IME is alive. If the old IME can still wait, a new `waiting_session` and independent deadline are set, and `input_drain` is sent. After this, new output from the old layout loses the right to send during the emptying stage. The old IME can submit the last key and text before completion. The Engine selects the destination through the old window reference, and still checks if the target is valid during actual delivery. This stage's verification involves checking "which route the last IME output is on" and "whether the window could actually receive at that time." When the old window is closed, there are no editable objects; the Engine retains the cleanup process and prevents the text from being sent elsewhere.

The two types of messages can be written as the following protocol objects. The first is sent by the Engine to the waiting component connections, and the second is confirmed by the component to the Engine. The example uses the `layout` stage; the IME stage uses its own session identity.

```json
{
    "message_type": "event",
    "event_type": "input_drain",
    "session_id": 2,
    "session_token": "<layout会话令牌>"
}
```

```json
{
    "message_type": "request",
    "id": 48,
    "session_id": 2,
    "session_token": "<layout会话令牌>",
    "op": "input_provider_drained"
}
```

The protocol does not require the input round number to be concatenated in these two messages. The stage is determined by the internal state of the Engine and the waiting connections. The component maintains the emptying flag and task count through the SDK, and the connections themselves remain orderly. If the boundary is missed and the component has lost its sending qualification, it cannot regain it by creating a new round number field.

### Stage four: Submit the switch and resume normal distribution.

When both old chains are completed or safely terminated, `finish_transition()` retracts the old waiting session, old component ID, and old window reference, retrieves the previously saved change actions, and sets `finishing` to constrain the queue processing during this submission period. The change actions are determined by the triggering reason. For example, closing requires emptying the rectangle, switching windows updates the current selection, switching modes modifies `physical`, and switching components activates a new session. Completing the actions refreshes the routing, publishes a new `input_ui_state`, and continues processing the queue. Only after this boundary is completed can new inputs be routed according to the new combination.

These four stages can be reviewed through actual interactions within a window. The user enters in Text Box One, then clicks on Text Box Two. First, the SDK updates the target to be selected, and then the old path drains queued input. The system knows where the user wants to go, yet it still sends the old output to the old target. Only after the word reaches the old editor can the new rectangle and focus be activated together. The application may also request to close again during the emptying process, and the SDK will incorporate the relevant callbacks into the already completed closing process. Separating "Received new intent" and "Writing new intent to active route" helps explain the situation where there is a brief pause but the focus remains correct.

## 7. How does the component know that the work has been emptied?

### Two counts respectively constrain the local task and the results sent out.

The input component needs to check two types of work. The first is the ongoing local task, such as searching for candidates from the background dictionary. The second is the input event that has been logically completed but not yet responded to and sent out. The SDK's `input_provider` is represented by `input_task_count` and `pending_send_count` respectively.

After calling `begin_input_task()`, the count increases. When the task is completed, `finish_input_task()` is called, the count is reduced, and it is rechecked to confirm the emptying. When the background thread returns the result, it should be received by the component's SDK thread and sent through the normal interface. The SDK connection has thread requirements; the work thread is suitable for calculations, and the objects and sending are processed by the thread. The key sequence is to deliver the final result of the task first, then end the task accounting. If `finish_input_task()` is called first to reset the count to zero, and `send_event()` has not started yet, the emptying may be confirmed earlier.

When `wire::send_event()` starts sending events, `pending_send_count` is increased. After receiving a response to the request, the count is reduced, and then `finish_drain()` is called. This allows "already calculated" and "Engine has received request" to be observed separately. When entering `process_drain()`, the SDK will enclose the callback with the task count to ensure that the finishing work sent during the callback is covered. Only when entering emptying, no confirmation has been sent, and both counts are zero, will `input_provider_drained` be sent. `drain_ack_sent` marks the confirmation as sent, limiting the component from sending new data for this old path. When a subsequent status notification is received, it is restored or kept inactive based on the new status.

A count track can be manually calculated. The old IME first has a dictionary task, with count `(1,0)`. When entering the emptying callback, it temporarily increases by one, becoming `(2,0)`, and becomes `(1,0)` after the callback returns. The dictionary result returns to the UI thread, and after submitting a `ime_submit`, it becomes `(1,1)`. Then the local task ends, leaving `(0,1)`. The application already has the chance to receive the final text, but the IME still waits for its own send response. Only when the Engine returns the packet does `(0,0)` arrive, after which confirmation is sent. If these two seemingly small counts are combined into a boolean value indicating "asynchronous work is done," at least one timing will be missed.

### Timeout, disconnection, and cancellation eligibility

An implementation might never confirm, or the process may exit during emptying. The Engine sets a `DRAIN_TIMEOUT{10}`-second timeout for each actual waiting stage, using a monotonic clock. A new timeout is set when moving to the next stage. If `input_router::update()` finds the current waiting session has timed out, it invalidates its lifecycle, calls the closing path, and notifies the component manager to disconnect. If the state still points to this timed-out session, the stage is advanced. The old process that has already been disconnected cannot submit from the original session even if it continues to calculate the result. This allows window switching to continue after a uncooperative component.

Disconnection follows similar boundaries. `disconnect()` marks the session as invalid, clearing the pending tasks and related selection processes for that session. If it is the current waiting session, it continues to advance. The application to which the old window belongs also invalidates the window, which is an event that can occur simultaneously with clearing the input component. Lifecycle checks are used to verify that queued tasks still have the qualification to start when they are restored. Treating "once a legitimate request was sent" as "will definitely be executed later" may leave outdated operations after long waits.

The component's emptying time limit and connection heartbeat have different responsibilities. An active connection can always have a heartbeat, but the task responsible for the dictionary remains stuck, so this path requires an independent completion time limit. Conversely, a disconnected component does not need to wait ten seconds anymore. When switching to the debug physical mode and waiting time is long, it is possible to record whether the current waiting is for layout or IME, whether the old session is still connected, and which count never returns to zero. It is difficult to determine which stage is waiting just by seeing if the current VR window is refreshed.

## 8. How to connect the local focus after the SDK is closed

On the application side, `ui_runtime::hide_input_ui()` first updates the local request intention, synchronizes the input bar, and collects `hide_callback_list`. If one close is already in progress, subsequent callbacks are added to the same round. When online, asynchronous `hide_input_ui` is sent, and the response is processed by the UI thread in the next round. Offline, the SDK directly completes local cleanup with a success result. `finish_input_hide()` clears `input_hide_pending`, and upon success, it cleans up the active areas and related objects, then moves the completion list to the local and calls them one by one. Thus, when the callback initiates a new round of operations, it goes through a new waiting list. Finally, the success path checks through `sync_input_ui()` to see if there are areas that need to be activated. Windows that are explicitly hidden can retain their original focus and keep the input area closed until the user re-enters.

There are two distinct moments in local operation. When the user presses `Tab`, the SDK can record the control to be selected. After the emptying result of the corresponding Engine is completed, the control that actually receives the text is updated. Online connections store asynchronous responses and events separately, but the UI pump retrieves them in a staggered order. The Engine first sends the old text to the same application session, then completes the close. The SDK has the opportunity to process the old text before the focus changes in the response callback. Synchronous `connection::request()` only consumes its own responses. If a text event callback makes a synchronous request for the clipboard, the request is completed first, then it returns to the original control event. Regular asynchronous operations wait for the next UI pump and will not preempt the application focus during this RPC wait.

A useful counterexample is to use synchronous calls in application scripts as a means to “process all queued events.” In the new connection, when synchronous calls return, other asynchronous responses may have arrived but are still waiting for explicit processing. If automated scripts are written, the UI pump and required conditions should be used for direct acceptance. Testing can construct three consecutive events: old text events, close responses, and new key events, and compare the distribution moments with the final content of the text boxes. The emptying guarantee in the formal implementation relies on this order.

## 9. Boundaries and release conditions for entity keyboard capture

### Two threads cooperate, and the hook only makes quick judgments

In `keyboard_broker.cpp`, the Windows driver uses `SetWindowsHookExW(WH_KEYBOARD_LL,...)` to register the low-level keyboard hook. The thread that holds the hook has its own Windows message loop. `run()` is responsible for waiting for messages, while `PeekMessageW/DispatchMessageW` handles the events assigned to it by the operating system. The hook reads the key codes, scan codes, and modifier states. It then calls `keyboard_policy::filter()` to decide whether to handle the event or not. Finally, it attempts to pass the event to the internal queue of the process. `CallNextHookEx()` is the normal release path. Only events that comply with internal rules are suppressed.

The Engine thread obtains the packet from the queue and checks again based on the snapshot whether it still belongs to the current valid target. Text decoding comes later; `keyboard_decoder`, according to the Windows keyboard layout and current state, converts the key into text and passes it to `runtime.handle_key_input()` or `handle_key_up()`. This division allows the hook thread to handle short and predictable tasks. Waiting for network, waiting for candidate calculations, or direct access to application controls in the hook not only confuses the owning thread but also slows down the operating system input chain.

The low-level hook observes keyboard events passed to it by Windows. Its scope is determined by the system input environment, and it should not be understood as being able to take over the raw data of all physical devices. The activation strategy of application windows is also maintained within this program. Installing hooks allows services to recognize switch keys, and whether ordinary keys are intercepted is controlled by the capture eligibility. Releasing the capture eligibility for ordinary keys and uninstalling Windows hooks are two different actions.

### Capture eligibility is the window lease that can expire

`keyboard_policy::is_active(now)` requires entity mode, the thread to be in listening state, a valid window ID that is not zero, and the lease to be within the period. `keyboard_broker::update()` renews the lease for the current window by `FOCUS_LEASE_MILLISECOND=500` milliseconds. `epoch` is modified when the window identity changes, also invalidating the previous decoding state. Leases and epochs can be seen as short-term tickets in the hook's hand. They indicate “which input context this set of keys can be given to.” If the Engine pauses too long without renewal, the hook loses the eligibility to take over ordinary new keys. If the queued packet comes from an old epoch, the consumer side will not treat it as a key of a new window.

The ordinary `Pause` is used to switch between entity modes. As long as the driver is in listening mode, it can handle this switch. To actually capture an ordinary key, lease conditions must be met. `Ctrl+Pause` requests access to the Desktop, while `Ctrl+Alt+Pause` requests a reset of the tracking center. These two global shortcut keys have their own matching paths. The ordinary IME switch shortcut must consider the current keyboard mode and valid context to avoid misidentification of modifier key combinations across windows. The screenshot request of `PrintScreen` must also be bound to a valid entity capture context. The implementation will track modifier keys, repeated presses, original capture targets, and actual releases. A key that has been pressed by a desktop application usually receives a paired release through the original path, rather than being suddenly handed over to VR during the pressing period.

When the context expires, the window becomes invalid, or the entity mode is exited, ordinary new keys are released. The original ownership of captured keys is used to handle their paired releases and cleanup, to avoid leaving empty states on both sides. If the device or queue cannot continue to reliably take over, the strategy will cancel the entity mode to prevent exceptions from spreading through a continuously blocked input chain. When a thread stops, the capture qualification is cleared, and `release_hook()` calls `UnhookWindowsHookEx`. These measures prevent "continuing to grab new keys after losing the window" and "retaining hooks after leaving the application."

### Input content and diagnostic information are processed separately.

The normal input path for items processes user text through the key package in memory, decoding results, IPC events, and editor buffers. The diagnostic focus of the hook and routing layer is on registration failures, timeouts, session ownership, task counts, and event types. It's important to check that nothing is left unprocessed from the user's actual input. Testing should use artificially constructed short texts and local markers, such as using `old` and `new` to verify the destination. In production mode, it's sufficient to record "old IME completed, waiting for session number and time" to determine the sequence, without recording combined strings or actual candidate content.

A piece of text may also be saved by a third-party IME in its own functional data, such as user word frequencies. This is a strategy specific to the component. The Engine's window, session, and emptying logic focuses on where the last event should be sent, without needing to hold component learning data. Distinguishing between these two levels clarifies the scope of diagnostics. If only confirming whether the text is in a window, counting, order of occurrence, current window, and old window IDs are sufficient.

## 10. Verify boundaries with logs and small experiments.

When encountering "old keys still respond after switching input methods," first confirm which session the result event comes from. If the old IME is still in the draining phase, the old target remains valid, and the old result may be attributed to the original editor. If the emptying is confirmed but the session result is still received, check the phase qualification and connection status. When "some characters are not sent," check whether the task is registered, whether there are unconfirmed messages after submission, and whether the SDK has pushed these responses. It's difficult to determine where the text went by just looking at the time the candidate window disappeared.

When encountering "the physical keyboard gets stuck on a key," the simplest path can be simulated. Enter the entity mode, keep the target window interactive, and press a modifier key. Switch the user window and observe that the old path receives the paired release. Try pressing another key while still physically holding the key, and record what the new window actually receives. After releasing the real key, press it again to confirm that it can enter the new path as a new set of presses. If problems occur only when the window is closed or tracking is lost, check the lease of the hook, Engine's `selection_valid`, and SDK's local focus simultaneously.

When writing tests, follow this order for positioning.

1. **First, verify a single path.** Check whether `key_down/key_up` can reach an ordinary window that is closed in the input area. After opening the input area, generate keys in the virtual mode using layout, and bypass layout in the entity mode to observe whether IMEs can consume events through the same interface.
2. **Then, verify the old output.** Pause the completion of the old IME, trigger the switch, and retain the result as `old`. Release it in the still valid old phase. After confirming that the old input is completed, use `new` to enter the new path, and check that the two text boxes do not write to each other.
3. **Finally, verify the failed path.** Use test fixtures to simulate component non-confirmation or disconnection. Confirm that sessions that lose their qualification cannot produce any delivery after exceeding the old phase boundary. If the window is destroyed first, check that the text does not automatically move to the new window when the old path is completed.

When checking the source code, look at `core/input_router.cpp` in the Engine. From there, examine `begin_transition()`, `advance_drain()`, and `finish_transition()`. Then, see how `driver/keyboard/keyboard_broker.cpp` and `keyboard_policy.cpp` are used for collection and lease determination. On the application side, look at `core/ui_runtime_session.cpp` and `core/ui_runtime_input.cpp` in the SDK. On the component side, look at `input/input_provider.cpp`. The corresponding regression tests include old editors and nested emptying in `tests/sdk_audit/sdk_audit_focus_probe.cpp`, focus switching in `tests/grid/grid_pointer_ime_probe.cpp`, and emptying submission in `tests/nightly_ime`. The most important assertion here is not “the pop-up window closes properly,” but rather “every input is processed in the editor and stage it belongs to.”
