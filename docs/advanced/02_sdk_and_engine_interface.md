# 原生SDK、语言绑定与窗体代码生成

C++里写`label.get_text()`，Python里读`label.text`，两边最后访问的是同一类原生对象。本章从链接讲到一次实际的事件派发，再讲对象能活多久以及设计器如何生成构造代码。把这个链条走一遍，便能理解一个属性在何处保存、什么时候需要进入Python解释器，以及关闭窗面后为何还能由调用方读取窗体。

## 1.一份原生实现怎样提供两种链接形态

`engine_interface/CMakeLists.txt`使用同一份源码列表构建`engine_interface_static`静态库和`engine_interface`共享库。C++应用包含`sdk/api/cpp/include`中的公开头，常用的集中入口是`easyvrui.h`。头文件提供声明和可见对象布局，库提供实现。实际构建的消费者链接已编译库，无需把控件实现源码拷进自己的工程。

静态库像一组已编译对象文件。链接器根据应用引入的符号，把需要的实现并入最终模块。DLL把实现留在单独的二进制中，导入库提供链接所需信息，进程加载时还要找到实际DLL。静态库和DLL导入库在Windows上都可能以`.lib`结尾，根据扩展名无法确定它是哪一种。静态链接只改变客户端代码如何进入进程，应用仍经独立连接使用Engine服务。

`ENGINE_INTERFACE_API`让编译器分辨三种情况。构建DLL时导出符号，消费DLL时导入符号，定义`ENGINE_INTERFACE_STATIC`时采用普通声明。它并不判断调用来自Python还是C++。例如编译`button`构造调用时，应用只需要知道参数和类型。链接选项随后决定引用如何解析，程序运行时才实际构造控件。

ABI是二进制层面共同遵守的约定。双方要用相容方式传递参数、放置返回对象、理解类的内存布局以及进入虚函数。若一个DLL提供`std::u32string`而另一个模块释放该字符串，双方对运行库、标准库配置以及调试迭代器的看法也要一致。构造成功并不保证析构安全，同名函数也不足以证明ABI相容。

项目的`EngineInterfaceRuntime.cmake`为静态目标选择`/MT`或`/MTd`，为DLL方式选择`/MD`或`/MDd`，并检查消费者的`MSVC_RUNTIME_LIBRARY`。当程序同时使用多个模块时，可以从返回字符串、集合或事件闭包的值传递反推为什么需要兼容运行时。真正碰到装载或链接问题，优先核对目标位数、Debug或Release、CRT配置、实际入口头与对应库版本。给二进制改名一般不能解决符号或布局不一致。

## 2.公开头文件如何限制依赖和内部访问

### 观察两种构建对故障形状的影响

如果组件A只链接静态SDK，修改控件实现后要重新链接组件A才能带上新实现。如果组件A使用配套DLL，进程启动时会解析DLL导入符号，部署目录里选错DLL可能产生导入错误或载入另一套兼容符号的实现。仅看源代码中的`#include <easyvrui.h>`，这两条路径几乎一样。排查可以分别检查CMake选中的目标、链接输入，再确认模块实际加载位置。这样可把“代码没有生效”拆成生成、链接、装载三个可见问题。

内置C++应用与安装版Python原生扩展默认链接`engine_interface_static`。安装器把唯一一份Python SDK放在`sdk/api/python/`，包、扩展和构建描述同时部署。自行构建采用共享链接的扩展时，需要相应的DLL。解释器版本、架构和链接模式须和扩展匹配。具有只读绑定的值对象与原生控件派生类也在二进制边界上使用配套声明。

Engine、SDK和内置应用各自将内置语言包编入目标文件。静态链接把SDK的语言资源带入可执行文件或扩展，DLL方式由SDK的DLL提供相同内置文字。应用通过`language_pack.load_directory()`可加载独立的自定义语言包。

公开头按值类型和可供应用调用的类组织。若在按钮头文件直接内嵌Windows平台句柄、网络类与设备对象，调用者便要看见这些类型和它们的所有间接依赖。其他头的宏和类型还会沿包含关系进入应用编译单元。把平台细节留在驱动实现文件，意味着扩充设备实现时修改范围更集中，应用也可以从公开声明看出自己真正需要的依赖。

PIMPL指“指向实现的指针”。以内部`connection`为例，前置声明让类持有指向`implementation`的指针，线程、条件变量与消息队列的实际布局由实现文件定义。调用者通过方法调用操作连接，不需要知道队列内部用什么容器。隶属关系、销毁时机和间接访问是这项设计的一部分。并非每个值类型都适合PIMPL，例如只保存分量的几何向量直接用值传递更清楚。

减少公开布局有助于压缩改动传播范围。它仍不能保证任意两版头和库可以混用。只要某个公开类的布局、继承或虚函数约定变化，同名接口仍可能生成不同机器码。使用配套SDK头、二进制和工具链，是比信赖单个导出宏更直接的部署依据。

内部`control_access`是另一类边界。控件借C++的friend规则允许受控的内部访问桥操作少数状态，SDK内部得以执行必要操作，应用仍只看到面向业务的属性、集合、事件和派生扩展点。这里的权限是编译时类访问规则，与Engine端鉴权、窗口编号或TCP连通性无关。业务若要改变文本框内容，调用公开setter或写Python属性即可，编辑器、捕获和绘图缓存仍由各自对象管理。

## 3.理解一次C++事件的订阅、快照和派发

`event_signal<source_type, argument_type_list...>`把发送对象与载荷类型作为模板参数。内部保存的条目含token和`std::function<void(source_type &, argument_type_list &...)>`。多数控件事件借助通用别名`event_container<argument_type_list...>`，将发送者固定为`control_base`。因此它们常用`control_base &`作为发送者以及一个强类型参数引用。模板实例化时编译器已知道关闭前允许写哪个字段、文本输入提供哪个字符串。若把只能接收键事件的处理器绑到普通点击，错误会在C++调用处被发现。

订阅时`add()`检查函数有效，给它分配编号，并按注册顺序追加。`+=`同样可订阅，需要事后精准移除时用`add()`保留编号，再调用`remove(token)`。派发的`call()`先复制回调列表，再按顺序执行这份快照。于是一个回调中增加另一个回调，通常在下次派发才可见。同样，在正在执行的快照里移除后面的回调，不会改写这次已复制的内容。输入组件还使用带生命周期检查的派发路径，在所属对象失效时停止继续派发。

快照带来一个容易忽视的C++细节。若可变lambda按值捕获普通整数，该捕获跟着其`std::function`被复制，修改本次快照里lambda的字段未必会积累到保存的订阅。要实现持久计数，可以让业务实例保存计数，或在明确生存期的共享状态中保存值。回调只负责从拥有者取得当前状态并提交修改。应用对每次触发的状态和对长时间业务状态由此能自然分开。

各回调看到的是同一个当前载荷的引用。比如第一个关闭处理器发现有未保存的数据，把`cancel`改为真。后面的处理器仍可读取这个决定。最后由发布关闭请求的代码读取最终值，决定是否继续。这和快照不冲突，快照保护的是回调列表，传给每一个回调的参数仍代表同一次事件。类似地，键、文本、指针和滚动的`handled`由发布者按事件语义解释。

## 4.十九种派生参数和空基类

普通点击、加载和许多属性专属的改变事件不需要附加值，使用空结构`event_args_t`。其余十九种参数公开继承它。日志工具可接受`const event_args_t &`表达“任意事件载荷”，而处理关闭的函数可直接接受`cancel_event_args_t &`。基类没有虚函数和数据成员，符合空基类优化适用的形状，通常不会迫使派生对象再为它单独留一个字节。派生对象的大小仍由自身字段及对齐决定，独立构造一个空基类对象也仍有非零大小。

继承带来的是一个统一的类型关系。把派生对象绑定到基类引用时，还可以继续以原有派生引用访问它的真实字段。把派生对象复制到基类值里只会保留基类部分。空基类不提供动态识别或虚函数分派，具体回调依旧直接选正确的派生类型。`cancel_event_args_t{}`由默认值获得`cancel=false`。在C++20聚合初始化中写`cancel_event_args_t{{}, true}`，第一个`{}`初始化空基类。

|派生类型|载荷|
|---|---|
|`cancel_event_args_t`|`cancel`，关闭可取消决定|
|`key_event_args_t`|`key`、Shift、Ctrl、Alt、Meta与`handled`|
|`text_input_event_args_t`|输入文字与`handled`|
|`pointer_event_args_t`|左右手、窗口和局部坐标、有效位置、修饰键、捕获、取消与处理状态|
|`scroll_event_args_t`|左右手、`delta_x`、`delta_y`、`handled`|
|`interaction_end_event_args_t`|`cancelled`，用于标识正常完成或取消|
|`property_changed_event_args_t`|`property_name`，需要新值时按公开属性自行读取|
|`control_collection_event_args_t`|控件指针与索引|
|`menu_item_event_args_t`|菜单项指针与索引|
|`tabpage_event_args_t`|页签页指针与索引|
|`listview_column_event_args_t`|由`shared_ptr`持有的列与索引|
|`listview_item_event_args_t`|由`shared_ptr`持有的项目与索引|
|`grid_column_event_args_t`|列索引与宽度|
|`grid_cell_event_args_t`|行、列及编辑错误字段|
|`tree_node_event_args_t`|树节点指针|
|`render_error_event_args_t`|渲染错误消息|
|`controller_event_args_t`|左右手、扳机、侧握、摇杆轴与按钮状态|
|`global_pointer_event_args_t`|左右手、全局手柄按键（`trigger/grip/joystick/primary/secondary`）及Unix毫秒时间戳|
|`control_input_event_args_t`|派生扩展使用的输入种类、位置、键、文本与相关状态|

返回对象的事件与仅通知变化的事件所需的参数不同。表格失败事件可以给出出错单元格，通用属性事件只提供名字。事件携带控件指针时，它仍是进程内的对象表示，与协议中标识一个窗口的数字是两种数据。把它理解为处理器执行时可访问的实体，有助于避免将内部引用错误写进传输或文件。

## 5.Python扩展怎样接住原生类型和事件

### 两个处理器之间的值如何流动

假设在一个关闭事件上先绑定Python处理器P，再绑定另一个处理器Q。原生初始载荷可以记成`E0={cancel:false}`。进入P时，绑定用原生载荷构建一个独立持有的参数对象，等价于将此时的值复制给`P0`。P设置`cancel`后，返回时把`P0`的可改状态复制回原生的同一载荷。Q开始派发时取得的就是已经更新的`E1`。如果Q也为Python处理器，它会从`E1`建立自己的参数对象。源码还在异常分支复制修改后再把异常抛出。调用方是否继续派发要由异常路径决定，不能把异常后的复制理解为继续正常触发其他回调。

把这套过程和C++处理器比较，C++处理器直接得到一个载荷引用。Python包装承担语言对象的寿命和解释器同步。两边写入的业务目的相同，内存管理方式各自适合语言。对这些派发参数，立即在回调内读写既能保留本次事件语义，也防止误将引用闭包留到另一线程。调试时可先在第一个处理器设值，再在第二个打印接收到的字段。看到它随派发改变，就验证了传递路径而无需启动一个耗时的后台动作。

事件桥还把发送者作为独立参数传给Python。例如同一个业务函数可绑定四个按钮，从`source.name`或对象身份判断哪一个被点击。事件字段则表达同一次动作里特有的数据。鼠标或激光坐标属于参数，控件公开名字属于发送者。将这两者写成单一通用字典会让每次使用都要临时猜字段和值类型，强类型适配把这些选择提前到注册和绑定定义。

Python使用公开的`easyvrui`包。`engine_interface_native*.pyd`通过pybind11显式绑定构造函数、方法、属性和对象容器。原生`get_text()`和`set_text()`可合成为Python的`text`属性。集合支持Python的迭代、下标和`len`，数据保存在原生对象中。安装后的包和扩展位于同一`sdk/api/python/`目录，载入失败时先检查解释器及模块搜索路径，再检查Engine连接。

C++的十九种派生载荷也以对应的Python类型继承`event_args`（其中全局手柄事件保留`global_pointer_event_args_t`名称）。`issubclass(easyvrui.cancel_event_args, easyvrui.event_args)`成立。实际写事件时，在`on_closing`处理器中只需按约定设置`event.cancel = True`。Python绑定会将原生事件适配为Python处理器可用的对象，回调结束时把修改送回C++逻辑，再传播可能发生的异常。保留一个回调入参并在未来改动它，不会重新启动已经完成的关闭或重算过去的输入决定。

锁在这里有两种不同职责。GIL协调解释器对象访问。UI线程归属保证控件树的操作顺序。Python调用原生`run()`和阻塞`show_dialog()`时可释放GIL，事件桥需要执行Python回调时再取得GIL。即便后台线程已取得GIL，从那里直接改另一个线程创建的控件也不满足控件归属。正确的做法是投递一项任务给控件的拥有者线程，由任务在回调内更新原生控件。

事件桥与虚函数桥的入口也不同。普通`button.on_click += handler`订阅一个业务动作。原生派生行为则通过trampoline寻找Python重写，必要时进入`python_override_support`的重写作用域。没有相应重写时沿原生实现运行。遇到业务按钮需要加一，可以订阅事件。要做一个自定义画布，才需要考虑经过绑定开放的控件派生点。两条路径最后都能在同一控件树内工作。

## 6.从登记、显示到关闭理解对象保活

`object_map`首先是按对象ID查找地址的索引。`ui_runtime::register_object()`可以用从空`shared_ptr`别名构造的非拥有入口登记对象。入口能找到地址，却不会为栈对象建出一套新的所有权。运行时查找窗口、普通控件和容器时，会尝试`weak_from_this().lock()`。如果对象确实有活着的共享控制块，就临时取得拥有引用。若实例由栈持有，程序仍需在外层作用域保证它活着。

显示由共享指针管理的窗口时，运行时会把`object_map`中的对应入口更新为拥有引用，使已显示的窗口不会在局部变量离开作用域时意外消失。关闭窗口后移除它的活动记录，并把索引恢复为非拥有入口。应用如果还要在这时读取对话框控件，应持有自己的共享引用或对应的Python实例。关闭服务窗面、停止参与事件循环，以及销毁原生对象，是三个可独立发生的步骤。

从集合访问控件也需分清是否持有对象。容器可以通过注册的共享对象保留其成员，临时查找得到的引用仍要尊重该对象的生命周期。集合事件里的指针宜在回调内当场使用。若要跨回调缓存一个对象，可按实际API取得适合的所有权，或保存可重新查询的业务标识，并重新检查对象是否仍有效。用一个裸指针保存旧控件，再删除整页并等待后台使用那个指针，会让对象寿命脱离可判定范围。

投递回调同样需要判断寿命。`control_base::begin_invoke()`交给线程所属的调度入口。内部`connection::post()`在短锁内更新`callback_list`并唤醒线程。`get_dispatcher()`返回捕获实现弱引用的函数，当目标实现还在且接受投递时才安排回调。这种弱持有避免后台任务仅因保存分发句柄而延长整个连接的寿命。任务本身若捕获了已销毁对象的裸引用，调度器仍无法替业务延长该对象的寿命。

可以想象后台加载一个较大的记录集。这项工作先完成解析，把结果放进清楚拥有的对象，再投递一项UI更新。逐行投递容易让大量排队操作与输入相互争抢。由UI线程应用一批完成的数据，可在一个连续区间内建立布局。若用户关窗，回调可检测预期目标是否仍有效。这项判断属于业务生命期判断，也因此可以仅在真正需要的地方进行。

## 7.窗体设计文件的树及校验

`.easyvruifrm`是设计期JSON。顶层记录`format`、`next_key`和`root`。各节点记录`key`、`type`、`name`、`property_map`、`collection_name`及`child_list`。不同类型可有附属集合，比如工具栏按钮、树节点或表格的列与行。数据保存的是重新构造窗体所需的布局和属性。运行时控件内部的捕获、滚动、待发送缓存及本机地址留在内存。

下面是没有子控件的窗体文档结构。程序名为`counter`时，文件可以命名`counter.easyvruifrm`。真实属性需要符合其所有控件的声明类型。

```json
{
    "format": "easyvruifrm",
    "next_key": 2,
    "root":
    {
        "key": 1,
        "type": "window",
        "name": "counter",
        "property_map": {},
        "collection_name": "control_list",
        "child_list": []
    }
}
```

`key`给设计器一个文档内的稳定识别点。`name`在导出后还要成为编程成员名。导出器检查目标标识符是否合法、是否和同一窗体其他成员重名、是否使用保留字或与窗口属性冲突。给标签取名`label_count`能从构造、属性编辑、生成代码和业务引用几个位置认出同一个角色。按钮搬进一个新容器时，节点位置改变但名称可以保留。重命名则应同步改用引用它的业务代码。

设计器的控件注册和属性模式为编解码、编辑器和生成器提供可编辑字段、值类型及所需setter（包含`rich_label`的富文本片段及`datetime_selector`的`YYYY-MM-DD HH:MM:SS`或`null`日期时间值）。比如有父容器时会判断可接受的子类型。表格列宽需要有效值。某些属性必须先于另一些初始化，导出器会按声明阶段排序。理解这一点后，若预览与导出不同，可逐项对照“文件声明”“构造顺序”“运行对象值”，不用把所有问题归到JSON格式。

## 8.生成类与业务类怎样组合

### 从文件到成员声明，逐步沿生成器读取

假设根窗体名为`counter`，里面有一个标签和一个按钮。设计文档的根节点与两个子节点各有自己的`key`，两个实际控件使用`label_count`和`button_add`作为名字。生成器先遍历校验并建立内部节点表，记下父节点编号、目标类型和将用于输出的标识符。这一步避免在输出构造函数写到一半时才发现父子关系不存在。内部表中的键用来解析设计文件中的引用，输出代码则用有意义的成员名称标明访问路径。

以C++普通导出为例，第一遍生成成员声明与构造语句。一个标签对应`std::shared_ptr<easyvrui::label> label_count`，构造时使用`std::make_shared`创建对象。第二遍生成挂接，把控件加入父节点的`get_control_list().add(...)`。第三遍生成元数据和属性赋值。Python采用同样的遍历阶段，前一遍编写`self.label_count = easyvrui.label(...)`，挂接阶段写成`control_list.add(...)`，最后写属性。把创建和挂接分开有理由。同一窗体中有些属性或元数据可能引用另一对象，即使后者在树中靠后，也可以先建立全部实例。

对于页面，生成器在`render_attachment()`中依照`collection_name`选择`page_list`或`control_list`。对于菜单和工具栏，特有内容还会走相应的挂接与初始化逻辑。表格也有两种常见模型。`listview`的列和项目是公开集合中的活对象，`grid`使用行列以及单元格数据。两者可能看起来都有表头和网格区域，但设计时必须根据各自的数据模式导出。若给前者写后者的行结构，即使能够在JSON文本里拼出字段，也没有正确的运行时语义。

导出图标和图像时，设计文档提供构造所需的原数据，导出器会为相应资源写出文件，生成代码引用自己能找到的路径。要把产物复制到另一目录使用，应把构建实际需要的生成文件与资源一并处理。判断导出是否等价时也要验证资源实际加载，看到字段非空不足以证明运行时能从该路径解码出图像。这里的独立资源文件与应用清单里的图标用途也不同。一个给窗体内部构造用，一个供Desktop等启动器显示应用项目。

可继续手算挂接顺序。若A是根窗，B是页签容器，C是页，D是按钮，阶段一完成后四个对象都存在，但它们还没有完整的父子关系。阶段二把B加入A，把C加入B的页面集合，再把D放入C。阶段三设置文本和几何，随后业务可以引用D。若把阶段二的C错误挂入A，编译和绑定仍可能成功，但切换页签时D不会按预期随页面隐藏。验证实际树关系比仅数代码行更有效。

`design_exporter.cpp`根据窗体描述生成构造代码，布局文件与布局类名统一附加`_ui`后缀（已有`_ui`后缀时保留单个后缀）。当前C++菜单导出在同一目录写`<窗体名>_ui.h`与`<窗体名>_ui.cpp`（如`counter_ui.h/.cpp`），头里放窗口类与公开控件成员，实现里放构造函数；Python导出为`<窗体名>_ui.py`，生成类型的`__init__`建立控件、应用属性及加入集合。导出器也提供完整项目选项，可输出无后缀业务子类、入口、清单及配套工程文件。查找生成结果时，要分别看实际的类声明和编译时需加入的实现文件。

生成类型自身需要继承`window`才能使用窗体功能。业务层组合持有这个生成实例，在初始化时创建它，再用`ui->button_add`或`ui.button_add`绑定业务方法。计数、持久化和后台任务由业务类管理，构造出的容器、按钮和标签由生成窗体提供。这就允许重生成布局时保留业务实现。若改动删除或更名成员，编译错误或属性访问错误会准确指向业务需要更新的引用。

一个具有页签的窗体可以说明构造顺序为何重要。根窗体包含`tabcontrol`，两个`tabpage`属于它的`page_list`，每个页面的按钮加入页面的`control_list`。如果把所有控件直接加入根窗体，它们即使仍显示在相同坐标，也失去了页签切换时相应的可见与焦点关系。生成器选择对应集合进行挂接，它产生的是一棵真实控件树。这组操作由同一设计在两种语言中映射到等价的公开接口。

组合也方便分开测试。先直接构造生成类型，验证成员存在、几何与被挂接位置合理。再让业务类接管实例，验证按钮点击后的业务状态。最后在应用运行时检查窗口与Engine的完整交互。布局更改时只需调整前两个实验中受影响的断言。两端的API边界详见[第03章](./03_ipc_tls_protocol.md)，带有模态行为时的回调与生命周期见[第04章](./04_session_and_context.md)。

## 9.用组合实例化验证端到端调用

下面示意项目已有设计器生成的`counter_ui`，它提供`button_add`和`label_count`。业务类的生命周期覆盖`easyvrui.run()`。处理器由生成对象的具体成员触发，业务不需要复制它的界面构造语句。实例化、绑定、显示是程序中三个可以分别观察的步骤。

```python
import easyvrui
from counter_ui import counter_ui

class counter_application:
    def __init__(self):
        self.ui = counter_ui()
        self.count = 0
        self.ui.button_add.on_click += self.button_add_click

    def button_add_click(self, source, event):
        self.count += 1
        self.ui.label_count.text = str(self.count)

def run_counter():
    easyvrui.set_application_name("计数器")
    application = counter_application()
    application.ui.show()
    easyvrui.run("计数器")
```

这里的`run_counter()`驱动当前调用线程创建的窗口。第一次点击之后，`count`属于持续存在的业务实例，第二次点击从上次值继续。生成的`label_count`由窗体及控件集合持有，回调写入它时已处于拥有者线程。换成C++时，可让业务类持有`std::shared_ptr<counter_ui>`，在事件lambda里调用业务成员方法。业务对象需比持有裸指针访问它的回调活得更久。若控件可能独立于业务对象存在，则应在恰当的阶段移除订阅，或按实际所有权从弱引用尝试取得业务实例。

完整项目导出另有输出业务脚手架的选项，现有模板可能给出一个继承生成类的空壳并保留用户文件。教程的业务示例采用组合，普通导出的生成构造仍能直接使用。读到生成类中的默认窗口名时，也可以从构造函数传不同的实例名，以保留同一界面设计的多个实例。此处实例名和进程的应用会话名分别用作窗口与会话标识，设置其中一个不会重命名另一个。两个不同工作流可以使用同一设计文件和控件树，进入运行阶段后会话、窗面和应用业务状态仍按前面的规则分工。

重生成之后可逐层验证三个断言。第一，`button_add`确实在该窗体成员和应属父集合里。第二，模拟或实际点击调用业务方法，数字写进本地标签。第三，Engine收到提交并显示对应数字。第一项失败查文档或生成器，第二项失败查绑定与焦点，第三项失败查提交、图形或连接。按这三层做回归，它们即使在一起运行也能给出清楚的故障起点。

### 关闭事件如何返回给原生调用者

在计数器基础上加入“保存以后才可以关闭”的行为，最直接的做法是订阅`on_closing`。状态如果未保存，就把本轮事件的`cancel`设为真。如果用户已经保存，让下一次关闭进入正常路径。每一次关闭首先创建新的事件载荷，旧的布尔值不会带到下一次关闭。若想在回调中显示询问，可结合模态所有者关系与对象销毁阶段评估调用位置。已经进入关闭或不可交互状态的窗口可以让特定owner校验失败，确定交互场景后按[第04章](./04_session_and_context.md)的条件选择合适入口。

C++侧的对应实验是给信号添加一项回调，在下一次派发前用token移除它。这个token只属于当前事件信号的管理逻辑，不应写入窗体文件，也不应传给另一个信号移除。Python侧则可用对应回调对象移除，尤其是需要拆卸长期挂接的业务模块时。事件名单、窗体内容、输入焦点与业务计数的有效期各不相同，把它们存在合适的对象中，重开一个窗口时便能清楚决定哪些状态要清零。

### 如何识别连接错误与绑定错误

编译或导入时找不到类，先验证公开接口、模块路径和二进制配套情况。创建控件时若属性类型不合适，通常会在本地构造或赋值时报错。已显示的窗口稍后因连接断开失效，则错误发生在对象成功创建之后，需去看会话和传输层。把相同设计导出两种语言后，可先在本地读取值来确认构造是否一致，再分别连接同一个服务观察接入现象。这种对照不要求修改协议，能把同一次故障定位到生成、绑定、原生运行时或服务中的具体一层。

另一个常见误解是某些渲染回调进入Python就意味着所有构造和渲染操作都会进解释器。默认原生控件的内建行为就运行在C++实现中，只有确实绑定的Python回调或派生重写需要语言桥。性能测试应固定窗面大小、节点量和业务操作次数，区分构造、事件、绘制记录与传输四段。若只让Python业务回调做一次短赋值，真正的热点可能在文本测量或远程提交等待。若业务在每帧自定义绘制大量细小图元，绑定转换的次数才会根据调用量增加。即便使用同一个SDK后端，应用组织代码的方式也会改变运行成本。
