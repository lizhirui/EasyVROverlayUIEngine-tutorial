# Engine, SDK, and Application Architecture

When a button is clicked in the headset, at least three things need to happen. First, the controller's pose is converted into a ray and the window surface is found. Then, the coordinates on the window surface are passed to a button, and finally, the new button's appearance is displayed. The first step requires knowing all the interactive windows in the space. The second step requires understanding the application-defined layout and business logic. The third step involves sending the screen to SteamVR. EasyVROverlayUIEngine uses different objects to represent these three actions and clearly defines who owns each object.

The entire example is based on a counter. It has a digital display `label` and a one-up increment `button`. Imagine it appearing alongside a desktop and a virtual keyboard in the headset. After reading through these four layers, you can explain why changing just one line of Python properties can update the screen, why other windows remain after an application exits, and why it’s important to determine where the failure occurred when startup fails.

## 1. First, distinguish between processes, libraries, and objects

Processes have independent address spaces. Pointers in Application A only point to memory in the process where Application A is located. Even if an object in Application B has the same address number, there is no connection between them. Within a process, member functions can be called directly, object properties can be read, and callbacks can be executed. When crossing processes, both ends must agree on meaningful message fields, which are transmitted through the operating system, and the receiving end interprets the fields into its own objects.

Libraries are loaded and used by processes. Code in static libraries usually enters the executable file or extension module during linking. Dynamic libraries are loaded into the process during program execution and provide implementation through exported symbols. The C++ counter and the Python counter run in their own processes. Linking the same native library does not allow both to share control objects. Even though Windows allows multiple processes to share a portion of the read-only code page, control instances, callback lists, thread states, and memory ownership remain independent in each process.

Objects are instances with state and behavior. The button object in this example knows its own rectangle, text, availability, and the event handler function to execute when clicked. The window object in Engine knows the window's size, visibility, spatial reference, and drawing nodes. They are in different processes and solve different problems. Two buttons can be drawn on the same window, and the window can be completely customized by the application. Only the application knows whether clicking the right side represents an increment, closing, or clearing.

From this, the four layers can be read based on the running position.

|Layer|Location|Work in the counter example|
|---|---|---|
|Independent application|Counter process|Create windows, labels, buttons, subscribe to clicks, and modify counts|
|Language access layer|Same counter process|The C++ header file provides declarations and types, and the Python extension connects properties and callbacks to native objects|
|`engine_interface`|Same counter process|Maintain the native control tree, focus, drawing command cache, and client connection|
|Engine|Independent service process|Unified handling of VR input, window state, GPU rendering, and OpenVR submission|

The first two columns of this table are important. When reading "SDK received click," it means the SDK in the counter process receives window events through the connection. When reading "Engine redrawn window," it means the service process re-grayscales previously submitted drawing commands. Both ends have a state that can be independently viewed and debugged.

## 2. Why does Engine centrally manage space and graphics resources

SteamVR sees multiple windows floating in space, while the application usually sees only a two-dimensional control tree. By having the headset, controller, and windows in the same space manager, Engine can use the same tracking pose to compare distances between multiple windows, check whether windows are currently visible, available, and interactable with the controller, and decide which session the event should be sent to. For example, if Window A is 0.7 meters from the ray start point and Window B is 0.9 meters from the ray start point, a normal hit first considers the closer effective intersection point. If the controller is dragging a control in B, the captured state can continue to send subsequent events to B. Any single application cannot make this cross-window judgment based solely on its own tree.

Graphic resources also have specific owners. Direct3D devices, textures, Direct2D device contexts, and the Overlay handle registered with SteamVR are all on the service process side. When the Engine starts, it obtains DXGI adapter information through OpenVR and uses that adapter to establish the graphics backend. Assigning texture creation, updating, submission, and release to a single process allows for unified handling of texture size, window closing, device errors, and the lifecycle of OpenVR operations. When an application draws a solid-colored rectangle, it only needs to submit the logical coordinates and color of the rectangle, without needing to pass a texture pointer that is only known to the sending process.

For example, a BGRA window with dimensions of 1000 pixels wide and 600 pixels high requires at least 2,400,000 bytes of texture pixel data. The commands needed to change the value from `9` to `10` are usually much smaller. The actual transfer amount is also affected by node commands, image payloads, and batch fields, while the display amount is influenced by resource caching, background rendering targets, and driver allocation. The key benefit of centralizing GPU ownership is having control over where these costs occur. The counter only tracks its own control and command memory, with the Engine responsible for the growth and recycling of windows and textures.

A single service does not mean that all work is squeezed into one thread. `engine_host` is responsible for SteamVR frame synchronization, tracking, and display updates, while IPC access has its own asynchronous network work, and low-level keyboard hooks use independent message loops. When network requests and rendering frames may access the same service runtime, `engine_host.cpp` protects the corresponding access with `runtime_mutex`. Service threads are important clues for fault location, but resource ownership is still maintained by processes and classes. Applications with work threads must also follow the ownership of their control threads.

Centralizing ownership also comes with clear costs to bear. There is an increase in serialization and one-way message exchanges between applications and the Engine, and the Engine is also a common dependency for multiple applications. Large amounts of drawing data, blocking service processing, or shared GPU failures may affect other windows. Reducing submission amounts through node differences, limiting input destinations with current window hit and focus rules, and restricting cleanup scope with session ownership address the issues of communication volume, interaction ownership, and resource recycling. Chapter [05,](./05_rendering_pipeline.md), further explains the timing differences between submission confirmation and the actual display.

## 3. Why do native libraries maintain the same set of control trees?

In C++ applications, `button`, `label`, and `window` are native objects. In Python applications, names like `easyvrui.button` reach the same native class through compiled extensions. Setting button text enters the corresponding native property logic. Only the Python callbacks provided by the application and derived classes' rewrites require a return to Python. Thus, the layout, focus rules, menu selection, text editing, and repainting of default controls only require one set of implementations to be maintained.

For example, changing the counter to support tab movement for focus. Both C++ and the Python example set `tab_index` on the same control. The control order and the judgment of visible, available, and focusable states are completed during SDK runtime. Python provides an integer, and the binding is responsible for type conversion. If you see different behaviors in the same scenario across languages, first rule out differences in the window tree, data values, event bindings, or storage, then check binding conversions.

Native libraries separate the local state of interface objects from the cross-process state passed to the Engine. After assigning a value to a label, the application can immediately read the same label to get the new value. Rendering then discovers that the corresponding object needs to reissue commands and sends the difference to the Engine at the submission point. The saving of properties is done by the object itself, so a continuous set of callbacks for text, color, and title settings can be updated multiple times locally without automatically sending a network request for each property read/write.

This design also leaves room for expansion. Composition is a direct method, such as using panels, text boxes, and buttons to create a counter. Derivation can be used to implement custom drawing or input behaviors, subject to open or protected extension points in various languages. Regardless of the method used, the output still must follow the drawing protocol understood by the Engine. Registering a Python class in the application process and adding a native drawing command to the Engine are two different types of extensions.

`ui_runtime` organizes the control root window, focus, and client connection. On the regular application side, when creating controls, the thread to which they belong is recorded. The program can be driven by `run()` for message loops or explicitly by `pump()`. After the business work thread generates data, it delivers the updates to the UI thread through the appropriate public scheduling entry. Taking a counter as an example, the network work thread can generate new counts, and the actual action of writing to the `label` property is placed in the UI thread callback. This arrangement ensures that numerical calculations and rendering take place in the same thread in sequence, avoiding the application from establishing additional concurrent protocols for each control.

## 4. Dependency direction of language access and application deployment

The C++ access layer provides `easyvrui.h` and category header files. The source code includes header file compilation, and the object code links to the SDK's static libraries or DLL import libraries. The header files tell the compiler about the object layout and function signatures, while the libraries provide the executable implementation. Installed applications do not need to copy `engine_interface/src` and compile their implementation files one by one. When choosing a DLL, it is necessary to provide the DLL and corresponding runtime that match the import library with the program. The static method brings the library code into the final module, also connecting to the independent Engine through the network.

The Python access layer is divided into public `easyvrui` packages and native extensions `engine_interface_native*.pyd`. The installer centrally deploys the packages and static-linked extensions in `sdk/api/python/`. When starting a Python script through the SDK, the SDK preloads the directory and retains the existing `PYTHONPATH`. During direct runtime, the caller configures this directory. Module loading occurs before the discovery of the named pipe, TLS connection, and control submission. During troubleshooting, first check the actual import path, CPython version, and module architecture.

The running directory separates the Engine from the application. `bin/` stores the Engine, SteamVR action resources, and configurations, while `app/` follows the application directory layout in the source code. The Engine uses relative paths in `bin/config.json` to start the Desktop and input components. The Desktop finds the built-in application script from `app/desktop/config.json`, which then locates the program entry according to its own directory. Each component embeds the built-in language package into its own binary.

Conversely, even after successfully importing the SDK, the application may still fail to connect. For example, if the SDK receives the wrong service public key fingerprint, the network may be connected, but the TLS identity check will report an error. Another example is that although the application has been authenticated and can perform management operations, the window does not display. In this case, check `show()`, the application message loop, `present` response, and the rendering status of the Engine. Test "can be stored in the database," "can access the session," and "can be displayed on the headset" separately to quickly narrow down the cause.

From the source code directory, one can also see the differences between two-way communication and one-way construction dependencies. The Engine and SDK each have their own protocol handling and Windows IPC drivers. They interact through pre-agreed messages and do not include each other's implementation files in their products. On the Engine side, multiple sessions are accessed, requests are received, and shared runtime is operated. On the client side, a discovered service is connected, and received events and asynchronous results are arranged in the local UI thread. Running data can flow bidirectionally, but the construction boundaries remain clear.

|Source code location|Issues suitable for tracking|
|---|---|
|`repo/engine/src/core`|Which windows are under the session name, which window is the current one, and how the input area status is switched|
|`repo/engine/src/driver/ipc`|How the discovery pipeline, TCP access, TLS server, and session transmission work|
|`repo/engine/src/driver/graphics` and `driver/steamvr`|How textures are created and submitted, and how controllers and spatial poses are sampled|
|`repo/sdk/engine_interface/src/easyvrui`|How controls, windows, event distribution, command recording, and submission work|
|`repo/sdk/engine_interface/src/driver/ipc`|How the client discovers services, connects, and transmits frames|
|`repo/sdk/api/cpp` and `repo/sdk/api/python`|How the interface visible to the caller and the conversion between Python values and native values are handled|
|`repo/app`|How applications such as Desktop, input components, and designers use the same public boundary|

## 5. From startup to obtaining a session

The local path is understood first from the running service. The Engine holds single-instance coordination resources, then initializes SteamVR, graphics devices, Overlay management, and service runtime. It establishes `ipc_server` in `engine_host::initialize()`, loads the configured listening port and access credentials, and prepares to start listening after a callback. The default port is 49537. The actual port is published by Bootstrap after the service is ready. The process of reading the port is called discovery. Here, “negotiation” refers to the client obtaining the selected port of the service; once the connection is established, no other data port will be used.

On the local machine, the SDK obtains descriptions through `\\.\pipe\EasyVROverlayUIEngine.Bootstrap`. It receives the protocol version, service process number, listening port, access credentials, and public key fingerprint, and then establishes a loopback TCP connection. The named pipe is responsible for delivering small connection materials, while actual control drawing and data input pass through TCP/TLS. Separating files, pipes, and ports is practical; `config.json` belongs to Engine configuration, Bootstrap to the active service entry, and TCP to the long-term connection data entry.

If the SDK does not discover the service, the local client can attempt to start the Engine and discover it again according to the implementation. `EASYVRUI_ENGINE` is used to specify the local Engine executable file path; it is not a credential environment variable. Remote clients provide connection materials through `--easyvrui-host=值`, `--easyvrui-port=值`, `--easyvrui-access-credential=值`, and `--easyvrui-public-key-fingerprint=值`, with default values used when the port is omitted. Remote addresses and credentials must come from pre-trusted configurations. Just being able to reach the listening endpoint means the network can connect; server identity and client access qualifications still need to be verified separately.

TLS is responsible for encrypted transmission and allowing the SDK to verify the server public key fingerprint. The protocol authentication uses random challenges from both ends and shared credentials to prove the client's access qualification. After success, `welcome` provides session identifiers and tokens. Both are used in subsequent requests, allowing the service to associate data with the same authenticated connection. A application window number is only interpreted within its session. `window=7` in Session A and `window=7` in Session B can exist simultaneously, and the Engine distinguishes them through the mapping of sessions to the global surface. They can use the same title or layout, and their states remain independent of each other.

The troubleshooting sequence is to first confirm that the Engine process can complete initialization, then check if Bootstrap can return a description, then examine TCP and TLS, and finally see if `welcome` has been obtained. If the engine fails to obtain the OpenVR interface, simply retrying TCP will not make the graphics backend ready. If the port is correct but the public key does not match, changing the application name will not solve the identity verification issue. If a session has been accessed but no windows have been submitted, re-generating the certificate has no reason to change the program's drawing process. Chapter [, Section 03,](./03_ipc_tls_protocol.md), will detail the sequence of each layer of inspection.

## 6. Follow the first show up to a frame in the headset.

Now execute the `show()` of the counter. First, change the window to the pending display state locally. The SDK tracks the object records and visible states of the window during runtime, then collects window properties and nodes that need redrawing. The initial submission requires the Engine to understand sufficient window metadata and drawing order. After parsing `present`, the Engine associates its window records with the current session and window number, verifying layout-related fields, drawing instructions, and involved resources. If the Engine determines the initial position, the response can also return calculated transformations, and the SDK synchronizes the locally observable state accordingly.

Understanding the window as a “two-dimensional content space surface” helps distinguish window properties. The layout rectangle describes how controls are arranged on the two-dimensional canvas. The window physical ratio converts logical pixels to meters. The reference mode determines which tracking object is updated, and position and rotation determine the transformation of the window surface in the reference coordinate system. D3D textures store two-dimensional pixels. Surface display is achieved through Overlay space parameters and corresponding hit geometry; when applying a rectangle, the window logical coordinates are still transmitted.

The Engine chooses when to redraw the texture based on dirty state, and then submits pose and texture through Overlay. SteamVR can continuously synthesize the last submitted texture, and head rotation also affects the perspective relationship seen by the user. Conversely, when an application has only one static label, the SDK does not need to re-run the label rendering every time the headset is refreshed. Space pose updates, GPU redraws, and application event loops are tasks with different rhythms.

After the program writes the number `10`, a log line is immediately output stating “Tag value updated”. When the log is displayed, the new value must already be present in memory. Whether the headset shows `10` depends on SDK recording, IPC submission, Engine rendering, and SteamVR synthesis. To verify end-to-end latency, time points can be assigned to attribute changes, submission, service reception, and texture updates, then the difference between each segment can be calculated. This helps determine if the bottleneck lies in application callbacks, submission backlog, rasterization, or headset rendering.

## 7. From trigger to button callback, then back to pixels

The press and release of the right trigger are sampled by Engine from the VR input source. Engine saves each hit and capture, calculates the window coordinates on the target window, and sends events indicating the window and pointer state to the target session. Events only reach the window level. The application’s SDK uses its own tree, control coordinates, and internal interaction rules to determine if the button was pressed.

The callback for button clicks is executed on the application UI thread. During execution, the count can be updated, or another window can be displayed based on conditions. The system also handles final actions. For example, after the trigger is pressed, if the laser leaves the button, the application should decide whether this counts as a click based on button semantics. Similarly, when the scroll bar is dragged and the ray exits the window, Engine can continue to send events to the original window, with the SDK determining which control receives them. Receiving messages and processing business are two separate causal chains.

The keyboard and laser share the concept of the current application window in space. Clicking on a regular window can change the Engine’s current window. Keyboard assignments go to the corresponding session, and then the SDK selects the focus control within that window. When clicking on the auxiliary surface of an input component, Engine can maintain the original application window as the input target. Components have their own interactions and rendering, so clicking on keys on the virtual keyboard can change the keyboard’s appearance, and letters can also be sent to the original counter input box via IME. Chapter [, Section](./06_input_routing_and_drain.md), specifically discusses how to clean up the trailing parts of old work when switching input paths.

A single click can also trigger two different levels of changes. For example, if the application changes the window title from “Counter” to “Counter10”, the title is window metadata. Changing the label from `9` to `10` requires updating node rendering. Both can merge in the same submission batch. If only the window position moves, submission can mainly carry metadata changes, while content textures can continue to be reused. Understanding this difference helps explain why two operations seem to change the screen, but different resources are consumed.

## 8. How independent applications connect to these boundaries

Desktop is the launcher application. Desktop also has its own windows and sessions. The application name, icon, and launch method in the interface come from the `.easyvrui` list. The process that initiates the launch is parsed by the SDK on the local machine and creates child processes. Connecting Desktop to another machine’s Engine still launches the application on the machine where the Desktop process is located. The new application can connect to the same remote Engine through the transmitted connection information, creating new windows on the remote headset. Thus, “which machine creates the process” and “which Engine displays the window” are two independent issues.

The standard virtual keyboard is a layout application. It makes keys into a printable, interactive interface and reports logical key events through the input component interface. Chinese Pinyin, Japanese IME, etc., are also independent applications that manage combined content, candidate selections, and final submission. After registration, Engine knows that the session assumes the role of layout or IME, and can apply corresponding rules to windows, positioning, and input messages. When an ordinary application requests to open the input area, it only provides a window and a rectangle; how the component window is drawn is determined by each application.

Form Designer also runs on top of the SDK. It edits `.easyvruifrm` in its own window and previews the design, generating code for the running application to use the public control API. The designer’s property bar, object tree, and canvas are design-time views. Business code holds the generated form instance, uses public members to access controls, bind events, and drive the running window. Modifying a design file affects the re-exported interface structure, and business callbacks can be retained in the business class.

The Task Manager and File Manager are also located in the application layer. The former manages sessions and windows through management interfaces, with permissions determined by the service based on the connection identity and target. The latter enumerates the file system from the calling machine and can launch applications through a list. They use the same window and table controls, with their own business data and error handling kept in their own processes. Built-in applications connect to public capabilities through clear lists, configurations, and roles, and third-party applications can also use the same entry point.

## 9. Normal shutdown, process crash, and public service exit

When a counter window is normally closed, the SDK triggers the shutdown semantics, handles the interaction and visibility of the window, sends a shutdown request to the submitted window, and removes it from the active window list. If the application still holds the window object, it can continue to read the control properties allowed by the lifecycle. There are three different life cycles here. When an object is destroyed is determined by the application's reference. When a window disappears is determined by shutdown and service recycling. When the entire process ends is determined by the message loop and the application's other tasks.

After the last window is closed, a regular `run()` driver will end and perform the corresponding cleanup. The client will attempt to empty pending asynchronous operations and callbacks, then close the connection according to the runtime state. If the process exits suddenly, this proactive path may not be able to proceed. TCP disconnection, keepalive timeout, or the death of a verified local process can cause the service to detect that the connection is invalid. The `engine_host` disconnection callback removes the session state under the protection of the runtime lock and notifies the application table and Desktop tracking object.

There are several ownership issues to be addressed during resource recycling. A window belongs to the session that created it; releasing it requires clearing related successes and captures. If the session uses a regular application window, the current window and input path also need to be handled. If it plays the role of an input component, it is also necessary to revoke the eligibility to send invalid connections, then finalize according to the input routing rules or select available components. Another regular application window will not be deleted just because its number is the same; the search key includes the session ownership. Graphics resources and Overlay are cleared in the Engine side along with the removal of the associated surface.

The meaning of application crash isolation is thus very specific. Heap corruption in a counter usually stops at the counter process; the service only sees the connection disappear. A failure of the service process itself or the device that handles global rendering may affect all applications. Centralized ownership makes this common failure domain clearly visible, allowing unified implementation of service diagnostics and resource recovery strategies. When multiple applications disappear simultaneously, priority should be given to the common Engine, VR runtime, and device. If only one window disappears, first check its application process, session, and submitted records.

### SteamVR disconnection and automatic recovery

The Engine identifies SteamVR instances using `vrserver.exe`'s PID and creation time. When a normal exit event `VREvent_Quit` is received, the Engine first confirms the exit and then releases the OpenVR connection. Abnormal process exit, frame synchronization failure, or OpenVR connection failure also trigger disconnection handling. VR tracking is paused during this time, and the Engine continues to serve IPC, retaining existing applications, Desktops, layouts, and IME sessions, and saving the state of newly submitted windows.

After the old instance such as the Engine completely exits and a new instance is detected, OpenVR is reinitialized, action lists are loaded, graphics adapters are switched as needed, and Overlay and textures are rebuilt according to the latest window state. Window pose, curvature, and laser tracking are restored. During troubleshooting, the content of opened windows can be updated during SteamVR restart, and then the content of the restored window and session ID can be verified.

## 10. Verify your understanding with a timeline

### First, look at the failure along the three directions of data.

Assuming the counter can display windows, the labels will also change according to the timer, with the only problem being that a hand cannot hit it. The first successful display has proven that the application process can at least load the SDK, establish a connection, and submit valid commands for the current window. The timer can update the label, indicating that the SDK is still running. Now, what needs to be checked is the reverse link. First, ask whether the Engine receives the controller state and reference used for the pose of this hand, then check whether the window can be hit by this hand, whether another window is captured, and whether the return to the application's window coordinates falls within the button rectangle. With these time points, it is possible to distinguish between "no input generated," "routed to another window," and "arrived at this window but not hit the button."

If the opposite occurs, both counting windows suddenly stop displaying, yet logs can still be written. First, determine whether other applications under the same Engine also lose functionality. Common failures may indicate issues with graphics services, SteamVR rendering, or a combination of both. If the coordinates of one window are incorrect, it may still be visible, but out of sight. Logs can record transformations relative to the headset, reference objects, and submitted windows. If the application is large, verifying whether a single smallest window can be displayed with the same connection is faster than guessing the main application's graphics state. The smallest window shares the network, engine, and device with the original application, eliminating the need for complex controls.

There is also a local path from the work thread to the UI thread. For example, counting tasks continuously read data from files or devices, with background statistics faster than window rendering. Each task sends a network request, turning a situation that should only display the latest value into a queuing problem. The boundary between the SDK and the Engine allows for merging counts at the business layer before delivering new values. Only external actions that must be processed sequentially need to be retained. When troubleshooting delays, count the number of tasks entering the UI thread, the size of each submission, and the time spent waiting for confirmation over a certain period, rather than using the headset's refresh rate as the business thread's work frequency.

### Verify responsibilities using different observation objects.

To verify that "layout belongs to the application," place two custom command areas on the same window. The service will only report the hit window and its two-dimensional position. Replace the same area with two controls with focus semantics, with role differences interpreted by the SDK and application. To verify that "space belongs to the Engine," start two counter processes that know nothing about each other, place them at different distances, and observe that the service still determines which one to prioritize based on rays. To verify that "image and application rhythms are independent," keep one window static and slightly rotate it. The relative position of the window changes, but logs only show relevant spatial updates, not reassigning each label due to this rotation.

The same experiment applies in different machine modes. Place the second application on the client machine, and keep the original counter on the server machine. Both can still display together. When the client machine exits its application, the server machine's counter remains. Thus, the failure domain is not only determined by the programming language but also by operating system processes, device machines, and connections. Write these items in the debug record during deployment to reproduce the conditions of "where the program runs, where the windows are displayed, and who receives input."

The complete path of the counter can be written as the following five lines. The subject of each line is changed once, making it easy to compare logs, source code, and actual windows.

1. The application loads the language layer and native libraries, creating window objects, buttons, and labels.
2. The local SDK discovers the Engine, establishes TLS and sessions, and then submits the first batch of drawing commands for the declared window.
3. The Engine updates the session window and off-screen rendering, handing the texture and spatial state to SteamVR.
4. The Engine picks up the laser target, and the SDK passes the event of this window to the counter button in the application thread. The application modifies the label, and the next batch of differences returns to the Engine along the original path.
5. The application closes the window and exits the message loop. When the session ends, the Engine reuses resources still connected to it.

During practice, first duplicate this example into two processes with the same control name. Close one window and observe that the other can continue counting. Then set the labels in the same process twice, recording the read values, requests sent, and final images. The first experiment verifies the boundaries of IDs and sessions, and the second experiment verifies local objects and remote rendering states. Finally, replace the button callback with a modal window. This retains the four-layer process, only changing the local SDK scheduling and window interaction qualifications. See Chapter 04 of [for related mechanisms:](./04_session_and_context.md).

When reading the source code, you can read from the entry of `application.cpp` down to the code responsible for connection and submission in `ui_runtime_session.cpp`, then follow the protocol to find `engine_host.cpp` and `service_runtime.cpp` of the Engine. When encountering input components, continue from the input routing in the service runtime to the independent application. This way, starting from the operation and following the entire chain is easier to establish a verifiable mental model than guessing responsibilities based solely on directory names.
