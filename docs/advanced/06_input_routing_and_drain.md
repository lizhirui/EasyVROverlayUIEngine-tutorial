# 输入路由与串行排空

设你在窗口A的输入框里键入拼音，手柄已经点到窗口B，候选词却要过一小会儿才计算结束。这个候选最终应送给哪一个窗口？如果系统只在发送时读取“当前窗口”，这个词就可能落进B。如果立即停止旧输入法，A又可能丢掉用户已经按下确认键的结果。正确处理这件事需要给旧路线留下一个可完成工作的时间段，并给切换建立一个明确的边界。

本章先把窗口选择、控件焦点、键盘模式和输入区分开，再从两条输入链追踪到Engine的`input_router`。最后逐步推导串行排空的必要条件，包括按键释放、迟到结果、组件超时以及SDK在单线程内如何回到旧编辑器完成这一轮输入。

## 1.区分窗口、控件、输入区和输入组件

### “现在选中了什么”有两层答案

Engine维护窗口级的当前目标。手柄激光在Engine选中符合条件的窗口后，普通按键有一个可到达的拥有会话。`input_router::get_current_window_id()`还检查该表面存在、可见、可交互、具有有效空间位姿，并且属于可成为当前目标的普通窗口。如果这个窗口暂时失去跟踪，即使还记得它先前的ID，也没有一个可靠的新输入目的地。这一层只需要窗口和会话，从而可以服务不同应用及不同部件。

SDK收到发往窗口的事件后维护窗口内部的焦点。焦点可能在某个`textbox`、按钮、列表或网格的编辑器上。一个窗口可以有多个编辑器，但同一个时刻键盘事件要送给当前选中的控件。窗口A内从第一个输入框按`Tab`移动到第二个输入框，Engine看到的窗口可能仍是A。在切换成另一条编辑输入链时，SDK还要确保哪一个控件接收旧文本以及何时应用新焦点。把窗口选择等同于控件焦点，会遗漏这种“未换窗但目标已经换了”的情况。

窗口没有可用编辑器时，用户依然可以操作按钮或列表，接收`key_down/key_up`。进入文本编辑时，SDK才在合适条件下请求开启输入区。输入区是关联一个普通窗口的矩形，沿窗面逻辑像素描述。它让Engine知道辅助窗口显示在哪里，也标明当前输入链应当经过IME。文本缓冲、选区和光标由SDK控件与应用维护。用户看到的候选词、组合内容则由IME生成。输入区矩形相同也不意味着两个文本框指向同一业务对象，所以切换需要靠清晰的时序而非坐标比较猜测。

### 键盘模式决定从哪里输入

键盘模式有实体与虚拟两类。实体模式下，系统可从物理键盘接收按键并送入Engine。虚拟模式下，`layout`是显示键位并产生键盘事件的独立应用。`ime`是消费、加工或转发按键并提交文本的独立应用。两个部件的职责可以从换键盘布局来理解。把美国键盘换成别的布局改变的是按键位置、字符和修饰关系。把拼音换成日文IME改变的是如何把连续输入解释成最终文字。两项选择可以分别改变。

组件被选中和当前正在处理输入是两个不同状态。注册完成意味着某个会话有已确认的组件角色。被选作默认或当前组件意味着它可能在下一段输入中使用。只有当前存在有效目标，输入区开启，且路径需要该组件，它才实际为`active`。实体键盘模式下选好的虚拟键盘依然存在，但不会在这条路径参与输入。普通应用的IME选择还可以按会话维护，选择了哪一款IME要通过当前应用的会话查找。`input_router::refresh_route()`从当前窗口的会话取`get_selected_ime_session()`，当为虚拟键盘且IME有效时再取活跃`layout`会话。

可把完整状态记成四元组`(目标窗,输入矩形,键盘模式,活动组件)`。当某个量变化时，问两件事就够了。旧路线还可能产生什么输出？新路线在什么条件下可以开始？`hide_input_ui`改变输入矩形，切窗改变目标，`Pause`改变键盘模式，选择不同IME改变活动组件。这些动作的界面效果不同，但都可能要求旧路线先收尾。

## 2.完整路由从哪里开始，在哪里结束

### 输入区关闭时直接投递普通键

假设一个窗口中焦点在`button`，输入区关闭，用户已开启实体模式。Engine把物理按键规范化为事件，`input_router::handle_key()`将它放入队列执行，`route_key()`验证活动的窗口和实体模式，再通过`send_window_event()`发给这个窗口所属会话。发送时，`window`写的是该会话的本地窗口ID。服务器对象表内部使用全局映射，应用仅需理解自己的本地ID。两个应用即使都创建编号`100`的窗口，也会经由不同会话到达不同目标。

对于同一物理按键，`key_down`与`key_up`表达两次状态变化。事件的`key`是规范键名，`shift/ctrl/alt/meta`说明当时的修饰状态。按下还可能附带键盘译码产生的`text`，例如按下字母`A`且没有修饰键，译码结果可能是`a`。但键名用来按键绑定，文本用来交给编辑器，两者必须区分。`Shift`本身通常不生成文本，`Backspace`对应编辑动作，IME提交的“你好”可能由许多键共同产生。将`text`写作按键标识会丢掉这些差别。

若输入区关闭且当前为虚拟模式，Engine的普通实体按键路径不启用。虚拟键盘作为输入区辅助组件，也要达到活跃条件才可以向旧路线或当前路线发键。这一状态下，手柄仍可直接激活窗口控件。输入法路由关注的是键盘和文本事件，激光点击不需要先经过IME再决定是否按下按钮。

### 菜单助记符与输入法组合键

SDK接到`Alt`按下事件时，会让当前窗口的`menubar`显示助记符下划线；进入菜单键盘导航后也会显示下划线。Engine只为独立按下、松开的`Alt`释放事件附加`alt_tap=true`。输入组件自动转发这次释放时保留该字段。SDK同时检查当前窗口和待激活状态，条件满足时才切换菜单键盘导航。

`Alt+Shift`由Engine作为输入语言切换处理。组合键释放和输入路径排空生成的释放采用普通键事件，切换后原`textbox`继续持有编辑焦点。排查时分别记录键的按下/释放、`alt_tap`、IME选择与控件焦点。

### 输入区开启时经过IME

输入区开启后，实体路径的起点仍是物理键盘，但是`route_key()`将规范事件发给当前IME。允许IME实现多种行为。它可以消费组词用的按键，按需要绘出候选界面，可以在用户确认时提交文本，也可以把未消费的按键原样作为键事件转给应用。例如输入框里已有未提交的拼音，按空格可以被IME消费用来选词。没有组合内容时，IME可按它的行为决定采用普通空格输入或转发。应用通过事件类型区分按键和完成的文本。

虚拟模式多一个起点。`layout`把激光命中的键转换成`key_down/key_up`，通过`input_provider_send`发给Engine，Engine只在它仍拥有该路径的发送资格时转给IME。此后和实体模式共享后半条链。内置EasyVRUI English直通按键，使用英文标识。内置拼音和日文IME各自绘制候选窗，候选窗按钮固定使用中文或日文。普通应用的输入条按SDK界面语言显示。第三方IME也可用独立辅助窗实现自己的候选界面。

|当前输入区|来源条件|路由到应用前的路径|
|---|---|---|
|关闭|实体模式有有效窗口|物理键盘→Engine→普通窗口所属SDK|
|开启|实体模式|物理键盘→Engine→IME→Engine→普通窗口所属SDK|
|开启|虚拟模式|`layout`→Engine→IME→Engine→普通窗口所属SDK|

这三条路都把最终的控件选择留在SDK。收到`ime_submit`时，SDK把`text`当作完成的文本输入，沿当前事件所属窗口的编辑焦点处理。在输入区开启期间，SDK处理`key_down`时会区分按键操作与IME提交的正文，以免一个已经送给IME的字符又被原样写一次。核对实际行为时，可把一个组合过程记录成事件序列，分别问每一项是“按键交互”还是“完成文本”。输入法如果既转发普通字母的文本又提交相同字串，会在消费规则上发生重复，路由层不会自动理解候选词的意义。

## 3.应用与组件分别用哪些协议动作

### 开启输入区由当前普通窗口请求

SDK从焦点编辑器计算窗口逻辑矩形。滚动容器中的输入控件可能只露出一部分，`get_input_area_rectangle()`组合祖先范围，取适合定位辅助界面的面积。若编辑器不可交互、只读或者没有正面积，SDK应通过输入状态管理停用输入区，而不是提供一个零宽高窗框让组件猜测。应用只需要提供窗口与几何范围，候选窗口的高度与内容由IME自身安排。

下面是一条在虚拟模式下请求开启输入区的例子，字段的坐标仍以左上角为原点。实际会话填写对应自身的凭据字段和请求序号。

```json
{
    "message_type": "request",
    "id": 21,
    "session_id": 1,
    "session_token": "<应用会话令牌>",
    "op": "show_input_ui",
    "window": 100,
    "enable_virtual_keyboard": true,
    "enable_ime": true,
    "rectangle":
    {
        "left": 24.0,
        "top": 124.0,
        "width": 590.0,
        "height": 42.0
    }
}
```

Engine的`input_router::handle_operation()`核对这是普通应用会话，以会话和窗口ID查找对应表面，要求它是当前窗口，并读取可选的`enable_virtual_keyboard`、`enable_ime`（省略均为`true`）以及有限的数值与正的宽高。`enable_ime=true`要求可用IME，虚拟模式下`enable_virtual_keyboard=true`要求可用`layout`；当`enable_ime=false`时（如`screen`控件仅启用虚拟键盘或直通实体键盘），按键直接投递给当前窗口SDK。本次应用变更时再次检查会话仍然存活与窗口仍然是当前目标，避免应用在排队期间关闭后还被打开辅助区。当前已有输入矩形时，仅位置调整可直接更新矩形，变更组件开关则先排空旧路径再应用新配置。关闭输入区的请求是`hide_input_ui`。Engine对已经关闭的区域可以直接返回成功，对正在使用的路径则先排空。

### `input_ui_state`按接收方描述不同视角

Engine发布`input_ui_state`时，普通应用收到`window/physical/rectangle`。`rectangle`为`null`表示该应用窗口当前没有输入区。组件收到`active/physical/rectangle`。组件在当前路径中必需且输入区有效时，`active`为真并给出实际矩形。否则收到空矩形。一些更新附带`provider_list`，用于更新输入条或组件选择器。该列表里的选择状态与本条状态事件的`active`含义不同。一个典型情况是实体键盘已经生效，虚拟键盘组件仍在已知配置里，但它收到`active=false`。

下面是IME处于当前输入链时可能收到的状态。这个例子展示了组件视角。普通应用获得相同的几何时，使用`window`来标明关联的本地窗口。

```json
{
    "message_type": "event",
    "event_type": "input_ui_state",
    "session_id": 3,
    "session_token": "<IME会话令牌>",
    "active": true,
    "physical": false,
    "rectangle":
    {
        "left": 24.0,
        "top": 124.0,
        "width": 590.0,
        "height": 42.0
    }
}
```

区分这两个视角有很实际的好处。IME只需判断自己的输入帮助界面是否需要启用，普通应用要知道该关闭哪一个输入区或把辅助条挂在哪个父窗口。协议表达的是窗口层路由，SDK可以继续保有多个控件自己的本地焦点与选区。若把组件的`active`当作应用焦点，切换实体模式会把虚拟键盘关闭错误地理解为文本框丢失焦点。

### 文本与按键的输出都从组件路径回到Engine

`input_provider::send_event()`将事件编码到`input_provider_send`的嵌套`event`对象。组件身份来自连接的会话。引擎会清理嵌套事件中的会话和目标窗口字段，按当前或者排空中保存的路线决定目的地。`layout`只能提交键事件。`ime`可以同时提交未消费键和`ime_submit`。两条分支检查字段类型，键或文本要能从当前协议编码读取。IME可以通过`commit_text()`表达提交正文。

```json
{
    "message_type": "request",
    "id": 47,
    "session_id": 3,
    "session_token": "<IME会话令牌>",
    "op": "input_provider_send",
    "event":
    {
        "event_type": "ime_submit",
        "text": "你好"
    }
}
```

Engine发给应用时写入`message_type="event"`和关联窗口的本地`window`。这使应用收到的是一条经过路由的窗口事件。输入法的猜词历史、未完成组合串和候选界面可以留在IME内部。提交正文前，IME窗口上绘出的内容可能变化很多次，每次变化都走普通窗面绘制，而最终正文事件只在选择提交时产生。不要把候选绘制频率和文本事件频率混在一起，后者直接修改应用中的编辑结果。

## 4.角色互斥与辅助表面的生命周期

一个SDK会话一旦注册为`layout`或`ime`，该连接按输入组件的角色运行，只创建辅助表面。普通应用负责在自己的有效窗口中开启输入区。这个边界可防止候选窗口一出现就把自己选作最终输入目标。用户点候选项时，事件送给该辅助表面所属组件，组件向Engine报告结果，实际当前应用窗口仍是父路由目标。普通应用会话也可以为本会话的当前输入区提供输入条等辅助窗。

Engine用`input_router::is_input_ui_surface_active()`验证辅助表面归属和是否处于当前输入链。组件失活、当前窗口失效或输入区关闭时，对应表面不再具备这条关联。计算位置时，`get_reference_pose()`读取当前普通窗口参考位姿，用输入区水平中心减去辅助窗半宽，得出辅助窗左边。竖直方向从输入区下边缘起，先排应用输入条，再排IME候选界面，再排虚拟键盘，使用已显示且有效的前序辅助窗高度累加。实体模式下没有活动`layout`，因此自动省去虚拟键盘区域。宽度变化后重新按中心对齐。辅助窗的缩放继承拥有窗口，微小的前后偏置根据观察侧避免表面贴在同一位置上。

设输入区在窗口坐标`left=200`、宽`240`，其水平中心是`320`。假设辅助窗自身没有额外位移、`physical_scale=1`、当前IME宽`400`逻辑像素，按同倍率换算，IME左端相对于窗口左上角约为`0.320−0.200=0.120`米。若IME根据候选个数把逻辑宽改成`280`，左端变成`0.320−0.140=0.180`米，中心仍是`0.320`米。输入区下边若位于第`300`像素行，则第一块辅助窗在窗口局部`Y≈−0.300`米处开始。这个算式说明同一IME可以复用任何父输入区域，Engine无需知道显示了几个字或使用何种词库。

模态窗口会改变实际可交互目标，不能让已阻塞或已隐藏父窗继续接收新按键。Engine在`invalidate_window()`中会及时使目标无效，若一个正在排空的旧窗也跟着失效，则把`old_window_valid`清掉。旧IME依然可以完成自己的清理动作，真正向旧应用投递时还要检查它是否已经消失、隐藏、被禁用或失去有效位姿。这个细节很重要。保存旧窗的目的在于保留指向旧路径的身份，并且只给仍合法的旧目标。窗口消失后的文本不能借新窗口存活而自动改投新窗口。

## 5.从两个竞态推导为什么必须串行排空

### 旧候选为什么会出现在新输入框

从一条故意简化的错误实现开始。Engine只维护变量`current_window`，收到IME输出时无条件读这个变量。时间顺序可能是

|时刻|动作|简化实现中的状态|
|---|---|---|
|`t₀`|输入框A收到组成拼音的按键|`current_window=A`|
|`t₁`|用户确认候选，IME开始查结果|结果还在旧IME内部|
|`t₂`|手柄选择窗口B|`current_window=B`|
|`t₃`|旧IME算完并提交“你好”|按新变量将“你好”送给B|

问题在于`t₁`和`t₃`之间的工作属于旧路径，`t₃`时读取的全局变量却描述新路径。方案必须让这两件事不混用。最朴素的修补是把所有旧IME的后续输出丢掉，这会使A忽然失去用户已确认的文字。固定等`50`毫秒也只是按估计推迟`t₂`，负载变化时没有一个可靠的完成条件。TCP有单连接顺序，但用户点击、layout与IME可以来自不同连接，某个进程的算法任务也不属于另一条连接的读写顺序。需要一个明确的“旧工作完成”信号。

串行排空先冻结旧路线的几个必要身份。旧目标是`old_window`，组件是`old_layout`与`old_ime`。新路线还没生效时，符合旧阶段资格的结果可由`forward_provider_event()`继续投递给仍有效的旧应用。待相关组件确认已经没有旧输出，Engine才变更当前窗口。可以看到，这条协议用因果边界代替猜延迟。即使`t₃`来得稍晚，只要在合法排空阶段内，`t₃`仍只能影响A。

另有一条更细的SDK侧时间线。假设A内有文本框一和二。旧IME在第一次输入里提交最后一个字。用户按`Tab`，SDK请求收起旧输入区，此时仍要保留文本框一的焦点。Engine完成旧通道后发送关闭成功响应。事件与关闭响应在连接上有顺序，SDK在下一轮泵送时先给文本框一应用已经到达的正文，再从成功回调应用待切换目标，之后才能打开文本框二的输入区。这条时间线验证了为什么切换既涉及Engine的旧会话身份，也涉及SDK的旧编辑焦点。

### 为什么先等layout，再让IME确认

虚拟键盘在链条上游，IME在下游。上游最后一项输出可能变成下游的新工作。设旧layout正在处理一个带修饰键的键序列。切换开始时它还有最后一个`key_up`等着发送。如果Engine同时让两者排空，IME可能先发现“自己目前没有任务”就回确认。几毫秒后，layout最后的按键才到Engine，此时已经没有可接收这条尾部按键的旧IME。这会丢掉末尾按键，或让新IME看见一条它未处理过的释放事件。

因此确认顺序要遵循依赖关系。让layout先完成它的发送，Engine在对应阶段仍把这些键转给旧IME。确认后关闭这个上游入口，再发`input_drain`给IME。此时IME收到的旧通道输入集合才封口，才能有意义地等“我已经处理了全部属于旧路径的工作”。这和生产流水线停机一样。先让最上游停止往传送带放东西，等最后一件物品进入下游，再关下游。如果反过来关闭下游，剩下的物品永远走不完整条链。

实体键盘路径没有活跃的虚拟layout，旧IME存在时可以直接进入IME排空。旧输入区本来没有组件，或旧组件已断开时，程序可以跳过不存在的阶段。跳过是根据真实路由和活跃连接做出的决定。两次排空动作从逻辑上依然有同样的依赖次序。

## 6.四阶段状态转换与实际实现

### 阶段一，截住新路线并保存旧路线

从`input_router::begin_transition()`进入。代码把`draining`置真，保存要在最后执行的`completion`，冻结旧窗口、旧组件和旧目标有效性。与此同时清空指针运动的相关缓存并重置IME快捷键暂存。对于已经通过Engine路由的实体按下状态，会按旧路线产生配对的`key_up`。例如按住`Shift`切窗，旧IME或关闭输入区时的旧窗口接收用于收尾的释放事件。这时新路由继续送入的普通输入会排队，避免同时走到两套目标。

为什么要合成释放？假设A收到`Ctrl down`之后，用户还没松手就切到B。如果只记录焦点新旧变化，A可能一直认为`Ctrl`按着，B收到一个它从没看见`down`的`up`。`pressed_key_map`保存Engine曾经路由的按下事件。合成释放时，代码将原事件改成`key_up`，移除正文`text`，并把该键放入`suppressed_key_set`。随后真实的物理释放到达才从抑制集合删除。这样切换期间仍按住的同一物理键不会立刻在新目标上重新生效。测试这件事要同时检查旧目标得到释放、真实松手不会变成新目标的孤立事件、新的按下能重新到达。只测试切换后能否继续输入字母，无法发现修饰键残留。

### 阶段二，等旧layout封口

Engine将`draining_layout`置真。如果旧layout仍能发送，就将其会话记录为`waiting_session`，设置该阶段期限，然后沿它的连接发送`input_drain`。仍处于这一阶段的旧layout可以发送旧键，Engine把这些键往旧IME转发。已经沉淀在旧IME里的输出也可按旧应用的合法性继续投递。排空时的快捷键处理不会再为旧layout输出发起新的IME选择。

`input_provider_drained`不是一个“随便谁发都能完成”的按钮。在`input_router::handle_operation()`中，它要求`draining`为真且发起会话等于当前`waiting_session`。这意味着旧IME不能抢在旧layout前发出有效确认，旧layout也不能在IME阶段再确认一次推进到下一条路线。组件连接已经通过会话验证，发送者不能在事件字段里改个`role`就顶替正在等待的组件。

### 阶段三，等旧IME完成转换与发送

收到layout确认后，`advance_drain()`清空阶段等待者，改变`draining_layout`，并按旧IME是否存活决定下一步。如果还能等旧IME，就设置新的`waiting_session`和独立期限，再发送`input_drain`。此后来自旧layout的新输出失去排空阶段的发送资格。旧IME在完成之前可提交最后的键和文本。Engine通过旧窗口引用选择去向，实际投递时仍检查目标合法吗。这一阶段的验证要同时看“IME最后的输出排在哪条线上”和“窗口当时是否真的还能接收”。旧窗口已关闭时无可编辑对象，Engine保留清理流程并阻止正文被改送到别处。

两种消息可以写成下列协议对象。第一条由Engine发到正在等待的组件连接，第二条由该组件向Engine确认。例子以`layout`阶段为例，IME阶段使用它自己的会话身份。

```json
{
    "message_type": "event",
    "event_type": "input_drain",
    "session_id": 2,
    "session_token": "<layout会话令牌>"
}
```

```json
{
    "message_type": "request",
    "id": 48,
    "session_id": 2,
    "session_token": "<layout会话令牌>",
    "op": "input_provider_drained"
}
```

协议没有要求应用在这两条消息中拼接输入轮次编号。阶段由Engine内部状态和等待连接共同决定。组件通过SDK维护排空标志和任务计数，连接本身保持有序。若错过边界而组件已被吊销发送资格，不能通过自行造一个轮次字段重新获得资格。

### 阶段四，提交切换并恢复正常派发

两条旧链都完成或已被安全终止时，`finish_transition()`收起旧等待会话、旧组件ID与旧窗引用，取出之前保存的变更动作，设置`finishing`来约束这段提交期间的队列处理。变更动作由触发原因决定。比如关闭要将矩形置空，切窗要更新当前选择，切模式要修改`physical`，切组件要激活新的会话。完成动作会刷新路由、发布新的`input_ui_state`并继续处理队列。这个边界完成后，新输入才能按新的组合路由。

这四个阶段可用一个窗口内的实际交互复核。用户在文本框一输入，随后点文本框二。先更新SDK待选择的目标，再由旧路执行排空。系统可以已知道用户想去哪，却仍将旧输出送到旧目标。等词语落到旧编辑器后，新矩形和焦点才能一起启用。应用也可能在排空期间再次请求关闭，SDK会把相关回调并到已经进行的一轮关闭中。把“收到新意图”和“将新意图写入活动路由”分开，才能解释眼前有短暂停顿但焦点没有错乱的情况。

## 7.组件如何知道工作已经排干

### 两个计数分别约束本地任务和发出的结果

输入组件需要检查两种工作。第一是进行中的本地任务，例如从后台词库查找候选。第二是已经逻辑完成但通过连接发出、尚未取得响应的输入事件。SDK的`input_provider`用`input_task_count`与`pending_send_count`分别表示。

调用`begin_input_task()`后，计数增加。任务完成时调用`finish_input_task()`，减少计数并重新检查能否确认排空。后台线程返回结果时，应在该组件的SDK线程接收结果并通过正常接口发送。SDK的连接有拥有线程要求，工作线程适合做计算，回到拥有线程再处理对象与发送。关键顺序是先交付属于任务的最后结果，再结束任务记账。若先调用`finish_input_task()`使计数归零，而`send_event()`还没开始，则排空可能提早确认。

`wire::send_event()`开始发事件时增加`pending_send_count`。收到请求响应后减少计数，再调用`finish_drain()`。这使“已算好”与“Engine已接收请求”能分别观察。进入`process_drain()`时，SDK会用一次任务计数包围该回调，确保回调期间发出的收尾工作被覆盖。只有进入排空、还没发过确认、两个计数都为零，才发送`input_provider_drained`。`drain_ack_sent`标记确认已经发出，限制该组件再发送属于这轮旧路径的新数据。收到后续状态通知时，根据新状态恢复或保持失活。

可以手算一个计数轨迹。旧IME先有一个词库任务，计数`(1,0)`。进入排空回调时暂时加一，成为`(2,0)`，回调返回后为`(1,0)`。词库结果回到UI线程，提交一个`ime_submit`后变成`(1,1)`。随即结束本地任务，剩`(0,1)`。应用已经有机会收到最终文本，但IME仍等它自己的发送响应。等Engine回包，才到`(0,0)`，之后发送确认。如果把这两个一看起来都很小的计数合并成“异步工作做完了”的布尔量，就会遗漏至少一个时序。

### 超时、断线与撤销资格

一个实现可能一直不确认，或进程在排空中退出。Engine给每个实际等待的阶段设置`DRAIN_TIMEOUT{10}`秒期限，使用单调时钟。转进下一阶段时设置新期限。`input_router::update()`发现当前等待会话超时，就使其生命周期失效，调用关闭连接的路径并通知组件管理器断开。若状态仍指向这个超时会话，再推进阶段。已经关闭连接的旧进程即使继续计算出结果，也无法从原会话提交。这样窗口切换可在一个不合作的组件之后继续。

断线走同类边界。`disconnect()`标记会话失效，清理该会话的待执行任务和相关选择流程。如果恰是当前等待会话，继续推进。旧窗口所属应用断开也要使窗口无效，与清理输入组件是两条可同时发生的事件。生命周期检查用于验证排队任务在恢复时仍有发起资格。把“曾经发出一个合法请求”视为“以后必定能执行”，会在长等待后留下过时操作。

组件排空期限与连接心跳分工不同。活跃连接可以一直有心跳，但负责词库的任务仍然卡住，因此这条路径需要独立的完成期限。反之，已断开的组件无需再等十秒。调试物理模式切换等待时间长时，可记录当前等待的是layout还是IME，旧会话是否仍然连接，哪一项计数迟迟不归零。只看当前VR窗口有没有刷新，难以判定哪一阶段在等。

## 8.SDK的关闭完成怎样衔接本地焦点

在应用一侧，`ui_runtime::hide_input_ui()`先更新本地请求意图、同步输入条，并收集`hide_callback_list`。若已有一次关闭在进行，后来的回调加入同一轮。在线时发异步`hide_input_ui`，由UI线程下一轮泵处理响应。离线时，SDK直接用成功结果完成本地清理。`finish_input_hide()`清除`input_hide_pending`，成功时清理已开启区域与相关对象，然后把本轮完成列表移到局部并逐个调用。这样回调本身发起新一轮操作时，会走新的等待列表。最后，成功路径通过`sync_input_ui()`检查是否有需要开启的区域。显式隐藏后的窗口可以保留原有焦点并保持输入区关闭，用户再次进入才重新启用。

本地有两个值得区别的时刻。用户按下`Tab`时，SDK可以记录待选择的控件。对应Engine的排空结果完成后再更新真正接收文本的控件。在线连接把异步响应和事件分开存储，但UI泵按接收顺序交错取出。Engine先将旧正文发入同一应用会话，再完成关闭，SDK有机会在响应回调改变焦点前处理旧正文。同步`connection::request()`只消费自己的响应。若某个文本事件回调内部为了剪贴板又做同步请求，先完成请求再回到原本的控件事件。普通异步工作等下一次UI泵，不会在这次RPC等待中抢先应用焦点。

一个有用的反例是在应用脚本里把同步调用当作“处理所有排队事件”的手段。新版连接中，同步调用返回时，其它异步响应可能已经到达，却仍在队列里等待显式泵。如果写了自动化脚本，应使用UI泵和所需条件直接验收。测试可以构造旧正文事件、关闭响应、新键事件的连续三项，对比分发时刻和文本框最终内容。正式实现中的排空保证依赖这条顺序保留。

## 9.实体键盘捕获的边界与释放条件

### 两条线程配合，钩子只做快速判定

Windows驱动在`keyboard_broker.cpp`里使用`SetWindowsHookExW(WH_KEYBOARD_LL,...)`注册低级键盘钩子。持有钩子的线程有自己的Windows消息循环，`run()`用消息等待和`PeekMessageW/DispatchMessageW`取得操作系统交给它的事件。钩子读取键码、扫描码和修饰状态，调用`keyboard_policy::filter()`决定是否托管这个事件，并快速尝试把包交给进程内队列。`CallNextHookEx()`是普通放行路径。只有符合内部规则的事件被抑制。

Engine线程取得队列里的包，基于快照再次检查它是否仍属于当前有效目标。文本译码在后面，`keyboard_decoder`按Windows键盘布局和当时状态，将按键翻出文本，并交给`runtime.handle_key_input()`或`handle_key_up()`。这个分工使钩子线程只处理很短的、可预测的工作。钩子里做网络等待、等待候选计算或直接访问应用控件，不仅会混淆拥有线程，也会使操作系统输入链被拖慢。

低级钩子观察的是Windows传给它的键盘事件。它的作用范围由系统输入环境决定，不需要将它理解为能接管所有物理设备的原始数据。应用窗口的激活策略也在本程序内部维护。安装钩子使服务可以识别切换键，而实际是否拦截普通按键由捕获资格控制。释放普通按键的捕获资格和卸载Windows钩子，是两个不同动作。

### 捕获资格是可过期的窗口租约

`keyboard_policy::is_active(now)`要求实体模式、线程已进入监听状态、有效窗口ID非零、租约仍在期限内。`keyboard_broker::update()`为当前窗口续期`FOCUS_LEASE_MILLISECOND=500`毫秒。窗口身份变化时修改`epoch`，同时使先前译码状态失效。租约和纪元可以看成钩子手里的一张短期票证。它说明“这组键能够交给哪一次输入上下文”。若Engine暂停过久没有续期，钩子失去接管普通新按键的资格。若排队的包来自旧纪元，消费侧也不会把它当作新窗的按键。

普通`Pause`用来切换实体模式。只要驱动已处于监听状态，就能处理这个切换动作（服务托管模式下由Helper同步活动输入桌面的键态，安全桌面仅登记Pause热键用于模式切换）。真正捕获普通键还要满足租约条件。`Ctrl+Pause`请求Desktop，`Ctrl+Alt+Pause`请求重置跟踪中心（成功后在新World原点显示15秒红十字），这两类全局快捷键有自己的匹配路径。普通IME切换快捷键则要结合当前键盘模式和有效上下文，避免修饰键组合被跨窗口错误领取。`PrintScreen`（VR视角）与`Alt+PrintScreen`（当前选中普通窗口的平面纹理）截图请求也须绑定有效实体捕获上下文，成功后均写入剪贴板并显示约2秒居中输入穿透提示。实现会跟踪修饰键、重复按下、原始捕获目标与真实释放。这样一个已经被桌面应用收到按下的键，通常仍由原路径收到配对释放，而不是在按住期间突然交给VR。

上下文过期、窗口失效、退出实体模式时，普通新键放行。已捕获键的原始归属则用于处理其配对释放与清理，避免两边都留下悬空状态。如果设备或队列无法继续可靠接管，策略会取消实体模式，让异常不会由一个一直被压住的输入链扩散。线程停止时清零捕获资格并由`release_hook()`调用`UnhookWindowsHookEx`。这些措施分别防止“失去窗口后继续抢新键”和“离开应用后还保有钩子”。

### 输入内容与诊断信息分别处理

项目的正常输入路径通过内存中的按键包、译码结果、IPC事件与编辑器缓冲处理用户文本。钩子和路由层的诊断关注注册失败、超时、会话归属、任务计数和事件种类。检查排空不需要留存用户实际打了什么。测试应使用人工构造的短文本和本地标记，例如用`old`与`new`验证去向。生产模式下，可记录“旧IME完成，等待会话编号及时间”来判断时序，无需记录组合串或真实候选内容。

一段文本也可能由第三方IME选择保存到其自己的功能数据，例如用户词频。那属于组件自己的策略。Engine的窗口、会话和排空逻辑关注最后事件应送到哪，而不需要持有组件学习数据。区分这两个层次能使诊断范围清晰。若只想确认文本是否串窗，计数、发生顺序、当前窗和旧窗的ID已经足够。

## 10.用日志和几个小实验验证边界

遇到“切换输入法以后旧键还有反应”，先确认结果事件来自哪个会话。若是在旧IME还处于排空阶段，旧目标仍有效，旧结果可能应落到原编辑器。排空确认已经完成却仍收到该会话结果，就要看阶段资格检查和连接状态。遇到“有些字没送到”，分别检查任务是否登记、提交后是否还有未确认消息、SDK是否泵送了这些回包。只看候选窗消失时间难以确定正文去哪了。

遇到“实体键盘卡键”，可以用最简单的一条路线模拟。进入实体模式，保持目标窗口可交互，按下一个修饰键。切换用户窗口，观察旧路径收到了配对释放。在仍物理按住该键时尝试按下另一个键，记录新窗口实际收到什么。真实松手后再按，确认它能作为新的一组按下进入新路径。若只有关闭窗口或跟踪丢失时出现问题，要同时检查钩子的租约、Engine的`selection_valid`与SDK的本地焦点。

写测试时应按以下顺序定位。

1. **先验证单路线。**在输入区关闭的普通窗口看`key_down/key_up`能否到达。开启输入区后，在虚拟模式用layout产生按键，在实体模式绕过layout，观察IME是否都能按同一接口消费事件。
2. **再验证旧输出。**暂停旧IME完成，触发切换，将结果保留为`old`。在还有效的旧阶段放行它。确认旧输入完成后，用`new`进入新路径，检查两个文本框没有相互写入。
3. **最后验证失败路径。**用测试夹具模拟组件不确认或断线，确认超过旧阶段边界后，失去资格的会话无法再产生任何投递。若窗口先被销毁，检查旧路线完成时没有将正文自动转到新的窗口。

查源码时，从Engine的`core/input_router.cpp`看`begin_transition()`、`advance_drain()`和`finish_transition()`。接着看`driver/keyboard/keyboard_broker.cpp`与`keyboard_policy.cpp`如何采集和租约判断。应用端看SDK的`core/ui_runtime_session.cpp`和`core/ui_runtime_input.cpp`，组件端看`input/input_provider.cpp`。对应的回归测试包括`tests/sdk_audit/sdk_audit_focus_probe.cpp`的旧编辑器和嵌套排空、`tests/grid/grid_pointer_ime_probe.cpp`的焦点切换、`tests/nightly_ime`中的排空提交用例。这些用例最有用的断言不是“弹窗最后关了”，而是“每一条输入在它该属于的编辑器和阶段被处理”。
